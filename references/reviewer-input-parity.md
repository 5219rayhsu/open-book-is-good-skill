# 審查者輸入等價（reviewer input parity）


## 目錄

> `head -100` 看不到全貌，故列出所有節名——**用節名搜尋，不要從頭讀**。

- 1. 這個病的五個化身（同一根因）
- 2. 三層零 token 防禦
- 3. 本質上給不了時的協議（圖片）
- 4. 回報而非誤報：finding schema 與零 token 分流
- 5. 熔斷器（擋下一個未知化身）
- 6. 為什麼這是淨省，不是增加成本
- 7. 已知待辦：`severity` 與 `c` 撞字面值
- 物化的 payload 沒進版控，等於沒有物化
- 字面比對的查核器：「名字對不上」與「沒有引用」同形

---

> **一句話**：審查者拿到的資訊少於撰寫者，就會把「我看不到」誤報成「內容錯」，
> 而下游修復站會照著把**正確**內容刪掉——所以這類誤報比漏報更糟。
>
> 治法不是再加一條 prompt 鐵則（每個化身都要再加一條），而是把「上下文可見性」
> 從**隱性約定**變成**宣告式、機器強制、發包前驗證**的性質。

## 1. 這個病的五個化身（同一根因）

| 化身 | 撰寫者有、審查者沒有 | 後果 |
| --- | --- | --- |
| **圖題**（最早） | 圖片本身（撰寫者附圖、純文字紅隊只有 `has_figure` 旗標） | 圖衍生內容被報成「無據增添／圖缺失」，**fix 率從真實約 18% 虛高到 43%**——過半 fix 量是假的 |
| **承上題** | `prev`（同卷前一題的題幹／選項／答案） | 生成站切塊器帶了、紅隊站切塊器沒帶。**對照實驗**：同 39 則分別以「無 `prev`」與「有 `prev`」各審一次，**判決翻轉 10 則（26%）、且全部是 `fix`→`pass`、零反向** |
| **題幹說有圖但圖檔不存在** | 兩邊都沒有（撰寫者也瞎） | 詳解成為**包裝成推理的猜測**，且 lint、答案錨、紅隊**全部通過**——因為紅隊也看不到那張不存在的圖 |
| **題組共用 `passage`**（2026-08-09，**發生在註冊表上線之後**） | `passage`（題組的共同閱讀材料） | 分科測驗導入這個欄位，**它從來沒被加進註冊表**，於是三層防禦全部靜默放行。實測 144 則 finding 有 **83 則（58%）** 是「紅隊看不到 passage」誤報，110 個 `fix` 判決有 62 個被污染 |
| **`type`（單選／多選／非選）**（2026-08-09，**封閉集合檢查上線之後**） | `type`——它被歸進「純中繼資料」豁免清單而被濾掉 | 分科測驗 192 題非選沒有答案鍵、沒有選項，審查者不知情就會拿選擇題三段式去判。**豁免清單是封閉集合檢查自己開的靜默通道**，見 §2.1b |

第三個化身特別要記住：**parity 只保證「審查者 ≥ 撰寫者」；若撰寫者當初就瞎，兩邊一起瞎、
parity 照樣通過。** 所以必須有獨立的「源頭可審性」檢查。

## 2. 三層零 token 防禦

### 2.1 欄位可見性註冊表（擋設計期漏宣告）

刪掉各站手寫的切塊器，改成單一註冊表，每個欄位宣告「誰看得到」，並在 **import／CI 時就
assert**（不用等跑完批次）：

```python
@dataclass(frozen=True)
class F:
    kind: str                    # id | evidence | derived | output
    gen: bool = False
    rt: bool = False
    fix: bool = False
    degraded: str | None = None      # 給不了原件時，改給什麼
    blind_policy: str | None = None  # 盲區怎麼處理、誰是權威

# 鐵則：evidence 且撰寫者可見 → 審查者也必須可見，
#       或同時宣告 degraded ＋ blind_policy。沒宣告就 raise。
for name, f in FIELDS.items():
    if f.kind == "evidence" and f.gen and not f.rt:
        assert f.degraded and f.blind_policy, name
```

> 🔴 **這裡原本寫「下一個化身在被發明的那一刻就會被擋下」——那句話是錯的，2026-08-09 被
> 實測推翻，而且被推翻的正是它自己舉的例子（題組共用說明）。**
>
> 上面那個 `for name, f in FIELDS.items()` 迴圈**只走訪註冊表自己**。一個**從來沒被加進去**
> 的欄位不在 `FIELDS` 裡，所以它不進迴圈、不觸發 assert、payload 靜靜地把它濾掉、
> parity 因為指紋裡沒有它而回報一切正常。**自我稽核的迴圈是循環論證：
> 它只能證明已登記的欄位有登記。**
>
> 註冊表是**人工維護的白名單**，它對「沒有人想到的欄位」永遠是靜默的——
> 而「沒有人想到」正是它要防的那件事的成因。

### 2.1a 把白名單變成封閉集合（擋「漏登記」本身）

新增一道與註冊表方向相反的檢查：不問「登記的欄位有沒有宣告」，
改問「**實際落盤的資料裡，有沒有欄位不在註冊表中**」。

```python
_KNOWN_NON_FIELD = {"exam", "type", "round", "year", "no", "group_id"}  # 純中繼資料

def unregistered_keys(record: dict) -> list[str]:
    return sorted(set(record) - set(FIELDS) - _KNOWN_NON_FIELD)

# 紅隊發包前：未登記欄位先擋，再跑 parity
gaps = [f"unregistered:{k}" for k in unregistered_keys(src)]
gaps += parity_check(gen_manifest(src), pay)
```

**canary 必須用一個不在註冊表裡的欄位**（`assert unregistered_keys({..., "audio_clip": "x"}) == ["audio_clip"]`）。
只用已登記欄位寫的 canary，證明的是「已知的沒退化」，對下一個化身一樣沉默。

> 一般化：**任何宣稱「這道閘擋得住未來的 X」的說法，要用一個閘作者沒想到的 X 去測。**
> 用想得到的 X 測，測的是想像力不是閘門。

### 2.1b 「純中繼資料」是最容易誤判的那一格

封閉集合檢查要有一份「不參與可審性的中繼資料」豁免清單（`exam`、`year`、`round`、
`no`⋯），否則每一筆資料都會噴一堆假警報。**而那份豁免清單，就是新的靜默通道。**

實測 2026-08-09（同一天、同一份註冊表，化身四）：`type`（單選／多選／非選）
被歸進豁免清單，於是紅隊 payload 濾掉它。分科測驗有 **192 題非選**——
沒有答案鍵、沒有 A–D 選項、詳解本體是分項演算步驟。審查者不知道這是非選，
就會拿選擇題的三段式結構去判它，把「沒有選項辨析」報成缺陷。
（同一份 `expl_lint` **早就**為 `type:非選` 開了結構規則例外，紅隊卻拿不到這個欄位。）

判準：**一個欄位是不是中繼資料，取決於下游拿它做什麼，不取決於它看起來像什麼。**
放進豁免清單前問一句：**有沒有任何一站會因為這個欄位的值而改變它的判準？**
會的話它就是 evidence 或 id，不是中繼資料。`year` 不會（沒有人因為是 114 年而改判準），
`type` 會（非選題整套結構規則都不適用）。

順帶：這一輪同時暴露了一個**便宜**的錯誤，正好當對照——`mkrt.py` 在 `src["ans"]`
直接 KeyError，192 題整批炸掉。那是最好的一種失敗：當場、明確、不可能被忽略。
**「這個欄位一定存在」的假設，是被第一個沒有它的考科打破的**，而打破時最好是爆炸，
不是靜靜地送出一個少了欄位的 payload。

各站 payload 一律由同一個 `payload(station, record)` 導出，不再各自從源資料重抽；
**紅隊 payload ＝ 生成 payload ＋ 生成產出（`t`, `c`）**，結構上保證超集。

### 2.2 源頭可審性 lint（擋資料期漏帶，也擋「撰寫者自己也瞎」）

生成站**發包前**跑，命中即不發包、先補資料：

| 檢查 | 缺口代號 |
| --- | --- |
| 題幹有「承上題」類詞但沒有 `prev` | `prev_missing_at_source` |
| 題幹引用表格但沒有 `table_md`（且無圖檔可代） | `table_ref_without_table` |
| 題幹說有圖但圖檔不存在 | `figure_ref_without_asset` |
| 圖檔存在但沒掛上 `figure` 欄 | `figure_asset_not_wired` |

> 🔴 **這些 regex 要調成高精確度、低召回。** 會誤報的預檢**比沒有預檢更糟**：它會攔下
> 正常題、逼人加例外清單，最後大家學會忽略它。實測誤報兩例，務必寫成回歸 canary：
> 「顯微鏡**下表現**的特徵」被 `下表` 命中；「心電**圖PR**間距」被 `圖[A-Z]` 命中。
> 校準方式：對全庫 stem 跑一遍、人工看完命中清單，寧可漏幾個交給下游。

實測產出（doctor 8,848 題，校準後 5 個真缺口）：其中 1 題「附圖中的上皮主要出現於
下列何者？」**沒有圖、完全無法作答**，而它的詳解專業得無懈可擊（單層柱狀上皮、纖毛細胞、
卵母細胞運輸）——結構 lint 通過、答案錨通過、紅隊也會通過。**只有這道預檢攔得住。**

### 2.3 物化 payload parity 斷言（擋兩站不對齊）

前兩個化身都是「程式碼看起來對、實際 payload 不對」，所以斷言要打在**落盤後的實際
payload** 上，並比 hash（連「`prev` 被截斷」「帶到舊版」都抓得到）：

```python
manifest[qid] = {f: sha1(record[f]) for f in evidence_fields_present}   # 生成站落盤時附
# 紅隊發包前（純 Python、零 token）
need = set(manifest[qid]) - DEGRADED_FIELDS
assert need <= set(rt_payload[qid])                              # 缺欄位 → 擋
assert all(sha1(rt_payload[qid][f]) == manifest[qid][f] for f in need)  # 陳舊／不一致 → 擋
```

**fail-closed**：不過的 qid 進 repair queue（補欄位是確定性操作），乾淨的照發；
失敗率超過閾值（如 2%）**中止整批**——那是切塊器 bug，不是個案。

### 2.3a 布林旗標的缺席與 `false` 同形——所以 prompt 的條件式要對上游斷言（2026-08-17 實測）

§2.3 的 parity 斷言比的是**證據欄位的 hash**，前提是「欄位在 manifest 裡登記過」。
但有一種欄位根本沒有 hash 可比，也不會出現在任何證據清單裡：**布林旗標**。
它的缺席與 `false` 完全同形，而 prompt 的規則正是以它為條件。

實測形狀（ast 詳解線）：

- `mkprompt.py` 寫了一整段**圖／表題鐵則**：「若該題 `has_figure` 為 true，
  **不得**因你看不到圖就報『圖缺失／題幹依據缺漏』」。
- `mkfix.py`（修復站上游）**有送** `has_figure`。
- `mkchunks.py` 與 `mk_blocks.py`（生成站與紅隊上游）**從來沒送過**。

於是那段鐵則的條件**永遠不成立**——不是偶爾漏，是一次都沒觸發過。紅隊照樣把
「文字未提供圖 2，無法核對」當 finding 交出來，正是鐵則明文禁止的那句話。
實測該批 114 題有 37 題有圖、全程盲判；翻回 8 天前的舊批輸入檔，同樣沒有這個欄位
——**不是迴歸，是一直如此**，而「一直如此」正是它從沒被發現的原因。

> **一般形式**：**條件永遠不成立的規則，觀測上等同於沒寫。**
> 它比「沒寫規則」更危險，因為文件裡看得到它，於是每個人都以為那件事被守住了。
> 這是 `gates.md` §A4「『我不知道』與任何合法值同形」在 prompt 層的同一個家族：
> 那裡是資料欄位，這裡是規則的觸發條件。

**閘門（跨檔對位，零 token，抄得走）**——打在切塊器上，因為切塊器才是唯一知道
自己「產得出哪些 key」的人：

```python
EMITTABLE = set(FIELDS) | {"qid", "stem", "options", "ans", "has_figure"}
PROMPT_KEYED = ("has_figure", "prev", "table_md", "passage")   # prompt 以其為條件的欄位

def guard_prompt_parity():
    src = (HERE / "mkprompt.py").read_text()
    missing = {k for k in PROMPT_KEYED if k in src} - EMITTABLE
    assert not missing, (f"mkprompt 以 {sorted(missing)} 為條件寫了規則，"
                         "但本檔產不出這些欄位——規則會安靜地永不觸發。")
```

它守的是**下一個**欄位：有人在 prompt 新增一條以欄位為條件的規則、卻忘了讓上游送得出來時，
發包前當場失敗。自檢要**故意把該欄位從 `EMITTABLE` 拿掉、確認斷言攔得下來**——
沒被否證過的閘門，不知道它有沒有在工作。

> **同一條原理也適用於自檢本身**（2026-08-17 同一輪踩到兩次）。`mkchunks.py` 的自檢
> 寫的是「counseling 應有送分題待補」——那斷言的是**待辦量**，而 `pick()` 只回還沒做的，
> 所以那批補完的當天它就永遠紅。**永遠紅的自檢兩天內會被註解掉**，連它真正要守的
> 「選題條件反了」也一起失守。改成斷言**極性**（`--free` 只撈得到送分題）之後，
> 又發現極性只在「有東西可撈」時檢得到——寫死在補完的那科上就是**空轉**：
> 永遠成立、什麼也沒守，而讀的人以為有守。
> **兩個失效方向要一起堵**：斷言不可綁定會歸零的進度量，而當它這次確實沒檢到東西時，
> 要**明講「本輪空轉」**，不要安靜地通過。零 token，一個 `print` 的事。

**兩個配套判斷（都是實測，別跳過）**：

1. **旗標只送「有沒有」，不送檔名。** 送 `figure: "xxx.png"` 給看不到圖的模型，
   只會誘它假裝看過；送 `has_figure: true` 才是誠實的資訊量。
2. **發現盲判後，先量再決定重不重跑。** 該批的處置是**不重跑**：量了 37 題有圖的
   生成端詳解，**0 則**出現「未提供圖／無法判讀」語氣——生成站從題幹自己推斷出圖存在，
   產出沒有退化；受損的只有紅隊的效率。修復站那條腿因為 `mkfix.py` 有送旗標而完好。
   **「上游壞了」不自動等於「產出壞了」**，中間隔著一次零 token 的量測。

### 2.3b 同一份資料的兩種表徵：學生看結構化、模型看舊字串（2026-08-17 實測）

§2.3a 是「欄位沒送到」。這一則更難看見：**欄位送到了，內容卻是另一個時代的**。

實測形狀：bank 的表有兩種表徵——結構化的 `q.table`（`headers` ＋ `rows`）與
markdown 字串 `q.table_md`。前端 `web/run.js` **只渲染 `q.table`**；切塊器的
`FIELDS` 裡有 `table_md`，於是 `q.get("table_md")` 直接抄那個字串送給模型。
某次維護把 37 張表重新掛載成結構化 `q.table`，**舊字串沒清**。40 題兩者並存、
5 題不一致。

**壞法不是缺資料，是錯位。** 舊字串把第一列資料當成表頭：

```
學生看到（q.table）              模型看到（舊 q.table_md）
| 國家＼年代 | 1830 | … | 1970 |   | 甲國 | 240 | 345 | … | 2705 |   ← 資料列被當表頭
| 甲國 | 240 | … | 2705 |          | --- | --- | … |
| 乙國 | 180 | … | 2130 |          | 乙國 | 180 | … | 2130 |
| 丙國 | 370 | … | 2225 |          | 丙國 | 370 | … | 2225 |
| 丁國 | 240 | … | 3605 |          （丁國整列消失）
```

該題問的正是「甲乙丙丁四國的先後順序」——模型看不到年代欄位，也看不到丁國，
卻仍寫出一則語氣完整、結論撞對官方答案的詳解（自標 `c=low`，是唯一的線索）。
**缺欄位會被發現，錯位不會**：少一欄模型會抱怨，欄錯位它會照著錯的欄位講得很順。

**規則**：

1. **哪一份表徵給學生看，哪一份就是正本。** 模型讀的那份必須**當場從正本推導**，
   不得讀任何預先算好的同義欄位。`table_md(q["table"])` 是一行的事，
   而 `q.get("table_md")` 也是一行——兩者長得一樣便宜，只有一個是對的。
2. **同義欄位並存時，寫一條斷言而不是一條註解。** 自檢直接釘住真實資料的表頭與末列：
   `assert md.splitlines()[0].startswith("| 國家＼年代")`、`assert "丁國" in md`。
   斷言會隨資料一起被驗證，註解不會。
3. **重新掛載／改資料表徵時，舊表徵要在同一個 commit 裡處理掉**（清空或改成從正本
   推導）。留著它就是留一個「看起來像資料、其實是化石」的欄位——這與
   `gates.md` §A3.2「工單旗標有兩個寫者，只有一個會清理」是同一個家族，
   差別只在那裡壞的是旗標、這裡壞的是整張表。

> **偵測手法（零 token，抄得走）**：對每一筆同時帶兩種表徵的紀錄，
> 拿正本重新推導一次、與既存欄位逐字比對，不一致就列出來。
> 它同時抓得到「陳舊」與「當初就轉錯」，而且不需要知道是哪一種。

## 3. 本質上給不了時的協議（圖片）

現行止血是叫紅隊「假設圖存在且支持詳解」——**那等於放棄審查**。改成兩件事：

### 3.1 `figure_desc`：讓紅隊有東西可核

圖題生成站**本來就看著圖**，要它在產詳解的同時多輸出一段 100–150 token 的**圖面客觀
描述**（圖型、軸、關鍵數值、標註）。邊際成本約每題 2%，一次付、終身用。
紅隊拿到後就能核：詳解的圖衍生敘述是否與描述一致、由描述推出的醫學推論是否成立。
盲區從「整張圖」縮到「描述本身是否忠於圖」——而後者本來就是視覺哨兵的職權。

### 3.2 前提／推論分離（盲區協議）

`figure_desc` 對紅隊是**前提**，不是**真相**：

- 紅隊審「前提→結論」的推論鏈與學科合理性。
- 覺得**前提本身**可疑 → 記 `figure_desc_conflict`，**路由視覺哨兵、永不進 fix 站**。

這樣既不是「假設它對」（推論照審、可疑照報），也不讓文字紅隊越權裁決它看不到的東西。

> ⚠️ **殘餘風險**：`figure_desc` 與詳解同源（同一個模型看同一張圖），描述錯會連詳解
> 一起錯、而異源紅隊核不出來。**視覺哨兵仍是圖面正確性的唯一權威**，`figure_desc`
> 只用於一致性與推論審查。這個分工不得混淆。
> （此節需 pilot：拿真實 fix 率已知的圖題批做 A/B，驗「帶 `figure_desc` 審」是否多抓
> 真錯而不虛增誤報，並確認「描述錯 → 紅隊把對的詳解改去遷就錯描述」確實被圍堵。）

## 4. 回報而非誤報：finding schema 與零 token 分流

### 4.1 schema 加兩個必填欄

```json
{
  "qid": "...", "severity": "...",
  "basis": "content_error | style | input_gap | figure_desc_conflict",
  "evidence_field": "stem|options|ans|table_md|prev|figure_desc",
  "claim": "...", "rationale": "..."
}
```

`content_error` **必填** `evidence_field`，且該欄位必須真的存在於這題的 payload——
一行 Python 就能驗。**引用不存在欄位的 `content_error` 自動降級為 `input_gap`。**
這條規則本身就把「拿『看不到』當『內容錯』」鎖死：**你說內容錯，就得指出跟哪個輸入欄位矛盾。**

### 4.2 確定性分流與指標分帳

| `basis` | 去向 | 計入 |
| --- | --- | --- |
| `content_error` | fix 站佇列 | `fix_rate` 分子候選 |
| `input_gap` | repair queue → 補欄位 → **只重審這些 qid** | `gap_rate`，**不入 fix 率** |
| `figure_desc_conflict` | 視覺哨兵佇列 | 獨立指標 |
| `style` | 低優先佇列 | 不入 fix 率 |

三層防呆（缺一層就會漏）：

1. **fix 站入口的過濾裝在程式碼裡，不在 prompt 裡**——上次的災難是 fix 站照單全收，
   所以濾網要在門口，模型偶爾不守 schema 也漏不進去。
2. **gap-language lint**：對 `content_error` 的 rationale 掃關鍵詞（看不到／未提供／
   為空／無法核對／缺圖／未附），命中即自動降級並記 audit log。
3. **指標定義寫死**：`fix_rate` ＝ fix 站接受的修復數 ÷ **送審題數**；
   `gap_rate` ＝ `input_gap` 數 ÷ 送審題數，**目標恆為 0**——>0 不是品質訊號，
   是管線工程 bug 警報（代表前三層漏了東西），觸發告警而非觸發修復。

## 5. 熔斷器（擋下一個未知化身）

註冊表擋已知模式，熔斷器擋未知模式：**首波批次（如 5 塊）一回來就跑 finding lint**，
`gap_rate` 或降級率異常 → 暫停批次、人看一眼再續（loop 本來就支援 resume-from-cache）。
血量上限從 100% 降到約 2%。近零成本。

## 6. 為什麼這是淨省，不是增加成本

紅隊全批（8,196 則、30 題／塊）實測約 **27M token**；**任何「重審一輪」都是再付一次
同等代價**。所以機制的價值主要在「一次做對、不要重審」：

| 項目 | 沒有機制（實際發生） | 有機制 |
| --- | ---: | ---: |
| 83 題承上題首輪紅隊浪費 | ~0.27M | 0 |
| 重審 3 塊 | ~0.3M | 0 |
| 假 fix 讓好詳解被改壞 → 事後排查 | 人力＋修復成本 | 0 |
| 新增成本：`prev` 進紅隊 payload | — | ~0.04M（全批 **0.15%**）|

圖題那個化身更貴：fix 率 43% vs 真實 18% ⇒ 過半 fix 量是假的，fix 站與裁決的 token
隨假 finding 線性膨脹，等於白付近一倍修復管線成本，還倒賠內容品質。

**預檢值不值得？** 純 Python、秒級、零 token，**抓到一題就回本**。不需實測。

## 7. 已知待辦：`severity` 與 `c` 撞字面值

同一份輸出裡兩個語意相反的欄位共用同一組字面值：

- `severity=high` ＝ **壞消息**（問題嚴重）
- `c=high` ＝ **好消息**（詳解可信）

掃 log 時一堆 `high` 混在一起**極易讀反**。正解是把 `severity` 改成
`blocker|major|minor`，與 `c` 一眼分得開。

**未立即施行的理由**：要動 prompt schema 與已產出的批次輸出格式，跑批中途改會讓新舊
批次不一致。**排在當前批次收斂、且確認不擾動其他流程之後**。新建的管線請直接採用
`blocker|major|minor`。

### 真正的危險不是撞名，是**方向相反**（2026-08-09 使用者指出）

兩個欄位共用 `high|med|low` 已經夠糟，但它們的**極性是反的**：

| | `severity=high` | `c=high` |
| --- | --- | --- |
| 讀到它該做什麼 | 停下來處理 | 放心放行 |
| 讀反的後果 | 把該擋的放行 | 把該放行的擋下 |

同名同值而**同向**的欄位讀錯，只是分不清出處，結論還在同一邊；
同名同值而**反向**的欄位讀錯，會得到**完全顛倒的結論**，而且顛倒得很有說服力
（`high` 很多 → 看起來像「品質很好」或「問題很多」，兩種讀法都自洽）。

實測同一輪的兩組數字擺在一起就是這個形狀：
`severity` high 32／med 33／low 43，`c` high 442／med 43／low 63。

> 命名判準：**極性相反的兩個量表，不可以共用值域。**
> 這比「欄位名要有意義」更硬——名字讀者可能不看，值讀者一定會看。
> 好消息用具名等級（`blocker|major|minor`、`draft|verified`），
> 壞消息用另一組，讓值本身就能自證它屬於哪個量表。

## 物化的 payload 沒進版控，等於沒有物化（2026-08-18 實測）

「先抓下來落成一個檔，兩站讀同一份」是本檔的核心手法。但它有一個沒寫出來的前提：
**那個檔要留得下來。**

實測：法規正本（32 部法、6,989 條，紅隊查證申論法源時比對的那份）從第一天就在
`.gitignore` 的黑洞裡——該 repo 用白名單制，第一行 `*` 全擋，而那個目錄從來沒被加進
白名單。沒有任何東西會報錯，`--build` 照跑、檔案照寫、紅隊照用。

後果是**判決留下來了，證據沒有**：紅隊今天判某則申論「法源錯誤」，
下一次 `--build` 覆蓋之後，沒有人能還原它當時比對的是哪一版條文。
一則被推翻的判定無法複驗，一則可疑的判定也無法平反。

判準：**payload 的 parity 有兩個維度，要分開檢查。**

| 維度 | 問題 | 怎麼驗 |
|---|---|---|
| 同步性 | 兩站讀的是同一份嗎 | 兩站都吃同一個路徑，跑批記錄該檔的 hash 或 commit SHA |
| 可重播性 | 三個月後還原得回來嗎 | `git log -- <path>` 有沒有東西；**空的就是沒有** |

第二個維度最容易漏，因為它在當下完全沒有症狀——**只有在有人回頭質疑一則判定時才會發現，
而那正是最需要它的時刻**。

兩個實作提醒：

- **白名單制的 `.gitignore` 會讓「我 commit 了」靜默落空。** 加檔案之前先跑一次
  `git check-ignore -v <path>`；`git add` 不報錯不代表加進去了（要 `git add -f` 或改白名單）。
- **上游來源可能不留歷史。** 那份法規 dump 每週被官方覆寫、無歷史版本，
  所以「這份 payload 是否忠實於當時的上游」永遠無法重演——除非你自己留一份上游快照。
  同步性靠指向同一個檔就能滿足，可重播性要靠**你自己**存下來。

## 字面比對的查核器：「名字對不上」與「沒有引用」同形（2026-08-18 實測）

第 1 節那五個化身再加一個，而且它是分母端的：**查核器只認得註冊表裡的字面，
資料用了別的寫法時，那筆引用不是 fail，是連被檢查的機會都沒有。**
`--verify` 印「0 fail」，而盲區裡的錯誤數是未知的。

實測（律師科 3,408 則詳解，法條錨定包 `anchor_pack.py --verify`）：

| | 筆數 |
|---|---|
| 註冊表字面看得見的引用 | 6,476 |
| 詳解寫俗名而看不見的 | **1,741**（刑法 1,418／憲法 230／憲法增修條文 93） |

註冊表寫官方全名「中華民國刑法」，詳解寫「刑法」——**21% 的引用整批消失**，
而報表上是滿分。三科合計補完後 7,205 → 9,292（+29%）。

### 四條可推廣的判準

1. **查核器一定要同報分母。** 只報 `fail` 數的閘門無法區分「都對」與「都沒看到」。
   最小可行做法：summary 一起印 `refs`（看得見幾筆）。分母掉下去比 fail 冒出來
   更難察覺，因為它長得像「這批資料很乾淨」。
2. **需求量往被查核的那一層量，不往相鄰的描述層量。** 本輪原本的待辦寫的是
   「清點 ref 層引用了哪些法名」，量了才發現問錯層：ref 是關鍵字層，錨定包查的是
   **詳解**的條號，兩者幾乎不相關——個資法在 ref 層出現 12 次、詳解引用 0 筆；
   特殊境遇家庭扶助條例 ref 層一次沒出現、詳解引用 28 筆。
   補了 ref 層熱門但詳解不引的法，包會變大而那部分永遠不會被查到。
3. **短名字會被長名字冒名，而那比看不見更糟。**
   「陸海空軍刑法第 76 條」被當成「中華民國刑法第 76 條」，會拿去對照**錯的那部法**
   然後印出一個看起來合法的 ok／fail。守衛的資料來源是全量 dump 的反查
   （`endswith(surface) and len > len(surface)`），不是憑印象列舉；而且
   **冒名者身分是逐科的**——全民健康保險法對社工是註冊法規、對律師才是冒名者，
   所以清單列全集、由當科註冊表現場排除。
   「全名與俗名同時命中同一段要去重」與這件事是同一條規則：**短的被長的包住就丟掉**。
4. **補覆蓋率會讓既有解析器的 bug 浮出來。** 補完當下冒出 1 筆 fail：
   「家庭暴力防治法第 58 條、特殊境遇家庭扶助條例及…」的反向配對把 58 掛到後面
   那部條例上。它之前抓不到，不是因為它不存在，而是**那部條例沒註冊，
   連被誤配的機會都沒有**。覆蓋率與正確性不是兩條獨立的軸。

### 守衛沒被否證過，就不知道它在不在工作

兩道守衛各做一次否證（拿掉清單，看錯誤是否重現）：拿掉冒名者清單，
「陸海空軍刑法第 76 條」立刻被掛到中華民國刑法上；拿掉別名表，「刑法第 271 條」
回到 0 筆。**兩次都重現，才算證明它們是承重的。** 反例寫進 `--selftest`
（本輪 +8 條，26/26）。

⚠️ 寫反例時注意：我第一版的反向引用反例是「第 271 條中華民國刑法之規定」，
它 FAIL 了——但攔下它的是**既有的尾字守衛**（法名後接漢字「之」不算引用），
與新規則無關。**反例失敗時先確認是哪道守衛擋的**，否則會去改一條沒壞的規則。

## 六、parity 成立，證不了兩站都拿到了題庫裡有的東西（2026-08-19 實測）

前面五節講的都是**兩站之間**的落差：撰寫者看得到、審查者看不到，於是「我看不到」被
誤報成「內容錯」。三層防禦（註冊表／源頭 lint／parity 斷言）把它壓住了。

這一則是同一個病的**第四個化身**，而且三層防禦對它全部靜默：

> 藥師 wave 3 收尾時清點紅隊的 `input_gap`，最大一類不是缺圖，是
> **64 則「承上題的前一題沒被帶進來」**。往上追一層：
> **生成站的 payload 是 `['ans','exam','options','qid','stem','subject']`**——
> 沒有 `prev`、沒有 `has_figure`、沒有 `table_md`。
> 紅隊 payload 形狀相同，所以 `parity_check` **完美通過**。
>
> 實測規模：266 題字面「承上題」，其中 **256 題的詳解是在看不到前一題的情況下寫的**；
> 另有 20 題有圖、生成時不知道圖存在。

**parity 是相對判準**。它問「兩站看到的一樣嗎」，答案可以是「一樣地少」。
兩站一起瞎的時候，它報的是綠燈——而且是**誠實的**綠燈，因為它本來就只保證對齊。

### 判準：對齊之外，還要有一個**絕對**判準——對題庫

三個問題要分開問，缺一個就會有一種缺陷永遠看不見：

| 問題 | 誰回答 |
| --- | --- |
| 這塊的題還在題庫裡嗎（有沒有被改過） | 輸入漂移檢查（比對題幹／選項文字） |
| 兩站看到的一樣嗎 | `parity_check`（比對落盤後的 payload 指紋） |
| **他們看到的，有題庫裡有的那些嗎** | **物化輸入稽核（回放註冊表）** |

第三個問題必須**對著已經躺在磁碟上的塊回放**，不能只在切塊那一刻跑一次：
真實情況是「那批塊在閘門存在之前就切好了」，而**在閘門之前切的塊，與通過閘門的塊
長得一模一樣**。實作見專案的 `audit_materialized_inputs.py`。

### 兩個實作陷阱（各踩過一次）

1. **推導欄位不能拿題庫列去驗。** `prev` 是從鄰列算出來的，題庫從不存它——把
   `source_lint(bank_row)` 直接回放，會對每一題承上題都亮紅燈，無論 payload 帶了沒。
   要驗的是 **payload**：這一站實際看到的東西裡，有沒有它該有的證據。
2. **稽核要能自證。** 這支尺跑出來的第一個有用訊號，是**唯一有算 `prev` 的切塊器
   （修復站）回報 0**，而沒算的兩站回報 256／173。**一把在應該是 0 的地方報 0 的尺，
   才有資格讓人相信它在別處報的非 0。**
