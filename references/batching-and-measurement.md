# 批次大小與 token 量測方法

> 本檔補 ADR-0005 七槓桿沒涵蓋的**第八槓桿**，並訂下量測紀律。
> 七槓桿講的是「prompt 裡放什麼」，這裡講的是「一次呼叫跑幾輪、一批放幾題」——
> 實測後者的影響**比前者大一個量級**。

## 1. 第八槓桿：消除工具往返（最大單一槓桿）

### 實測數字（doctor 圖題站，2026-07-30）

| 版本 | 工具往返 | 中位 token／題 | 394 題預估 |
| --- | ---: | ---: | ---: |
| v1：模型 Read 輸入檔 → 寫輸出檔 → 自驗 | **7 次 exec** | **26,370** | 10.4M |
| v2：題目內嵌 prompt ＋ `--output-schema` 收結構化回覆 | **0 次** | **9,130** | 3.6M |

**降為 1/2.9。** 同一個模型、同一個 effort、同樣的圖。

### 原理

每一次工具往返，**整個累積 context 會被重新送一次**。圖題站的 context 含圖片
（單張約 1–2.5k token），所以每一輪往返的單價比純文字站更高——同一個錯在圖題被放大。

七槓桿的槓桿 1／2 已經說了「別叫模型去 Read 操作卡與金樣」，但那只涵蓋**靜態素材**。
**逐題的輸入與輸出檔案 I/O 同樣是往返**，而且它們藏在「腳本把檔名寫進 prompt」這個
看起來很正常的做法裡。規則要擴大成一句話：

> **模型不該碰檔案系統。輸入內嵌進 prompt，輸出用 `--output-schema` ＋ `-o` 直接收。**

### 三個附帶收益（與成本無關，但都是真的）

1. **`--sandbox read-only` 成為可能**。模型不需寫檔，就不必給寫入權限。
   實測遇過一個代理在 `workspace-write` 下去 `apply_patch` 改**另一批**的輸出檔——
   資料沒壞，但那是不該發生的。拿掉寫入權限即根除。
2. **字面 `\n` 序列化 bug 消失**。模型手寫 JSON 進檔案時，會把換行寫成字面的
   反斜線加 n（實測 8,227 則中 93 則如此），下游 lint 看到「只有一段」判 fail。
   改用 structured output 後 JSON 由 API 層產生，此類 bug 不再可能。
   ⚠️ 這個 bug 危險在**它偽裝成內容缺陷**：lint 摘要報「段落不足」，若不把字串
   `repr` 出來看，結論會是「模型寫壞了、重生」——白花 93 題的錢重寫本來正確的內容。
3. **輸出契約由 API 強制**，不必在 prompt 裡反覆叮嚀「四個欄位一個都不能少」。

### `--output-schema` 的坑（會被 400 拒絕）

OpenAI structured outputs 要求 `required` **列出 `properties` 的每一個 key**，
巢狀物件亦同。**沒有選填欄位**。想要「可有可無」的欄位，寫成可為 null 並列入 `required`：

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["qid", "ans", "t", "c", "data_defect"],
  "properties": {
    "qid": {"type": "string"},
    "c": {"type": "string", "enum": ["high", "med", "low"]},
    "data_defect": {
      "type": ["object", "null"],
      "additionalProperties": false,
      "required": ["kind", "detail"],
      "properties": {"kind": {"type": "string"}, "detail": {"type": "string"}}
    }
  }
}
```

並在 prompt 明講「沒有缺陷時 `data_defect` 填 null」。**先用 1 題實測 schema 過不過**——
這個 400 若沒先擋下，會在整批的每一次呼叫上重複發生。

### 往返砍完之後：天花板變成「呼叫次數」（視覺哨兵站實測，2026-07-30）

同一條產線後來又出現 **27,000 token／題**的站別（視覺哨兵，一題一呼叫、零往返）。
三個直覺假設**依序被實測否證**：

| 假設 | 實測 |
| --- | --- |
| 貴在 reasoning effort | `low` 與 `medium` 都是 27k／題 |
| 貴在圖片 | 同一題**不附圖**仍是 26,782 token |
| **貴在每次呼叫的固定開銷** | ✅ `codex exec` 每次送約 26k 系統 prompt；自家內容僅佔 2.5k、圖約 400 |

一題一呼叫時 **96% 的錢與要審的內容無關**。改 6 題／批 → **5,672／題（省 4.8 倍）**，
399 題從 10.8M 壓到約 2.3M。

**所以第八槓桿有兩段，別只做前半**：先砍工具往返（省的是「重送 context」），
再砍呼叫次數（省的是「重送系統 prompt」）。後者對**任何**外部 CLI 站別都成立，
且與 effort、圖片、prompt 長度都無關——那三個是最容易先去調的，也是最沒用的。

⚠️ 這條與 §2 的兩個上限**直接衝突**：批次省錢，但錯配風險與重試波及都變大。
衝突的解法不是選一邊，是**把錯配變成可偵測**（見 §2「若真的必須批次又要可偵測」）。

## 2. 一批放幾題：先算，再用兩個上限封頂

### 算式

設 `P`＝恆定前綴 token（操作卡＋金樣＋素材包）、`d`＝每題變動尾 token、`N`＝批次題數：

```
每題成本 ≈ P/N + d + （推理與輸出）
```

前綴分攤是**雙曲線**：`N` 加倍只讓前綴份額減半，很快就不值得再加。實務判準：

> **取 `N` 使 `N·d ≈ 4P`**（此時前綴只佔變動成本的兩成，再加 `N` 邊際收益極小）。

以 `P ≈ 5.5k` 為例：

| 站 | 每題變動尾 `d` | 算出的 `N` | 實務採用 | 說明 |
| --- | ---: | ---: | ---: | --- |
| 文字生成 | ~1k | 17–28 | **20** | 與既有選擇一致 |
| 紅隊（含詳解全文） | ~2k | 8–14 | **30** | 已遠過前綴影響點；30 是為別的理由選的（見下） |
| 圖題 | ~2.5k（含圖） | 7–11 | **1** | 被上限 B 否決，見下 |

### 上限 A：重試波及範圍

一塊失敗＝那一塊**整批**重跑。`N=30` 的塊掛掉要重付 30 題。批次越大，
單次失敗越貴，而失敗率不會因為批次大就下降。

### 上限 B：逐題錯配是否可偵測（🔴 硬上限）

**若「模型把第 3 題的素材寫進第 5 題」這件事沒有零 token 關卡抓得到，`N` 必須是 1。**

圖題就是這種情形。錯配後的產物是：

- 結構 lint → **通過**（三段式格式完好）
- 答案錨 → **通過**（答案字母照抄官方）
- 文字紅隊 → **不會報**（紅隊 prompt 明文禁止提圖類 finding，
  因為文字紅隊對圖題硬答曾造成 fix 率虛高一倍）

也就是一則格式合規、答案正確、但圖像描述張冠李戴的詳解，直接上線給考生。
所以 explanations-redteam.md §6 那條「圖題每 12 題一檔」**不適用於一題一圖的科目**：
量算出 7–11，上限 B 直接把它壓到 1。

代價只是前綴重複稅（394 題約 2.17M token，吃 prefix cache 後折半），
**而且消除往返省下的 6.8M 遠大於它**——兩件事別混為一談：
往返要砍，批次大小另外算。

### 若真的必須批次又要可偵測

把題號燒印在圖檔白邊上（擴 canvas、不覆蓋影像內容），批次送 N 張，
要求每則詳解回報「圖角編號」，零 token lint 驗回報編號＝題號。
錨點來自圖像本身，錯配即被抓。**四千題以上量級才值得建置**；
幾百題規模投報率為負（省的錢少於建置＋重跑實測的成本）。

#### 便宜版：`fig_gist` 自檢欄（幾百題規模就划算，2026-07-30 實測）

schema 強制每題回一個 **`fig_gist`＝「用 ≤20 字說出你在該題那張圖上看到什麼」**，
prompt 明文要求「誠實寫你看到的，**不要從題幹反推**」。零建置成本（多一個欄位），
而且**它立刻抓到一次真的漏送**：

`while IFS= read -r line` 在**檔尾無換行**時會丟掉最後一行 → 6 張圖只送出 5 張，
第 6 題被判「圖無法辨識」。模型回的 `fig_gist` 是「未附第 6 張圖」，**一眼可見**。
修法：`|| [ -n "$line" ]` ＋ 加一道「圖數必須等於題數，否則跳過該批」的前置閘。

> **沒有那個欄位，這個靜默漏送會被誤讀成「圖真的壞了」**——而那正是會被歸類成
> 「源圖品質上限、不可修」然後永久放過的失效模式。

對位驗證方式：拿**自己親眼看過**的 N 張圖刻意打亂順序送，比對 gist 與實物。
（實測 6 張中 5 個完全吻合，第 6 個就是上面那個漏送。）

**誠實講它的射程**：`fig_gist` 抓得到「沒收到圖」與「圖與題明顯不符」，
抓不到「兩張長得很像的圖互換」——那仍需燒印題號。先上便宜版，
量級到四千題再加燒印。

## 3. 量測紀律（🔴 三次判斷錯誤換來的）

`codex exec` 的 log **只報總 token，不報 cached／reasoning／輸出的拆解**。
沒有拆解就只能「改一個變數、量足夠樣本」，於是很容易錯：

| 依據 | 結論 | 對錯 |
| --- | --- | --- |
| 從 prompt 大小（5.5k）推算 | 「浪費只有 1–3 美元，不值得改」 | ❌ 真實是 26k／題 |
| 從 `exec` 次數（7 次）推算 | 「往返是主成本」 | ✅ 但當時無法證明 |
| 從 3 個樣本量 | 「v2 沒效，中位 27,989 ≈ v1 26,370」 | ❌ 抽到兩個高推理離群值 |
| 從 15 個樣本量 | 「v2 中位 9,130，降為 1/2.9」 | ✅ |

規則：

1. **不要從 prompt 大小推總成本。** 量總量。推理與往返都不在 prompt 裡。
2. **一次只改一個變數。** 同時改批次大小與往返，兩者的貢獻分不開。
3. **`n ≥ 12–15`，用中位數不用平均。** 分佈右偏（同一批三題實測
   7.7k／28k／28k，離散 3.6 倍）——推理量的變異會直接偽裝成結論。
4. **前置實測不可省。** 今天有兩個錯誤是靠 1 塊前置實測擋下的：
   schema 被 400 拒絕、以及送分題誤入生成。兩者都會在整批上重複數百次。
5. **改批次大小或換模型層級時，摻毒批紅隊召回率必重跑**（ADR-0005 槓桿 4 的配套）
   ——否則省下的 token 可能是拿偵測率換的而不自知。

## 4. 一頁總結

```
優先序（實測的效果排序，不是直覺排序）：
  1. 砍掉工具往返           → 2.9×   ← 最大，且順帶拿到 read-only 與 schema 保證
  2. 恆定前綴吃 prefix cache → ~2×    （ADR-0005 槓桿 1）
  3. 批次大小 N ≥ 4P/d      → ~1.2×  （邊際，且有兩個上限封頂）
  4. 降 effort              → 未測，醫學影像判讀有品質風險，須 A/B 才動

硬規則：
  🔴 逐題錯配若不可偵測 → N=1，不管算式算出多少
  🔴 模型不碰檔案系統：輸入內嵌、輸出走 --output-schema、沙箱 read-only
  🔴 n<12 的量測不足以推翻既有設計
```

## 5. 併發上限固定時，pipeline **不會**增加吞吐量（2026-08-01 實戰，一次判斷錯誤換來的）

夜跑跑完一科後我把「階段之間全是 barrier」列為最大損失——**那是錯的**，而且錯得有結構。

實測：生成 83 塊、紅隊 56 塊、修復 8 塊，合計 **147 塊**，在 `PAR=5` 下共 **148 分鐘**
（≈ 29.4 波 × 5 分鐘/波）。

- **barrier 的真實代價只有「排空尾巴」**：每站結尾剩不足 PAR 塊、跑不滿的那段。
  兩次轉場合計約 **10 分鐘**。
- **總牆鐘時間 ≈ 總塊數 × 每塊時間 ÷ PAR，與排序無關。** 147 塊要跑完就是要跑完；
  pipeline 讓第 1 塊提早進下一站，但併發槽位就那 5 個，省不出第 6 個槽。
- **真正的旋鈕是 PAR。** 同樣 147 塊在 `PAR=10` 是 14.7 波 ≈ **74 分鐘**，2 倍。
  `codex exec` 是網路／API 受限不是 CPU 受限，把 `PAR` 寫死成 5 等於白白排隊。

> pipeline 的價值在**降低單一項目的端到端延遲**（第一則詳解多快可用），
> 不在提高**總吞吐**。夜跑要的是後者。兩者常被混為一談。

### 比這兩者都大的，是「隊列裡沒東西可跑」

同一夜真正的天花板不是排程也不是併發，是**下一科的前置沒就緒**：
兩個待做科目的操作卡與金樣不存在，硬前置沒過就開不了工。
就算 `PAR` 開到 20、pipeline 排到完美，那一夜可跑的池子也只有已就緒那一科。

**排程規則**：模型配額吃緊時（批次在跑），把**不吃配額的前置工作**（下一科的操作卡、
金樣、零 token 掃描器）排進同一段時間。前置是**序列相依**的——它不就緒，後面再快也沒用。

## 6. 無人值守：本機排程撐不過闔蓋

`/loop` 這類**本機**排程隨機器睡眠而停。`caffeinate -dimsu` 擋得住閒置睡眠，
**擋不住闔蓋**。實測夜跑在 04:06 停止、閒置 6.5 小時才被發現。

- 任務可能跨闔蓋或關機 → 用**雲端** routine（`/schedule`），不要用本機 loop。
- 看門狗判死看的是**輸出檔 mtime ＋ CPU 累計**，不是行程是否存在：闔蓋後換網路介面會讓
  in-flight 的 `codex exec` socket 變殭屍，而它**沒有網路 idle timeout**，會永久卡住，
  `pgrep` 看起來完全正常。
- 但看門狗自己也是本機行程——**它擋得住卡死，擋不住睡著**。這兩件事要分開解。

## 7. 中間檔名與備份檔名：撞名會靜默毀掉別人的回溯點

同一個坑在這個專案踩了兩次，第二次是在已經寫進 CLAUDE.md 之後。

- **備份檔**：`bank.json.bak_<用途>` 這種名字會撞——第二次 `--write` 直接蓋掉前一輪的
  回溯點。**工具層強制**：撞名就換一個（`_2`／`_3`），換不到就中止，不要靠人記得。
- **中間檔**：把 `_rt_all.json`／`<exam>_FINAL.json` 這類名字**寫死**在切塊器裡，
  跑第二科時就會覆蓋掉第一科的紅隊紀錄。路徑一律可傳入，預設值只是方便。

兩者都是「靜默毀損」——不報錯、不影響當次執行，只有回頭想 rollback 時才發現東西沒了。
