## 1. 第八槓桿：消除工具往返（最大單一槓桿）

### 實測數字（doctor 圖題站，2026-07-30）

| 版本 | 工具往返 | 中位 token／題 | 394 題預估 |
| --- | ---: | ---: | ---: |
| v1：模型 Read 輸入檔 → 寫輸出檔 → 自驗 | **7 次 exec** | **26,370** | 10.4M |
| v2：題目內嵌 prompt ＋ `--output-schema` 收結構化回覆 | **0 次** | **9,130** | 3.6M |

**降為 1/2.9。** 同一個模型、同一個 effort、同樣的圖。

### 原理

每一次工具往返，**整個累積 context 會被重新送一次**。圖題站的 context 含圖片
（單張約 1–2.5k token），所以每一輪往返的單價比純文字站更高——同一個錯在圖題被放大。

七槓桿的槓桿 1／2 已經說了「別叫模型去 Read 操作卡與金樣」，但那只涵蓋**靜態素材**。
**逐題的輸入與輸出檔案 I/O 同樣是往返**，而且它們藏在「腳本把檔名寫進 prompt」這個
看起來很正常的做法裡。規則要擴大成一句話：

> **模型不該碰檔案系統。輸入內嵌進 prompt，輸出用 `--output-schema` ＋ `-o` 直接收。**

### 三個附帶收益（與成本無關，但都是真的）

1. **`--sandbox read-only` 成為可能**。模型不需寫檔，就不必給寫入權限。
   實測遇過一個代理在 `workspace-write` 下去 `apply_patch` 改**另一批**的輸出檔——
   資料沒壞，但那是不該發生的。拿掉寫入權限即根除。
2. **字面 `\n` 序列化 bug 消失**。模型手寫 JSON 進檔案時，會把換行寫成字面的
   反斜線加 n（實測 8,227 則中 93 則如此），下游 lint 看到「只有一段」判 fail。
   改用 structured output 後 JSON 由 API 層產生，此類 bug 不再可能。
   ⚠️ 這個 bug 危險在**它偽裝成內容缺陷**：lint 摘要報「段落不足」，若不把字串
   `repr` 出來看，結論會是「模型寫壞了、重生」——白花 93 題的錢重寫本來正確的內容。
3. **輸出契約由 API 強制**，不必在 prompt 裡反覆叮嚀「四個欄位一個都不能少」。

### `--output-schema` 的坑（會被 400 拒絕）

OpenAI structured outputs 要求 `required` **列出 `properties` 的每一個 key**，
巢狀物件亦同。**沒有選填欄位**。想要「可有可無」的欄位，寫成可為 null 並列入 `required`：

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["qid", "ans", "t", "c", "data_defect"],
  "properties": {
    "qid": {"type": "string"},
    "c": {"type": "string", "enum": ["high", "med", "low"]},
    "data_defect": {
      "type": ["object", "null"],
      "additionalProperties": false,
      "required": ["kind", "detail"],
      "properties": {"kind": {"type": "string"}, "detail": {"type": "string"}}
    }
  }
}
```

並在 prompt 明講「沒有缺陷時 `data_defect` 填 null」。**先用 1 題實測 schema 過不過**——
這個 400 若沒先擋下，會在整批的每一次呼叫上重複發生。

### 往返砍完之後：天花板變成「呼叫次數」（視覺哨兵站實測，2026-07-30）

同一條產線後來又出現 **27,000 token／題**的站別（視覺哨兵，一題一呼叫、零往返）。
三個直覺假設**依序被實測否證**：

| 假設 | 實測 |
| --- | --- |
| 貴在 reasoning effort | `low` 與 `medium` 都是 27k／題 |
| 貴在圖片 | 同一題**不附圖**仍是 26,782 token |
| **貴在每次呼叫的固定開銷** | ✅ `codex exec` 每次送約 26k 系統 prompt；自家內容僅佔 2.5k、圖約 400 |

一題一呼叫時 **96% 的錢與要審的內容無關**。改 6 題／批 → **5,672／題（省 4.8 倍）**，
399 題從 10.8M 壓到約 2.3M。

**所以第八槓桿有兩段，別只做前半**：先砍工具往返（省的是「重送 context」），
再砍呼叫次數（省的是「重送系統 prompt」）。後者對**任何**外部 CLI 站別都成立，
且與 effort、圖片、prompt 長度都無關——那三個是最容易先去調的，也是最沒用的。

⚠️ 這條與 §2 的兩個上限**直接衝突**：批次省錢，但錯配風險與重試波及都變大。
衝突的解法不是選一邊，是**把錯配變成可偵測**（見 §2「若真的必須批次又要可偵測」）。

## 2. 一批放幾題：先算，再用兩個上限封頂

### 算式

設 `P`＝恆定前綴 token（操作卡＋金樣＋素材包）、`d`＝每題變動尾 token、`N`＝批次題數：

```
每題成本 ≈ P/N + d + （推理與輸出）
```

前綴分攤是**雙曲線**：`N` 加倍只讓前綴份額減半，很快就不值得再加。實務判準：

> **取 `N` 使 `N·d ≈ 4P`**（此時前綴只佔變動成本的兩成，再加 `N` 邊際收益極小）。

以 `P ≈ 5.5k` 為例：

| 站 | 每題變動尾 `d` | 算出的 `N` | 實務採用 | 說明 |
| --- | ---: | ---: | ---: | --- |
| 文字生成 | ~1k | 17–28 | **20** | 與既有選擇一致 |
| 紅隊（含詳解全文） | ~2k | 8–14 | **30** | 已遠過前綴影響點；30 是為別的理由選的（見下） |
| 圖題 | ~2.5k（含圖） | 7–11 | **1** | 被上限 B 否決，見下 |

### 上限 A：重試波及範圍

一塊失敗＝那一塊**整批**重跑。`N=30` 的塊掛掉要重付 30 題。批次越大，
單次失敗越貴，而失敗率不會因為批次大就下降。

### 上限 B：逐題錯配是否可偵測（🔴 硬上限）

**若「模型把第 3 題的素材寫進第 5 題」這件事沒有零 token 關卡抓得到，`N` 必須是 1。**

圖題就是這種情形。錯配後的產物是：

- 結構 lint → **通過**（三段式格式完好）
- 答案錨 → **通過**（答案字母照抄官方）
- 文字紅隊 → **不會報**（紅隊 prompt 明文禁止提圖類 finding，
  因為文字紅隊對圖題硬答曾造成 fix 率虛高一倍）

也就是一則格式合規、答案正確、但圖像描述張冠李戴的詳解，直接上線給考生。
所以 explanations-redteam.md §6 那條「圖題每 12 題一檔」**不適用於一題一圖的科目**：
量算出 7–11，上限 B 直接把它壓到 1。

代價只是前綴重複稅（394 題約 2.17M token，吃 prefix cache 後折半），
**而且消除往返省下的 6.8M 遠大於它**——兩件事別混為一談：
往返要砍，批次大小另外算。

### 若真的必須批次又要可偵測

把題號燒印在圖檔白邊上（擴 canvas、不覆蓋影像內容），批次送 N 張，
要求每則詳解回報「圖角編號」，零 token lint 驗回報編號＝題號。
錨點來自圖像本身，錯配即被抓。**四千題以上量級才值得建置**；
幾百題規模投報率為負（省的錢少於建置＋重跑實測的成本）。

#### 便宜版：`fig_gist` 自檢欄（幾百題規模就划算，2026-07-30 實測）

schema 強制每題回一個 **`fig_gist`＝「用 ≤20 字說出你在該題那張圖上看到什麼」**，
prompt 明文要求「誠實寫你看到的，**不要從題幹反推**」。零建置成本（多一個欄位），
而且**它立刻抓到一次真的漏送**：

`while IFS= read -r line` 在**檔尾無換行**時會丟掉最後一行 → 6 張圖只送出 5 張，
第 6 題被判「圖無法辨識」。模型回的 `fig_gist` 是「未附第 6 張圖」，**一眼可見**。
修法：`|| [ -n "$line" ]` ＋ 加一道「圖數必須等於題數，否則跳過該批」的前置閘。

> **沒有那個欄位，這個靜默漏送會被誤讀成「圖真的壞了」**——而那正是會被歸類成
> 「源圖品質上限、不可修」然後永久放過的失效模式。

對位驗證方式：拿**自己親眼看過**的 N 張圖刻意打亂順序送，比對 gist 與實物。
（實測 6 張中 5 個完全吻合，第 6 個就是上面那個漏送。）

**誠實講它的射程**：`fig_gist` 抓得到「沒收到圖」與「圖與題明顯不符」，
抓不到「兩張長得很像的圖互換」——那仍需燒印題號。先上便宜版，
量級到四千題再加燒印。

## 3. 量測紀律（🔴 三次判斷錯誤換來的）

`codex exec` 的 log **只報總 token，不報 cached／reasoning／輸出的拆解**。
沒有拆解就只能「改一個變數、量足夠樣本」，於是很容易錯：

| 依據 | 結論 | 對錯 |
| --- | --- | --- |
| 從 prompt 大小（5.5k）推算 | 「浪費只有 1–3 美元，不值得改」 | ❌ 真實是 26k／題 |
| 從 `exec` 次數（7 次）推算 | 「往返是主成本」 | ✅ 但當時無法證明 |
| 從 3 個樣本量 | 「v2 沒效，中位 27,989 ≈ v1 26,370」 | ❌ 抽到兩個高推理離群值 |
| 從 15 個樣本量 | 「v2 中位 9,130，降為 1/2.9」 | ✅ |

規則：

1. **不要從 prompt 大小推總成本。** 量總量。推理與往返都不在 prompt 裡。
2. **一次只改一個變數。** 同時改批次大小與往返，兩者的貢獻分不開。
3. **`n ≥ 12–15`，用中位數不用平均。** 分佈右偏（同一批三題實測
   7.7k／28k／28k，離散 3.6 倍）——推理量的變異會直接偽裝成結論。
4. **前置實測不可省。** 今天有兩個錯誤是靠 1 塊前置實測擋下的：
   schema 被 400 拒絕、以及送分題誤入生成。兩者都會在整批上重複數百次。
5. **改批次大小或換模型層級時，摻毒批紅隊召回率必重跑**（ADR-0005 槓桿 4 的配套）
   ——否則省下的 token 可能是拿偵測率換的而不自知。

## 4. 一頁總結

```
優先序（實測的效果排序，不是直覺排序）：
  1. 砍掉工具往返           → 2.9×   ← 最大，且順帶拿到 read-only 與 schema 保證
  2. 恆定前綴吃 prefix cache → ~2×    （ADR-0005 槓桿 1）
  3. 批次大小 N ≥ 4P/d      → ~1.2×  （邊際，且有兩個上限封頂）
  4. 降 effort              → 未測，醫學影像判讀有品質風險，須 A/B 才動

硬規則：
  🔴 逐題錯配若不可偵測 → N=1，不管算式算出多少
  🔴 模型不碰檔案系統：輸入內嵌、輸出走 --output-schema、沙箱 read-only
  🔴 n<12 的量測不足以推翻既有設計
```

## 5. 併發上限固定時，pipeline **不會**增加吞吐量（2026-08-01 實戰，一次判斷錯誤換來的）

夜跑跑完一科後我把「階段之間全是 barrier」列為最大損失——**那是錯的**，而且錯得有結構。

實測：生成 83 塊、紅隊 56 塊、修復 8 塊，合計 **147 塊**，在 `PAR=5` 下共 **148 分鐘**
（≈ 29.4 波 × 5 分鐘/波）。

- **barrier 的真實代價只有「排空尾巴」**：每站結尾剩不足 PAR 塊、跑不滿的那段。
  兩次轉場合計約 **10 分鐘**。
- **總牆鐘時間 ≈ 總塊數 × 每塊時間 ÷ PAR，與排序無關。** 147 塊要跑完就是要跑完；
  pipeline 讓第 1 塊提早進下一站，但併發槽位就那 5 個，省不出第 6 個槽。
- **真正的旋鈕是 PAR。** 同樣 147 塊在 `PAR=10` 是 14.7 波 ≈ **74 分鐘**，2 倍。
  `codex exec` 是網路／API 受限不是 CPU 受限，把 `PAR` 寫死成 5 等於白白排隊。

> pipeline 的價值在**降低單一項目的端到端延遲**（第一則詳解多快可用），
> 不在提高**總吞吐**。夜跑要的是後者。兩者常被混為一談。

### 比這兩者都大的，是「隊列裡沒東西可跑」

同一夜真正的天花板不是排程也不是併發，是**下一科的前置沒就緒**：
兩個待做科目的操作卡與金樣不存在，硬前置沒過就開不了工。
就算 `PAR` 開到 20、pipeline 排到完美，那一夜可跑的池子也只有已就緒那一科。

**排程規則**：模型配額吃緊時（批次在跑），把**不吃配額的前置工作**（下一科的操作卡、
金樣、零 token 掃描器）排進同一段時間。前置是**序列相依**的——它不就緒，後面再快也沒用。

## 6. 無人值守：本機排程撐不過闔蓋

`/loop` 這類**本機**排程隨機器睡眠而停。`caffeinate -dimsu` 擋得住閒置睡眠，
**擋不住闔蓋**。實測夜跑在 04:06 停止、閒置 6.5 小時才被發現。

- 任務可能跨闔蓋或關機 → 用**雲端** routine（`/schedule`），不要用本機 loop。
- 看門狗判死看的是**輸出檔 mtime ＋ CPU 累計**，不是行程是否存在：闔蓋後換網路介面會讓
  in-flight 的 `codex exec` socket 變殭屍，而它**沒有網路 idle timeout**，會永久卡住，
  `pgrep` 看起來完全正常。
- 但看門狗自己也是本機行程——**它擋得住卡死，擋不住睡著**。這兩件事要分開解。

## 7. 中間檔名與備份檔名：撞名會靜默毀掉別人的回溯點

同一個坑在這個專案踩了兩次，第二次是在已經寫進 CLAUDE.md 之後。

- **備份檔**：`bank.json.bak_<用途>` 這種名字會撞——第二次 `--write` 直接蓋掉前一輪的
  回溯點。**工具層強制**：撞名就換一個（`_2`／`_3`），換不到就中止，不要靠人記得。
- **中間檔**：把 `_rt_all.json`／`<exam>_FINAL.json` 這類名字**寫死**在切塊器裡，
  跑第二科時就會覆蓋掉第一科的紅隊紀錄。路徑一律可傳入，預設值只是方便。

兩者都是「靜默毀損」——不報錯、不影響當次執行，只有回頭想 rollback 時才發現東西沒了。

## 8. 批次式併發的隱藏損失：每批都被最慢的那塊拖住（2026-08-01 實測）

`PAR` 那個旋鈕最常見的寫法是「每 PAR 個 `wait` 一次」：

```zsh
for i in $(seq 1 $N); do
  codex exec ... &
  if [ $((i % PAR)) -eq 0 ]; then wait; fi   # ← 等整批
done
```

`wait` 等的是**整批全部回來**，不是「空出一個位子就補一個」。於是每一批都被該批最慢的
那塊拖住，先完成的槽位就這樣空等。

### 損失有多大：三次真實跑批，21–26%

從 `*_out_p*.json` 的 mtime 還原批次結構，算「槽位閒置秒數 ÷ 總槽位秒數」：

| 跑批 | PAR | 塊數 | 每批最快→最慢落差（中位） | **槽位閒置佔比** |
| --- | ---: | ---: | ---: | ---: |
| 生成 | 5 | 83 | 82s | **26%** |
| 紅隊 | 5 | 56 | 98s | **21%** |
| 重構 | 10 | 56 | 78s | **26%** |

每批本身約 250 秒，落差 80–100 秒——**調高 `PAR` 不會讓這個比例變好**（第三列 PAR=10
仍是 26%），因為它是批內變異造成的，與批寬無關。塊數越多累積越多：229 塊的科目等於
白丟四分之一時間。

> 這與「站與站之間的 barrier」是同一個病的兩種尺度：站間我加了大排空，批間 shell 又加了
> 小排空。兩處都是**等全部**而不是**等一個**。差別在站間的 barrier 只發生 2 次（約 10 分鐘），
> 批間的發生 N/PAR 次。

### 正確寫法：滾動補位。但 zsh 有兩個坑

```zsh
pids=()
for i in $(seq 1 $N); do
  while (( ${#pids} >= PAR )); do
    alive=(); for _p in $pids; do kill -0 $_p 2>/dev/null && alive+=($_p); done
    pids=($alive); (( ${#pids} >= PAR )) && sleep 0.5
  done
  codex exec ... &
  pids+=($!)
done
wait
```

1. **zsh 5.9 沒有 `wait -n`**（實測 `exit 127`）。那是 bash 4.3+ 的功能，照抄 bash 寫法會靜默失效。
2. 🔴 **不可用 `while (( $(jobs -rp | wc -l) >= PAR ))`。** 命令替換開的是**子 shell**，
   子 shell 的 job table 是空的 → 計數永遠 0 → 閘門形同不存在。
   實測這版把 229 塊**一次全丟出去**，瞬間 84 個 codex 行程。
   只能自己記 PID、再用 `kill -0` 篩活著的。

### 🔴 最重要的一條：這種閘門壞掉是**朝著看起來成功的方向**壞

併發上限失效不會報錯，它讓程式**跑得更快**——看起來就像優化生效了，直到行程數炸開、
撞速率限制或記憶體才發現。所以它必須有自檢，而且**自檢要量對東西**：

| 判定式 | 能不能分辨 |
| --- | --- |
| 看**完成順序**是否交錯 | ❌ 全部同時跑也會交錯。實測用這條誤判過一次，放行了完全沒有上限的版本 |
| 量**最大同時數** | ✅ 舊批次式 3／子 shell 版 **9**／PID 追蹤版 3（PAR=3） |

新寫的判定式要先在 **known-good 與 known-bad 兩種狀態各跑一次**，確認它不會恆真。
`run_stage.sh --selftest` 就是這件事：起 9 個假工作、記 S/E 事件、算最大同時數，超過 `PAR` 就非零退出。

## 9. 跑批進行中讀產出檔：旁觀者必須容忍半截檔（2026-08-01）

跑批期間想提早驗格式（見 `explanations-redteam.md` §12），就得掃 `*_out_p*.json`——
會撞上**正在落盤的那一兩個檔**，`json.load` 丟 `Invalid control character`。

同一批檔案，讀取者的時序不同、安全性就不同：

| 讀取者 | 何時讀 | 會不會撞半截檔 |
| --- | --- | --- |
| `run_stage.sh` 的冪等判斷 | 啟動第 i 塊**之前**讀第 i 塊 | ❌ 不會——那時沒人在寫它 |
| 預檢／彙整／統計腳本 | 全場都在寫時掃**全部**檔案 | ✅ 一定會 |

所以旁觀型腳本一律 `try/except: continue`，**不要**因為一個半截檔就整個崩掉：

```python
try:
    recs = json.loads(p.read_text("utf-8"))
except Exception:
    skipped += 1; continue   # 正在落盤，下次再讀
```

並且**把 skipped 數印出來**——靜默跳過會讓「掃到 300 則」看起來像「總共只有 300 則」。

## 10. 🔴 有效 ≠ 完整：兩層閘門都不看題數，短塊會靜默蒸發（2026-08-01 實戰）

clinical 生成收斂，看門狗判定 **229/229 檔全到**、`run_stage.sh` 的冪等判準也全部通過。
但實際題數是 **4,566/4,576——少了 10 則**：

```
題數不足的塊: [('cl1_out_p227.json', '10/20')]
```

模型寫到一半就收尾，回了 10 題的**合法 JSON 陣列**。於是：

| 閘門 | 判準 | 對短塊的反應 |
| --- | --- | --- |
| `run_stage.sh` 冪等 | 輸出檔 `json.load` 成功 | ✅ 通過 → 重跑時**靜默跳過** |
| `watchdog.sh` 收斂 | 輸出**檔案數** ≥ N | ✅ 通過 → 判定跑完、退出 |

兩層都對，兩層都不看題數，所以 10 則無聲消失。**「JSON 有效」是格式判準，
「題數等於輸入」才是完整性判準**——§7 的教訓（冪等判準是 JSON 有效不是檔案非空）
只解決了半截檔，沒解決半截**內容**。

### 收斂後一定要跑的完整性對帳

```python
for p in sorted(glob.glob(f"{prefix}_out_p*.json")):
    try: out = json.loads(open(p, encoding="utf-8").read())
    except Exception: bad.append(p); continue          # §9：半截檔要跳過不要炸
    inp = json.loads(open(p.replace("_out_", "_in_"), encoding="utf-8").read())
    if len(out) != len(inp): short.append((p, f"{len(out)}/{len(inp)}"))
    qids += [x["qid"] for x in out]
# 三個都要驗：總數、unique qid（抓重複）、逐塊題數（抓短塊）
```

修法：**把短塊的輸出檔移開**（`mv` 不是 `rm`，留備查、撞名要換號），
再用原本的 `run_stage.sh <stage> <prefix> <N>` 重下——冪等判準會讓另外 228 塊直接
`continue`，只補那一塊，零額外成本。**不要另寫一支「只跑第 227 塊」的腳本**：
那要多維護一份「哪些該跑」的判準，兩份判準遲早分岔。

補完的驗收條件要寫成「JSON 有效**且題數等於輸入**」——只驗 JSON 有效正是這次破洞的成因。
而且要驗**全科 qid 集合**不是只驗補的那一塊：只驗自己剛動過的地方會漏掉「修 A 碰壞了 B」，
順帶還能證明另外 228 塊沒有同類短塊——這個結論用只驗一塊換不到。

> **這一條還有第三代**：題數對了也可能整塊是**別人的輸出**（前綴撞號）。
> 判準最終要問身分不是形狀——見 §24。

## 11. 收工停跑批：`pkill` 的作用域是整台機器（2026-08-02）

使用者叫停跑批，我用三條 `pkill` 收工，事後才被提醒「其他 session 也在跑 codex 驗證」：

| 指令 | 作用域 | 評估 |
| --- | --- | --- |
| `pkill -f "codex exec.*cl1_out_p"` | 綁自己的塊名 | ✅ 安全 |
| `pkill -f "watchdog.sh redteam rt_"` | 所有 `rt_` 前綴的紅隊 | ⚠️ 別人用同前綴就會中 |
| `pkill -x caffeinate` | **整台機器上每一個** | 🔴 一定誤傷 |

- 樣式必須綁到**本次跑批獨有的字串**（自己的 prefix／輸出檔名）。stage 名、工具名是共用詞，不能當樣式。
- **沒有獨有字串可綁的共用工具（`caffeinate`、`ssh`、`node`）就不要用 `pkill`**——
  啟動時記下 PID（`nohup … & echo $!`），收工 `kill` 那個 PID。
- 殺之前先 `pgrep -fl <樣式>` 把**將被殺的完整命令列**印出來看一眼。

### 🔴 被殺的行程不會留下錯誤訊息

它只是安靜消失，看起來跟「跑完了」一模一樣。所以事後查證不能問「有沒有報錯」，要問
**「最近 N 分鐘有誰的輸出檔剛好停止更新」**：

```bash
find . -maxdepth 1 -mmin -10 -name "*_out_p*.json"   # 誰剛動過
ls -lT <可疑檔>                                       # 落檔時間 vs 你動手的時間
```

本案就是這樣證明沒誤殺的：對方的 `abB1` 在 02:32:20 落檔、02:33:46 log 結束（結尾是
完整引用段落不是截斷），我 02:40 才動手。**這與 §9、§10 是同一條原則：沉默不是成功的證據。**

## 12. 跑批成本：codex log 裡就有實際 token 數，不要用估的

`run_stage.sh` 把每塊的 codex 輸出導進 `<prefix>_log_p<i>.txt`，收尾會寫一行 `tokens used`。
彙總它就是**實測成本**，不需要猜：

```python
tot = 0
for f in glob.glob(f"{prefix}_log_p*.txt"):
    m = re.findall(r"tokens used[:\s]*([\d,]+)",
                   open(f, encoding="utf-8", errors="ignore").read(), re.I)
    if m: tot += int(m[-1].replace(",", ""))     # 取最後一次＝該塊的總計
```

實測（紅隊 30 題/塊、含整段詳解當輸入）：**每塊中位 ~79k tokens**，13,552 題的紅隊
全程約 **36M tokens**。生成站每塊 20 題約 …（依科而異，同法量）。

用途有二：(1) 事前用「已完成塊的中位數 × 剩餘塊數」推剩餘成本，比拍腦袋準；
(2) 額度快見底時，把它當**停損的代理指標**——`codex` CLI 沒有 usage 子指令，
讀不到真實百分比，只能用使用者回報的兩個時間點校準（本案：11 分鐘掉 3%、跑 41 塊
→ 1% ≈ 1.1M tokens）。**校準要取保守側**（讓停損提早而非延後），並且明說這是推算不是實測。

⚠️ glob 要綁前綴：`rt_*_log_p*.txt` 會把歷史輪次（`rt_cs1`、`rt_csr1`）一起算進來，
一次把 137 塊灌成 371 塊。分類統計**沒做互斥／範圍檢查，結論一定膨脹**——
同一輪我還用兩條正則分別數「情況段」與「其他引導語」，結果第二條抓到的是同一段裡的
「依此」，兩邊各數各的就變兩倍。**先看實例，再相信數字。**

### 🔴 訂閱制**不等於**量不到成本（2026-08-06，一次判斷錯誤換來的）

我一度做出「這輪走訂閱額度，所以拿不到 `usage`，模型選型的成本軸會廢掉」的判斷，
還把它寫成待使用者裁定的三選一。**錯了**——上面整節講的 codex 那輪，本來就是
**訂閱制的 CLI 呼叫**。成本從來不是讀帳單，是**撈 token 數再乘牌價**。

> **判準：成本軸要的是「用了多少 token」，不是「被扣了多少錢」。**
> 只要跑批留下 token 紀錄，計費管道是訂閱還是 API 都不影響成本軸成立。
> 會被計費管道影響的只有**折扣**（例如 Batches 五折）——而訂閱制下折扣沒有意義。

Claude Code 側的對應物在逐字稿（`~/.claude/projects/<專案>/*.jsonl`），**比 codex 那條更細**：

| | codex log | Claude Code 逐字稿 |
|---|---|---|
| token | 一行 `tokens used` **總數** | `input`／`cache_creation`／`cache_read`／`output` **四欄分開** |
| 歸戶 | 靠檔名前綴 | **原生欄位 `message.model` ＋ 頂層 `effort`** |

```python
d = json.loads(line)                      # 半截行要 try/except 跳過
u = d["message"]["usage"]                 # 只有 assistant 訊息有
key = (d["message"]["model"], d.get("effort"))     # ← 選型的「臂」就是這組
```

🔴 **四欄分開是關鍵，加總會高估數倍**：`cache_read` 只算輸入價的 **10%**、
`cache_creation` 算 **125%**。實測某輪修復站：新輸入 542 token vs `cache_read` 1.29 億——
若把四欄加總乘輸入價，帳會錯到不能用。

**附帶好處**：模型選型的每一臂在定義上就是一組 `(model, effort)`，所以歸戶鍵是現成的，
不必自己插標記；同一臂的多次 run 用 `timestamp` 切開，run 間變異直接量得到。

⚠️ 兩個仍要守的：**時間窗一定要綁**（不綁就是上面那個 137→371 塊的膨脹）；
**牌價表會標日期**，過期就先更新表再信數字。

## 12′ 重測模型時的三個坑（都長得像「模型不行」）

本專案 2026-08 實測。**模型名有保鮮期、兩條原則沒有**——`reviewer ≥ generator`
與「避免成本倒置」不會過期，但「哪個模型放哪一檔」與所有錯誤率百分比都會。
模型改版與降價的節奏是數月一次，**照抄一年前的配置等於用過期的尺**。重測時：

1. **不要照抄外部跑分。** 那量的是它們的任務。本方法四個工作的失效模式完全不同
   （生成怕寫錯、重構怕弄丟舊事實、查核怕漏報、修復怕改壞沒指到的部分），
   決定性判準就不同——用同一把尺選四個工作，等於假設它們是同一個問題。
2. **先分辨是模型層、prompt 層還是架構層。** 實測兩次「某模型不行」的真因分別是
   prompt 缺一條保真條款（補上後同一模型從 43% 到 100%）與架構問題（改成寫入屏障後
   附帶損害結構性歸零）——**換模型都解不掉**。
3. **樣本量先算。** 缺陷率型指標在 n=40 下量不出任何東西：本專案曾以 n=40 定案
   「某配置錯誤率是三倍」，加到 n=200 配對後**連正負號都反了**。見 §14。

還有一條不會過期的規矩：**降階必須寫明兜底驗證網是哪道門，寫不出即不准降。**

## 13. 🔴 評測環境必須與生產環境一致：三次把「機器可修的問題」判成「模型不行」（2026-08-02）

模型評測那一輪，同一個病踩了三次，每次都差點導向錯誤的產線決策：

| 次 | 我以為的結論 | 真相 | 差點造成 |
|---|---|---|---|
| 1 | R 線輸入「lint 合規 0%」 | `wide-op-in-latin`，`normalize_mixed_punct()` 修得掉 | 誤判整批輸入不可用 |
| 2 | 修復站附帶損害 6.5%，推估「已上線的庫有數百段被改壞」 | 判分器抓選項字母只抓到 41%（只認「B 段／B：」，漏掉「B 的」「B 題項」「C 所列」），`want` 為空 → 所有段落被當成未指涉 | 對著不存在的事故發動全庫回溯（修正後實際 **1 題**） |
| 3 | luna 重構「lint 合規 0%」 | 它段落之間只給一個 `\n`，lint 的切段判準是 `\n{2,}` | **把當時保真度唯一勝出的配置判成不合格** |

根因同一個：**評測時沒有套用生產環境本來就會跑的零 token 修復步驟**。那些步驟原本
散在 `_build_RESUME_aprime.md` 的續跑清單裡，每支腳本各自實作、各自記得——所以每寫
一支新判分器就漏一次。

**修法不是寫一條規則，是收成單一正本**：`_build_features/premerge_gates.py`

```python
from premerge_gates import apply_gates
t = apply_gates(raw_t)                    # 四門依序：字面 \n → 單換行補雙 → 中段拆回 → 標點正規化
fails, warns = expl_lint.lint_one(t, ans, n_opt, options=..., stem=..., qtype=...)
```

**契約：任何要對詳解跑 lint、算合規率、或做模型評測的地方，都必須先呼叫
`apply_gates()`。不要自己複製其中任何一道**——複製就會分岔，分岔就會再踩一次。
`python3.11 premerge_gates.py --selftest` 驗四門本身（每門一則來自真實跑批的否證，
外加續行不誤切、冪等、空值）。

### 為什麼這件事特別容易騙過人

這類誤判**朝著「模型不行」的方向壞**，而那個結論看起來很合理——低價模型合規率 0%，
誰都會點頭。**它不會像 crash 一樣叫**，只會安靜地把一個好配置從候選名單上劃掉。
判準：任何模型在某個指標上拿到 **0% 或 100%** 這種極端值，先假設是判分器壞了，
不是模型壞了；去看它的實際輸出再說。第 3 次就是靠「0% 太反常」才回頭查出來的。

### 連帶：模型比較前先問「這個指標的分母乾淨嗎」

同一輪另一個坑：拿歷史紅隊 fix 當「髒題」考卷，實測 **73% 的髒題只是措辭修改**

不分流就用，召回率的分母是壞的，四個配置的比較全部建立在噪音上。
分流本身零 token——**`difflib` 比一次修復前後就知道**。

## 14. 🔴 樣本量：低基礎率下，n=40 量不出任何東西（2026-08-02，一個被推翻的定案）

A′ 生成站曾以 n=40 定案「terra max 錯誤率是 medium 的三倍」——真身是 **1 題 vs 3 題**。
Fisher 精確檢定 **p=0.62**，兩者的 95% 信賴區間 [0.4%,12.9%] 與 [2.6%,19.9%] 幾乎完全重疊。
加大到 **n=200 配對**之後：medium 12.0%、max 8.5%——**不只不顯著，正負號還反了**。

### 開跑前先算，不要跑完才發現量不出來

真實率若是 2.5% vs 7.5%（缺陷率型指標的典型量級），各臂需要的 n：

```
n= 40 →  1 vs  3  p=0.62      n=160 →  4 vs 12  p=0.070
n= 80 →  2 vs  6  p=0.28      n=200 →  5 vs 15  p=0.037   ← 門檻
n=120 →  3 vs  9  p=0.14      n=400 → 10 vs 30  p=0.0017
```

**配對設計省一半。** 兩臂寫同一批題、用 McNemar 只看不一致對，吃掉「這批題本來就比較難」
這個變異來源，同樣的 n 檢定力較高。A′ 兩臂同題就是這樣做的。

### 三方選一的勝率，不可以當兩方比率去做檢定

同一輪的第二個錯：盲評三個配置（甲乙丙）得到「15% vs 57.5%」，我拿 Fisher 當**獨立二項**
檢定算出 p=0.00015。那是錯的——三方勝率是多項分布，三個數字加起來才是 1，彼此不獨立。
正確做法是**限縮到兩者的對決場次跑符號檢定**（23:6 → p=0.0023）。差了兩個數量級。

### 單一科目的結論推不到全庫

那個盲評的 40 題全部來自同一個科目。換成跨 6 科的 n=60 重判，勝率從 23:6 縮到 38:22
（p=0.052），六個維度的均分差全部 ≤0.10。方向一致（併池 p=0.0006）但**效果小得多**。
定案前務必問：**這批考卷的科目分布，像不像我要套用的那個母體？**

### 順帶：1–5 分的評分維度容易全貼天花板

兩輪盲評的六維均分都落在 4.4–5.0，實際給分 **69% 是 5 分**。維度分數等於沒有鑑別力，
所有訊息都由 `best`（強制二選一）承載。**要鑑別力就用強制對決，不要用李克特量表。**

## 15. 🔴 實驗臂輸入等價：兩臂收到的字不同，比的就不是模型（2026-08-02）

> 📌 本節原本排在 §17 之後（它是後來補寫的，直接附在檔尾）。
> 2026-08-06 移到這裡，讓節號單調——**外部引用的 `§15` 一律指本節**
> （`SKILL.md`、`scripts/arm_parity.py`、`scripts/README.md`），所以搬的是位置、
> 不動編號；緊接其後的 `§15′` 是另一則、與本節無關，只是編號相鄰。

§13 管的是「評測 vs 生產」這條軸，本節管「臂 vs 臂」——同日、同病、不同軸。
另可對照 `reviewer-input-parity.md`：**兩個應該看到同樣東西的角色，實際看到不一樣的東西，
而差異不可見**——這是同一個疾病家族的第三員（審查者對撰寫者、評測對生產、臂對臂）。

### 實測案例

比較 A′ 生成站的兩個供應商。GPT 臂走 `codex exec "$PROMPT"`——18,559 字元的操作卡是
**指令本文**。Claude 臂沒有 CLI 可用，只能用 agent 派發，於是啟動者手打了一個包裝：
「去讀那個檔案，照它做」。

```
Sonnet 5（包裝：去讀檔案照做）   lint  0/20
Sonnet 5（操作卡逐字直達）       lint 20/20 ← 不同包裝
GPT terra max（本來就直達）      lint 20/20
```

同一個模型、同一批題、同一支判分器。**差 20 個百分點是模型差異，差 100 個百分點是
啟動者的差異——而它長得像結果，會被寫進報告變成「Sonnet 5 不合規」。**

### 契約三句

1. **啟動端**每發一塊就 `record(exp, arm, block, prompt, model, outfile)`，記的是
   **真正送出去的那串字**的雜湊。
2. **判分器**在算任何比較數字**之前** `assert_parity(...)`，不一致就拋錯。
3. **查無紀錄＝失敗，不是通過。** 這是最重要的一條——若「查無紀錄」放行，
   這道閘退化成 opt-in，跟散文規則一樣會被忘掉。

### 遮罩紀律

**不做語意正規化**——這道閘的存在意義就是抓「看起來一樣其實不一樣」，把差異洗掉
等於把自己關掉。只准遮兩樣，各有具名理由：

- **行尾／首尾空白**：shell 與檔案讀寫會動它，不遮會製造假警報，
  而**假警報會逼人關掉這道閘，那比沒有閘更糟**。
- **呼叫端指名的輸出檔名**：各臂必然寫到不同檔，是基礎設施差異。
  **必須明講是哪個字串**——不接受「自動偵測看起來像檔名的東西」，那會變成靜默的萬用洗白。

自檢要驗**六個方向**（少一個這道閘就有洞）：同文放行／異文擋下／未登記擋下／
空白不誤報／遮罩遮得掉但**遮不寬**／**舊帳不得為新跑背書**。最後一條是時間軸破口：
帳本跨執行持久化，重跑時忘了重新 `record()`，閘門會拿上一輪的雜湊放行。
判分器應傳入最舊輸出檔的 mtime 當 `newer_than`。

### 報告 parity 段落（缺了就是草稿）

任何 A/B 結論表下方**必附**：每臂的 `prompt_sha`、投遞通道（CLI 變數直達／agent 派發）、
機檢狀態。三態：**通過**／**擋下**／**未機檢**。

### 投遞保真：產生端與投遞端之間不能有人

```
CLI 臂    p="$(mkprompt ...)" ; codex exec "$p"     產生與投遞是同一個變數，中間沒有人
agent 臂  腳本產生 → 人肉眼手抄 → 貼進工具呼叫       ← 缺口在這
```

agent 派發的臂有一個 CLI 臂沒有的結構性缺口：工具的 prompt 參數只能來自訊息文字，
**沒有機制讓腳本既產生又投遞**。抄漏一行，帳本會說一致而事實不是。三個處置：

1. **投遞通道必須有一份不經人手的機械紀錄**——你的 harness 的紀錄在哪，開工前先找到它。
   （Claude Code 把每次 Agent 呼叫的完整 prompt 寫進 session 逐字稿 JSONL，那就是它的
   對應物。）比對 `generated_sha == delivered_sha`。
2. **自證雜湊行**：prompt 產生器在末尾附 `#PARITY sha256=<本文雜湊> chars=<N>`。
   兩臂拿到的這行逐位元組相同（不破壞等價），但任何捕捉點都能不依賴帳本自驗完整性
   ——手抄漏一行，字元數當場對不上。
3. **捕捉失敗＝強制標註「未機檢」，不得靜默視為通過。** 這是「查無紀錄＝失敗」在
   投遞層的延伸（放行但留疤，因為此時擋下等於全面禁用 agent 臂）。

**否決的作法**（列出來是因為它們看起來都合理）：
- 「禁止 agent 派發的模型當實驗臂」——過寬且歸因錯：缺口是**通道**的屬性，不是供應商的。
- 「手抄後回寫成檔案再 diff」——驗的是兩次手抄的一致性，不是投遞保真度；
  系統性抄寫錯誤會在兩次裡**重複同一個錯**，diff 照樣通過。
- 「叫子代理自報收到內容的雜湊」——證言必須由工具算出，不能由模型說出。

#### 🔴 反向的同一個洞：子代理**回**給你的東西也不能經人手（2026-08-07）

上面講的是「送出去」。實測回程有一模一樣的缺口，而且更容易得手：
子代理的結構化輸出裡有一個自由文字的 `reason` 欄，它在那裡描述了一句題幹該長什麼樣。
我**用手把那句話抄進修復腳本的 `EXTRA_STEM` 常數**——於是題庫裡多了一則
**非官方的改寫**（`104_104030_…_20`）。下一輪的子代理把它抓了出來。

> 手抄不是「這次不小心」，是**流程允許它發生**。允許了，遲早會發生一次。

處置與投遞端對稱：**修復值只能來自結構化欄位，且整筆覆蓋**。
子代理要改題幹就把**完整的 `stem`／`options` 陣列**放進結構化欄位裡回傳，
腳本 `q["stem"] = r["stem"]` 整筆寫入；`reason` 永遠只當人看的說明，**不得成為資料來源**。
這樣「手抄」在流程上不存在，不需要靠紀律。

副作用要一起想到：整筆覆蓋會動到題組共用欄位。實測子代理指出
`104_104030_總論一_14` 的 `passage` 是同組三題共用，只覆蓋 14 會讓同組不一致
——**覆蓋的粒度要對齊資料的共享粒度**。

### 條件模式：兩臂都走指標式投遞

讓兩臂都收到同一句「去讀 X 檔案照做」，等價瞬間恢復（一行字、肉眼可驗）。
**但只有當生產端本來就走指標式投遞時才合法**——上面那個 0/20 正好證明包裝不是行為中性的，
生產若是直達操作卡，指標式的評測就違反 §13。

### 這道閘為什麼會生效：閘放在必經之路

`premerge_gates`、發佈閘、`arm_parity` 三者都成功，共同點是**閘門放在「想要產物就繞不開
的那一步」，不放在「需要自律的那一步」**。啟動端需要紀律（會忘）；判分器是你想要數字
就一定得跑的那步。散文規則的失效模式是「要生效得先被想起」——這三層裡沒有一層依賴想起。

## 15′. 🔴 「該改的有沒有動」不等於「改對了」（2026-08-02，判分器讀反的第四例）

> 編號原本與下面的「§15 實驗臂輸入等價」撞號（2026-08-06 發現）。**所有外部引用的 §15
> 都指臂等價**（`SKILL.md`、`scripts/arm_parity.py`、`scripts/README.md`），故本節改為 §15′。
> 撞號在索引裡看不出來，只有拿章號當路由時才會把人送錯地方。

修復站訣選用「命中率＝finding 指到的段落有沒有被改動」當指標，結果 terra medium
96%、luna max 92%，看起來 terra 較好。**讀反了。**

四個不一致段落有三個來自同一題，該題的紅隊 finding 是：

> 結論雖與 ans 相符，**B、C、D 也列對**，但正解段以「官方答案」作答……

B、C、D 是被**稱讚**的，問題只在正解段。零 token 定位器看到字母就把三段標成待修：
- **luna max 原文照抄**（prompt 明寫：finding 不成立 → 不要改）→ 被判為「未命中」
- **terra medium 三段全改寫**了本來就正確的文字 → 被判為「命中」

指標在獎勵亂改。**任何「有沒有動」型的指標，都必須配一個「動得對不對」的復核**——
把修復成品丟回紅隊算通過率，才是決定性判準（實測兩者 9/31 vs 10/31，McNemar p=1.000，
完全打平；於是成本 5.3× 的差距成為唯一有效訊號）。

### 連帶：寫入屏障擋得住射程外亂改，擋不住定位器**超收**

段落級修復的「附帶損害 0%」是**相對於定位器的射程**算的。定位器把好段落劃進射程時，
模型改壞它會被記成「命中」而不是「附帶損害」——這道閘完全看不見。
定位器的精確度因此不是優化項，是**承重牆**。

## 16. `git rev-list --all` 包含 `refs/stash`（2026-08-02）

用 git 物件可達性判斷「這個 `.bak` 還有沒有留的必要」時，判準寫成 `rev-list --objects --all`
是錯的。`--all` 的意思是「`refs/` 底下全部」，**包含 `refs/stash`**，不是常被讀成的
heads/tags/remotes 三者。

只活在 stash 裡的內容是**假的「已備份」**：它撐得住 `git gc`，但 `git stash drop` 一下就沒了
——而我們正要拿「它已經在 git 裡」當理由刪掉唯一副本。正確寫法是明列耐久命名空間：

```bash
git rev-list --objects --branches --tags --remotes
```

這條是外部評審提出的灰帶，寫成自檢**當場踩中**。教訓不是「stash 很陰險」，是
**任何「它已經安全存在別處」的判斷，都要問那個別處會不會被單一指令抹掉**。

## 17. 接手檔要收攏成兩份，父計畫不可抄子線的數字（2026-08-02）

跑批專案會自然長出一堆「先讀這份」的接手檔——本輪計畫檔、當前狀態檔、
未解議題檔、每條線各自的 `RESUME_*.md`。實測長到 **7 份**，其中 4 份停在
三到五週前，而指路的 `CLAUDE.md` 指的正是最舊那份。

**危險的不是檔案過期，是「有東西叫人優先讀它」。** 一個壓縮後接手的 agent 照做，
會拿到五週前的世界觀，然後在那上面繼續推理——它不會知道自己讀的是舊的。

### 收攏規則

- **只留兩份會隨時間變的**：「還沒做完的」一份（每輪覆寫）、「做完的」一份
  （按日期＋commit 追加）。其餘各冊只記**不隨時間變的判準**（踩坑、決策、題型處理）。
- **單線續跑寫進計畫檔該線那一格，不要另開 `RESUME_*.md`。** 該線收工就蒸餾進回顧檔。
- 🔴 **一條線的進度數字只在一個地方有。父格要引用就放指標，不要抄。**
  實測：計畫檔抄的「counseling 2,909 題待辦」在該科已 100% 之後仍留著，
  照做會白燒 2,909 題的 token。**抄一次就開始腐爛。**

### 停用一份檔案：留墓碑，不要刪

刪掉會把所有 inbound link 變成死連結（實測 `00_STATE.md` 有 8 個檔在指、
`OPEN_ISSUES.md` 有 6 個）。改成三行墓碑指向新位置——
**一份不再宣稱任何事實的檔案就沒有說謊的能力**，比讓它保持正確便宜得多。

### 🔴 搬檔前先查誰在指它

跟「`pkill` 前先 `pgrep -fl`」是同一條規則：**先量作用域，再動手**。

```bash
rg -l "被搬的檔名" --glob '!_bak_archive/**' --glob '!**/.git/**' .
```

**尤其要看有沒有腳本在指它**，不是只有文件。實測兩支收尾腳本用
`echo … >> "$RESUME"` append 進度——檔案搬走後再跑，`>>` 會**把它生回來**
（空的、只有那一行），而且完全沒有錯誤訊息。退役的腳本要加 fail-loud 守衛：

```bash
[ -f "$R" ] || { echo "❌ $R 已封存；本腳本已退役" >&2; exit 1; }
```

（本輪就是先搬才查，順序錯了才補救——寫在這裡免得再犯。）

## 18. 多 session 下改 repo 名：push 會被重新導向到你不預期的地方（2026-08-02）

GitHub 改名後**舊 URL 會自動重新導向到新位置**，git push／fetch 都吃這個導向。
平常那是好事；**兩個 repo 交換名字的那幾秒鐘，它會把 push 送到錯的 repo。**

實測順序：

```
21:50  我把資料 repo 併進工具 repo
22:0x  我 rename A → A-frozen，再 rename B → A     ← 名字被交換
22:03  另一 session 在同一個工作目錄 commit 並 push
       它用的 URL 是舊的 A → 被導向到 A-frozen
結果：新 commit 落在「凍結備份」裡，主 repo 反而落後一個 commit
```

沒有任何錯誤訊息——push 成功、對方以為推上去了、主 repo 安靜地少一個 commit。

### 三條規則

1. **改名前先 `pgrep`／問一聲有沒有人在同一個工作目錄工作。** 多 session 共用同一個
   `.git`，你看到的「未提交變動」下一秒可能就變成別人的 commit（本輪就是：我報告
   「這是另一 session 未提交的檔」，三分鐘後它已經是 `HEAD`）。
2. **改名後立刻對帳三個數字**：本機 `HEAD`、新名 repo 的 `main`、舊名 repo 的 `main`。
   三者不一致就是有 push 走岔了。用 API 查（`gh api repos/<owner>/<name>/commits/main`），
   不要用 `git ls-remote`——後者也吃重新導向，會告訴你「舊名還活著」而看不出它其實指向新家。
3. **快照要打 tag，不要靠「某個 repo 的 HEAD 停在那裡」。** 「留舊 repo 當保險」這個
   做法的保險性來自 HEAD 的位置，而 HEAD 會被別人的 push 推走。改用
   `git tag pre-merge-<date> <sha>` 並推到兩邊——**tag 不會因為誰 push 就移動**。

> 修復很簡單（把落後的那邊 fast-forward 上去即可，commit 本身沒丟），
> 但**發現它靠的是主動對帳**。這類錯誤不會自己喊。

## 19. 🔴 「需人工改寫」常常是**操作選錯**，不是真的需要人腦（2026-08-02）

清操作卡術語洩漏（正文寫進了內部術語「題眼」）時，清理器只實作了**刪除**：
`正解：題眼在X` → `正解：X`。8,188 則裡 7,954 則過關，剩 **234 則刪了會斷句**
（術語出現在句中、或後面接的不是名詞片語），於是被標記「需人工改寫」躺了一輪。

**它們不需要人工。需要的是換一種操作：刪除 → 替換。**

```
刪除：本題問何者錯誤，題眼是急性間歇性紫質症…  →  ✗ 斷句
替換：本題問何者錯誤，關鍵是急性間歇性紫質症…  →  ✓ 名詞換名詞，文法必然成立
```

一張二十列的對照表就把 234 則全清完，順帶清掉其餘 6 科同缺陷的 847 則。

### 為什麼會判斷錯

**因為修法是跟著「怎麼發現的」走，不是跟著「壞在哪裡」走。** 缺陷是靠
`^正解：題眼在` 這個開頭樣式抓出來的，所以修法自然寫成「把開頭那段刪掉」；
但缺陷的本質是**詞彙洩漏**（不該出現的詞出現在正文），不是句構問題。
本質是詞彙的，就該用詞彙級操作——刪除是句構級操作，難怪句中的處理不了。

**下次遇到「剩 N 則需人工」，先問三個問題，再決定要不要動用人或模型：**

1. **這個缺陷的本質是哪一層**（字元／詞彙／句構／語意）？修法在同一層嗎？
2. **有沒有一個更保守的操作能達成同一目的**（替換 vs 刪除、標註 vs 移除）？
3. 真的要動模型的話——**它會改到不該改的東西嗎**？已驗證過的內容重寫一次，
   就是把附帶損害重新開一次門（見 IDR-0023 段落級修復的理由）。

### 換掉之後也要防「靜默猜測」

替換表必須是**允許清單**：後接詞不在表上就原樣留下並列印，由人看。
本輪第一版對主科剩 1 則、對其餘 6 科剩 14 則落在表外（`為`／`即`／`句`／`全是`），
逐一看過原文才進表。**若當初設一個 fallback 預設值，這 15 則會被靜默改成猜的詞，
而輸出畫面會顯示「殘留 0」。** 同 §13 的病根：看起來像成功的失敗最貴。

### 驗收（零 token，替換型改動專用）

| 驗什麼 | 為什麼 |
| --- | --- |
| 原字串殘留數 = 0 | 主指標 |
| **`apply_gates` 冪等數改前改後一致** | 證明只動了詞、沒動到結構——比「長度變化」更硬的訊號 |
| 記錄數不變、單行 JSON 不變式維持 | 資料不變式 |
| 抽 20–30 則替換後的上下文人眼看過 | 文法成立 ≠ 讀得順 |

## 20. 🔴 修復器認不出結構時，會生出**比輸入更壞**的輸出（2026-08-02）

併庫閘門有一道「單換行分段補成雙換行」：模型有時在段落中間折行，續行要接回上一段。
判斷「是不是段首」靠一組樣式（`正解：`／`A：`／`本題考點：`）。

套到**舊格式散文**上（`正解 B。` 沒有冒號、`A 正確：` 不是 `A：`、還有
`辨析重點：`／`(2)`／「四者相比，…」當段首），**沒有任何一行認得出來**，
於是每一行都被判成續行接回去——整則黏成一坨：

```
前: 正解 B。…故 B 為錯誤敘述。\nA 正確：戒酒硫…\n辨析重點：…   ← 3 段，可讀
後: 正解 B。…故 B 為錯誤敘述。A 正確：戒酒硫…辨析重點：…       ← 1 段，文字牆
```

**而流程只會看到「閘門跑過了」。** 沒有任何一個計數器會變紅：筆數沒少、字沒掉、
沒有例外拋出。這比 crash 難發現得多。

### 兩條修法，缺一不可

1. **給修復器一條退路**：接回去若接出「只剩一段」，就**原樣退回**。
   認不出結構時要承認認不出，不是硬給一個答案。這條要配一則**反向斷言**
   （丟一段沒有任何段首樣式的散文進去，斷言輸出 == 輸入）。
2. **換一個不必猜的訊號**。段首樣式列不完（下一個舊格式又會有新寫法）；
   改問「**每一非末行是不是都以終止符（`。！？：；`）收尾**」——是的話，
   一行就是一段，不必知道段首長什麼樣。實測 21 則舊格式散文**全部**符合，0 例外。

> **通則：白名單式的判斷（「長這樣才算段首」）碰到白名單外的輸入時，
> 預設行為必須是「不動」，不能是「當成另一類處理」。** 前者留下待辦，後者製造損壞。

### 為什麼會拖這麼久才發現

閘門是**併庫時**跑的，所以比它更早併進去的批次沒吃到、新增一道門也不回溯。
症狀藏在「`apply_gates(t) != t`」這個沒人在看的指標裡。

**把它變成一條可查的不變式**：全庫跑一次 `apply_gates`，數有幾則會變。
穩定狀態應該是 0——非 0 就代表**線上呈現與閘門認定的樣子不一致**。
每次新增一道門，這個數字都會跳起來，正好提醒你補套。

### 補套的驗收判準

正規化型改動不要用長度或肉眼驗。**主判準是「正規化後相等」**：把閘門**唯一被允許動的
東西**（空白、那幾個全形運算子）抹平之後，改前改後必須逐字相同——這證明只動了排版。
任一則不等就整批中止。再加冪等、記錄數、資料不變式，以及一次**端到端**確認
（取伺服器實際吐出的 bytes、跑前端同一段切段程式碼，不是只看本地檔案）。

### 🔴 §19 兩個 session 同時寫同一個資料檔，先確定誰擁有這條線

合併成單一 repo 之後，兩條線同時修同一個 `bank.json` 的同一個病灶。實測後果：

- 對方的交接單記錄到「掃描讀到寫入前的舊檔」——**並行寫入會互相覆蓋，
  而且沒有任何錯誤訊息**，只是後寫的贏。
- 兩邊各自逐題列舉，交集的題被修兩次、聯集之外的題兩邊都沒修。
- 更隱蔽的：**兩邊的呈現慣例不同**（一邊 Unicode `C₁₉H₁₉N₇O₆`、
  一邊 LaTeX `\(C_{19}H_{19}N_{7}O_{6}\)`），混在同一科裡很難看，
  而且之後沒有人知道哪一種是「對的」。

作法：**動手前先把未提交的東西提交掉**（未提交的最脆弱），
然後在交接單上寫明「這條線現在歸誰」與「慣例定為哪一種」——
這兩件事都不是跑腳本能決定的，要人裁決。發現對方也在寫時，**先報告再動手**，
不要因為「我這批已經驗過了」就搶著寫入。

### 🔴 §20 canary 證明判定式會動，樣本統計才證明它動對方向

寫「修題必檢詳解」的機檢器時，三個判定式**各被真資料修正過一次**，
而三次都是 canary 全綠、上真資料才現形：

| 判定式 | canary 說 | 真資料說 |
| --- | --- | --- |
| B'「引號片段在不在新題文」 | 合成案例過 | **7/7 全誤報**——詳解的「」大多是概念強調，本來就不在題文裡 |
| A 結論句只收一種寫法 | 合成案例過 | 三則正常詳解被判「沒有結論」；本站實測五種寫法 |
| 「X 正確」＝結論 | 合成案例過 | 負向題（何者不正確）裡的「B 正確」是**干擾選項**；813 則裡就 1 則露出 |

原因很直白：**canary 是我自己寫的，它只涵蓋我想得到的維度。** 上面第三條的
「題目正負向」這個維度，合成案例裡根本不存在——我寫的每個假題目都是正向的。

作法：**判定式寫完，先在整個母體上跑一次分佈，再看極端值。**
這一輪的分佈是「命中 88.4%／抽不出 11.4%／矛盾 0.1%」——
矛盾那 0.1% 只有一則，正是它把 polarity 這個維度暴露出來。
若當初只看「88.4% 很高，可以了」就收工，那條 bug 會一直在。

修完再跑一次分佈確認方向對了（矛盾 0.1% → **0**），而且要確認**其他格子沒有惡化**
——實測放寬結論句時「抽不出」從 93 掉到 92，沒有把誤報搬到別的格子。

順帶一條：負向偵測**不可收單字**。`未` 會把「其未平衡的熱化學反應式」
（正向題）誤判成負向。負向詞要綁在疑問句型上（`何者不`／`哪些不`／`不正確`）。

## 21. 🔴 量測迴路的污染：四個「不會報錯、只會給你一個合理數字」的洞（2026-08-06）

「商鞅測試」（紅隊／修復站的 model×effort 選型）開跑前逐項稽核輸入，抓到四個
**同一形狀**的洞——受測臂自己留下的痕跡混進了量測迴路。共同特徵是
**失敗時很安靜**：不報錯、產出一個看起來合理的數字。

| 洞 | 若沒攔下會看到什麼 |
| --- | --- |
| 考卷夾小抄（見下 `c` 混淆） | 一份 p 值全不顯著的漂亮報表 |
| 成本工具算主控自己的 token | 「基準臂又貴又慢」的合理結論 |
| 盲裁 `case_id` 印著臂代號 | 一份「盲裁」結果 |
| 用抽查認定資料來源 | 「189 塊全是同一個配置」 |

### 21.1 `c` 混淆：危害不是讓某臂佔便宜，是**壓縮臂間差距**

考卷的每一題都帶著生成站自報的把握度 `c`，而紅隊 prompt 明寫「c=low 加倍嚴審」。
實測 `c` 與髒不髒高度相關（臨床髒題 68% 是 `c=low`、乾淨題 20%，**3.4 倍富集**）。

**這等於在錯題上做了記號，還在指示裡叫受測者特別看那個記號。**
反直覺的地方：所有臂拿到同一張考卷，**沒有任何一臂佔便宜**——
危害是大家都被導到該看的題上，**分數一起被推高、擠在一起**，
p 值一律不顯著，於是「打平時取最便宜」的決策規則自動生效。
**這種偏誤不會在任何檢查點亮紅燈。**

解法**不是刪掉 `c`**（產線本來就帶著它跑，刪掉是在測一個不存在的管線），
是**乾淨題照髒題的 `c` 分佈分層抽樣**——`c` 還在、產線保真度不變，
但它不再攜帶「髒不髒」的資訊。代價要明講：乾淨組的 `c` 組成不再等於產線，
量到的誤報率會**高於**產線實況。

⇒ 一般化：**盤點考卷的每一個欄位，問「這個欄位跟正確答案有沒有相關」。**
有相關又被受測者看得到，就是小抄，即使它是產線本來就有的欄位。

### 21.2 兩次陽性對照：對受測者要求的，對裁決者也要要求

**第一次（受測臂）**：三個 Sonnet 臂在 12 題髒題上全部 0 召回、三檔零變異。
兩解——真的抓不到／任務沒送到。**手驗分不出來**：抽當年標 `high` 的髒題，
連基準臂也判 pass，標籤本身太硬，**那個樣本對兩種假設的鑑別力是零**。
⇒ 改造一個**不可能漏**的缺陷：拿乾淨題只翻結論字母、中段一字不動，
製造「首段說故選 A、中段說 A 故非答案」的自我矛盾。六臂全部 3/3 抓到
⇒ harness 一視同仁，0 召回是真的能力結果。

**第二次（裁決者）**：130 則盲裁跑出 **零個 `invalid`**。同一個形狀，
**不能對受測臂要求對照、對裁決者就免了**。⇒ 餵三類「照 prompt 明文就該判
invalid」的假質疑（假引文／要求改答案／要求補無關延伸）各 3 則，9/9 全中
⇒ 裁決者有鑑別力，零 invalid 是真的。

⇒ 一般化：**當一個判準「兩種完全相反的解釋都說得通」時，加測試不如加一個已知答案的樣本。**
而那個樣本要選**不可能漏**的形狀，不是選最典型的形狀。

### 21.3 成本是**行為**的函數，不是標價的函數

開跑前用標價推的「等成本對決」（$0.15 vs $0.14，近乎等成本）被實測推翻：
**$1.43 vs $0.85，1.68×**。粗估錯在假設「N token 輸入 × 標價」，
而真實成本由 `cache_read` 主導，**它的佔比取決於模型跑幾輪工具**——那是模型自己的選擇。

同一個 (model, effort) 在不同批次密度下也差很多：同樣 Opus 5 medium 跑紅隊，
小批交錯 ~$1.88/塊、37 塊同模板一次跑 **$0.50/塊，3.7×**。

⇒ **任何「等成本設計」只准在探針實測後現配，且換 prompt 就要重探。**
跨輪比較成本時，除了模型與 effort，還要註明**批次怎麼排**。

### 21.4 三個工具層的坑（都只會靜默算錯）

- **逐字稿的 `timestamp` 是 UTC，命令列給的是本地時間。** 直接字串比大小整整偏 8 小時。
  全滅時看得見（「沒撈到資料」），**窗口只錯開一部分時會靜默少算**。
- **subagent 的逐字稿在下一層目錄，主 session 的在上一層。** 若主控自己也跑在受測配置上
  （例：主控 Opus 5 high、基準臂也是），用時間窗撈會把 orchestration 記進基準臂。
  **指到 workflow 的逐字稿目錄是結構性排除，不靠記得切窗。**
- **`case_id` 這種「技術欄位」也會洩漏來源。** 第一版寫成 `f"{qid}#{tag}{run}{j}"`，
  臂代號就印在 id 裡送給裁決者看。**欄位名乾淨不代表欄位值乾淨**——
  白名單要驗到值。

### 21.5 兩票 OR 的價值要逐對量，不能由標籤推定

`IDR-0021` 的頭條「跨模型多樣性勝過挑一個更強的單一模型」機制完好，
但**被推翻的是拿模型名目差異當「誤差不相關」的代理**。
Claude 5 家族內實測：每一對臂的 `P(B漏|A漏)` 都落在 **0.89–1.00**，
而 `P(B漏)` 只有 0.38–0.79——**一個臂漏掉的題，另一個幾乎必然也漏**。
最佳組合聯集 36/52，而單臂已有 34/52，**第二票只買到 +2 題、成本翻倍**。

「同廠不同模型」這個標籤在兩個世代給出相反的答案 ⇒ 它不能當預測子。
**要買第二票之前先量那一對的 `P(B漏|A漏)`。**

### 21.6 兩站會選出不同檔位，而且方向相反

同一批候選臂，紅隊站選出 `medium`、修復站選出 `low`：
紅隊要**發現**（effort 買到更深的搜尋），修復站要**執行既定指令**
（finding 已指明哪裡錯、怎麼改，多想沒有用）。
⇒ **分站選型不是形式主義**——一律用同一個配置的話，一站會過省、另一站會過付。

## 22. 🔴 回報一個數字之前，先確認它回答的是對方要決定的那件事（2026-08-07）

前一節談的是**數字算錯**。這一節談一個更便宜也更常見的失敗：**數字是對的，
但它回答的不是對方拿它來做決定的那個問題。**

實測：我回報「clinical 有 **30 卷**原卷不存在，需要決定要不要回考選部補抓」。
真相是——

- **30** 是「**還缺詳解**的題數」；
- 「**無卷可驗**」的是 **1,240 題**；
- 而原卷其實**一卷都沒缺**（三個工具缺陷，見 `parsing.md` §11.5）。

我把兩個不同母體的數字併成一句話，差 **40 倍**，而且那句話的用途是**要使用者去跑一趟**。
使用者只問了一句「哪個年份、哪個考科？」，整個結論就散了——
**因為那個問題要的是清單，而我手上只有一個總數。**

三條檢查，回報前逐條問自己：

1. **這個數字的母體是什麼？** 「缺詳解的題」「無卷可驗的題」「缺檔的卷」是三個母體，
   任何兩個放進同一句話都要先講清楚各自是誰。
2. **對方要用它做什麼決定？** 決定要不要花力氣 ⇒ 他要的是**成本**（幾卷、哪幾卷）；
   決定要不要信任資料 ⇒ 他要的是**覆蓋率**。給錯那個，數字再準也沒用。
3. **能不能當場列出來？** 列不出清單的總數，多半代表我還沒真的看過那批東西
   ——**列不出來這件事本身就是訊號**，不要用總數把它蓋過去。

> 這與 gates.md「產物形狀要求」是同一條律換到人身上：那條講「沒跑要看得見」，
> 這條講**「我其實沒查過」也要看得見**——而總數是最好的遮蔽物。

## 23. 🔴 使用者給了兩條路線，工具就不可以硬編其中一條（2026-08-07）

**實測**：使用者明講「有兩條路線（自家模型／外部 CLI），這週外部額度快沒了，走自家這條」，
計畫檔也白紙黑字寫著「本輪所有跑批走 A 路線，B 路線目前不可用、不是現在的選項」。
結果仍然跑了 24 次 B 路線，把外部週額度從 92% 燒到 100%。

**根因不是「沒讀到」，是兩個缺陷疊在一起**：

| 缺陷 | 為什麼致命 |
|---|---|
| **後端被硬編在腳本裡** | 指令違反一次是一次；**工具寫死是每次執行都違反**。而且它會複製傳染。那批是同一個模板複製四份，修一份留三份 |
| **模型與 effort 有隱含預設** | `MODEL=${4:-<某模型>}` `EFFORT=${5:-medium}` 這種寫法，讓一次跑批可以落在**沒有人指名過的組合**上 |

### 三條規則

1. **雙軌是介面問題，不是紀律問題。** 若計畫裡存在兩條路線，runner 必須有
   `BACKEND` 這類參數，**且預設值是使用者指定的那一條**。「記得選對邊」是散文規則，
   要被想起來才生效；預設值不需要被想起來。
   成本對比很誇張：**雙軌的代價是一個環境變數，單軌的代價是一次額度歸零。**
2. **具體指出哪個模型、哪個效能，不給預設值。** 「用最強的」不是一個配置，
   它會靜默解析成最貴的那一格。缺 `MODEL` 或 `EFFORT` 一律**拒跑**，不要填補。
   （改動一組配對是一次**量測**，屬於 skill `shangyang-retier`，不屬於「改一下腳本預設值」。）
3. **配額訊號優先從後端「已經寫下的副產物」讀，不要另外發 probe。**
   實測繞了一圈：先假設有 `usage` 子指令（沒有），再想「跑一個極小 probe 拿狀態」
   （probe 拿不到配額，而且自己也要花錢）。正解是後端**每次呼叫後都把配額快照寫進自己的
   log**，讀上一次的殘留即可，零 token、零網路，而且**跑越多越準**。
   > 通則：**要找的訊號常常已經在系統的副產物裡，不必另外製造一個。**
   > 找不到官方查詢介面時，先問「它有沒有把這件事寫進哪個檔」，再考慮發請求。

### 閘門形狀（可機檢）

- runner 缺 `BACKEND`／`MODEL`／`EFFORT` 任一 → **退出碼非 0，且訊息要指出另一條路怎麼走**。
- 配額讀不到時回傳的必須是 `unknown` **這個自己的值**，且呼叫端一律當「拒跑」處理。
  **`unknown` 不可以退化成 0**，否則「我讀不出來」會被靜默升級成「還很多」。
  這是 `gates.md` §A4 那條律（「我不知道」不可與合法值同形）在**配額**上的第 N 個實例：
  同一條律已在答案狀態、缺塊判定、額度三個地方各咬過一次。
- 停跑門檻用**剩餘**表述、不要用已用（人腦問的是「還剩多少」）；且要分兩段：
  **開新工作的門檻**與**收尾已開工作的地板**，兩者之間必須靠**實測燒率**做預估，
  不是拍一個固定值。燒率隨模型、effort、塊大小變，寫死的數字下一次配置就錯。
- 跑批**必須保留後端回報的計量欄位**（token 數、配額快照）。實測那四支把後端輸出
  丟進 25 bytes 的 log，事後查不到任何東西。這是「缺產物＝未跑」在**計量**上的版本。

**不要寫進本 skill 的部分**：哪個供應商、哪個模型名、門檻設幾 %。那些是專案決策，
放專案的 SPEC／ADR。**原則沒有保鮮期，模型名有**，抄過來的當天就開始腐爛。

## 24. 🔴 冪等判準從來沒問過「這是誰的輸出」——前綴撞號會讓整塊靜默跳過（2026-08-09 實戰）

§7（撞名毀掉回溯點）與 §10（有效 ≠ 完整）的第三代。前兩代講的是**同一次工作**的輸出
壞掉或寫不完；這一代是**別人的輸出**冒充你的。

實況：`rg1` 這個 prefix 七月底跑過 doctor，`rg1_out_p1.json`（16 筆醫師題）一直躺在
`goldens/` 裡。2026-08-09 拿同一個 prefix 跑 nursing 的 179 題重生成，第 1 塊被冪等判準
判定「已完成」整塊跳過。那個檔：

- 存在 ✅（擋得住 `[ -s "$OUT" ]`）
- JSON 合法 ✅（擋得住 `json.load`）
- 內容與本次輸入 **一題都不重疊** ❌

三層判準演進，每一層都只補了上一層漏掉的那一種：

| 判準 | 擋得住 | 擋不住 |
| --- | --- | --- |
| 檔案非空 | 空檔 | 半截檔（§7） |
| JSON 合法 | 半截檔 | 短塊（§10） |
| 題數等於輸入 | 短塊 | **撞號**（題數剛好也對就完全看不出來） |
| ✅ **輸入的 qid 集合 ⊆ 輸出的 qid 集合** | 以上全部 | — |

**判準要問的是身分不是形狀。** 前三層問的都是「這個檔長得對不對」，而長相是可以碰巧
對的。只有「這些題在不在裡面」是身分問題，碰巧對不了。

機器閘（教訓畢業律）：

```zsh
# run_stage.sh 的冪等判準
if [ -s "$OUT" ] && python3 -c '
import json,sys
try:
    want={r["qid"] for r in json.load(open(sys.argv[1]))}
    got={r.get("qid") for r in json.load(open(sys.argv[2]))}
except Exception: sys.exit(1)
sys.exit(0 if want and want<=got else 1)' "$IN" "$OUT" 2>/dev/null; then
  continue
fi
```

外加一支可單獨跑的對帳器（`verify_blocks.py <prefix> [--rescue]`），逐塊印
`in / out / 缺哪些 qid`，`--rescue` 把不合格的輸出 `mv` 成 `.short`（**不是 `rm`**，
撞號的那份可能是別條線還沒併庫的資產）並把輸入改寫成只剩缺的題，重跑即補洞。
它自帶 `--selftest`：造一個「合法 JSON、形狀正確、少一題」的檔，判準必須擋下來。

**順帶的操作規則**：prefix 是命名空間，不是標籤。開新一批前先
`ls <prefix>_*` 看有沒有人住過；要嘛換 prefix，要嘛先把舊的搬走。

## 25. 🔴 配額快照沒有時效檢查：兩天前的 100% 與現在的 100% 完全同形（2026-08-09）

§21 那四個洞的第五個。配額讀數來自 codex 寫在 `~/.codex/sessions/**/rollout-*.jsonl`
裡的 `rate_limits` 殘留——**零 token、零網路**，這個設計是對的。錯的是讀法：

```zsh
codex_used() {
  for f in $(ls -t ~/.codex/sessions/*/*/*/rollout-*.jsonl | head -30); do
    v=$(rg -o '"used_percent":[0-9.]+' "$f" | tail -1 | grep -o '[0-9.]*$')
    [ -n "$v" ] && { print -r -- "$v"; return 0 }      # ← 沒問這個數字幾歲
  done
  print -r -- unknown
}
```

實測：2026-08-06 配額燒到 100%，08-08 01:26 重置。08-09 開工時這支回報 `used 100.0`、
`remaining 0.0`，閘門正確地拒絕啟動——**而配額其實是滿的**。最新那份 rollout 是
08-07 寫的，裡面那個 100 是兩天前的事實。

`unknown` 這條路設計得很好（「我不知道」與任何合法值不同形，見 §21），但**過期的已知值
沒有走進那條路**——它長得像一個合法的新讀數。

修法有兩層，第二層才是真的：

1. **加時效**：快照比 `now - 重置週期` 舊就回 `unknown`，讓它走既有的拒絕路徑。
2. **用一次最便宜的呼叫刷新它**：`codex exec -m <小模型> -c model_reasoning_effort='"low"'
   --sandbox read-only "Reply with exactly: PROBE_OK"`，實測 11.5k token、數秒，
   回來之後快照就是當下的。**開工前的第一件事就是這個 probe**，比事後懷疑數字便宜太多。

判準：**任何從殘留檔讀來的數字，都要能回答「它幾歲」**。回答不出來的，
和讀不到應該是同一種待遇。

## 26. 🔴 派工給沙盒代理：分工線是「誰有出口」，不是「誰比較聰明」（2026-08-09 實戰）

一輪之內，同一個代理被三種**與能力無關**的環境缺口擋死三次。三次的表面症狀都像
「代理不會做」，真因全是「我沒給它做得到的條件」。

| 缺口 | 代理的反應 | 如果沒發現會怎樣 |
| --- | --- | --- |
| 沙盒**沒有對外網路**（`curl ceec.edu.tw` 直接 DNS 失敗、MCP 也連不上） | 停下來要 URL 清單 | 以為「資料源掛了」 |
| 操作卡的數字**過期**（卡寫 180 卷、磁碟上 174 卷） | 停在資料契約矛盾，拒絕產出 | 以為代理鑽牛角尖 |
| 沙盒**裝不了 pymupdf**（沒網路，`pip install` 必敗） | **自行降級成 `pdftotext`，把全部題標成 `review`** | ☠️ 最危險的一種，見下 |

### 第三種最危險：誠實標註的降級品

它沒有說謊——輸出確實寫了「本次僅能使用 `pdftotext`，故降級為 `review`」。
但那不是誠實降級，那是**把「我沒用對工具」包裝成「資料有問題」**。
下游看到的是一批 `review`，會照著去修一批**根本沒壞**的資料，而每一則 `review`
都要人去查源 PDF。一個誠實的錯誤標籤，成本比一個明顯的失敗高得多。

操作卡要寫死這一條：

> 拿不到指定工具就**停下來回報**，不要交降級品。把工具缺口寫成資料缺陷，
> 是本卡唯一不可原諒的錯。

### 三條可直接照抄的派工規則

1. **分工線畫在出口能力上**：要網路、要 MCP、要憑證的活留在主控（它有這些）；
   要 token 的活給代理（它有這個）。主控先把 URL 清單、PDF、manifest 全部落到本機，
   操作卡改寫成「檔案已經在了，**不要嘗試下載**」。實測：改寫之前兩次派工全部空手而回，
   改寫之後第一次就開始做事。
2. **環境要預先建好，不要叫代理自己裝**。例：主控先 `uv venv .venv-pdf` 並裝好 pymupdf，
   卡裡直接寫「用 `.venv-pdf/bin/python`，不要 pip install」。
   一句路徑省掉的是一整輪的降級品。
3. **卡裡的每個數字都要在派工當下從產物量一次**，不要從舊的偵察報告抄。
   一個與磁碟牴觸的數字會讓好代理直接停機（這其實是對的行為），
   而讓壞代理去圓那個數字。

## 27. 🔴 產線一律倒敘：資源不夠時，順序就是唯一決定成果價值的東西（2026-08-09 使用者裁定）

開一科新題庫的詳解產線時量到：每塊 20 題約消耗週配額 0.33%，該科 12,763 題切成 639 塊，
**全跑要 209% 的配額**，一個週期放不下。

而產線原本的順序是 **qid 字典序**——也就是最舊的年份排最前面。
那不是任何人選的順序，是「沒有人做決定」時的預設值，
而它剛好把最貴的資源優先花在**最不會被練的年份**上。

配額停下來時，成品會是「最舊的四年有詳解、最新的四年沒有」。**而且看不出來**：
停下來時你看到的是「已完成 227/639」，那個百分比不會告訴你它停在哪一年。
**進度數字會隱藏順序的後果。**

### 規則（詳解生成、紅隊、修復三站一致）

1. **一律由新到舊。** 切塊前依年份遞減排序，第 1 塊必須是最新一年。
2. **預設目標是最近十年，不是全部。** 十年做完就停下來重新評估，
   要不要往回延伸依邊際效益（那些年份實際被練的頻率）與邊際成本（配額、以及紅隊與修復的
   連帶量）而定，**不是預設要做完**。
3. **十年清單必須在每次派工當下重算**，不可存成固定名單——明年的「最近十年」不是今年這十年，
   沿用舊清單會靜默漏掉最新一年。

### 這與 era 下限是兩件事，不可混為一談

- **era（收哪些年份入庫）** 是內容判斷：這些題還算不算數。入庫是零 token 且可逆的，
  砍年份不可逆，所以預設全收。
- **產線順序（先做哪些）** 是資源排程。

把資源排程寫成 era，會讓下一個接手的人以為那些年份的題**有問題**，
而它們只是還沒排到。兩者混用一次，就要花一輪去查一個不存在的資料缺陷。

### 代價要寫在規則旁邊

- 舊年份會長期停在「有題無詳解」。前端必須分得開「這題沒有詳解」與「還沒生成」，
  否則使用者看到的是空白而不是狀態。
- 十年之外的題仍佔著 `parse:ok`，若練習池不分年份，使用者仍可能抽到沒詳解的舊題。
- 「十年」是依考生實務下的判斷，不是量出來的最適值；要翻案請帶實際作答分佈回來。
