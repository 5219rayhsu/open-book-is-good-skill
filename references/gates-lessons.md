## §D 🔴 產物存續：閘門的證據躺在哪，決定它是不是真的存在（2026-08-07）

「缺產物＝未跑」這條律有個沒寫出來的前提：**產物要活得比它證明的那件事久**。
實測一天之內，同一個判準的三個方向各踩一次：

| 踩法 | 實況 |
| --- | --- |
| 以為「有備份」就安全 | 備份寫進了 `_bak_archive/`，而那個目錄被 gitignore。備份不進版控＝只活在一台機器上 |
| 以為「留在工作樹」才安全 | 58 支腳本 58/58 都在 git 追蹤中，刪掉一個 byte 都沒少。留著只多一份可被複製的舊模板 |
| **以為閘門在跑，證據就存在** | 臂等價帳本 `_arm_parity.json` **一直被 .gitignore 的白名單擋在外面**。閘門天天在跑、發表的數字全靠它舉證，而它只活在一台機器上，而且沒有人發現 |

第三個最貴，因為它**沒有任何症狀**：閘門正常運作、數字正常產出、檔案正常存在，
只有在換一台機器或磁碟壞掉的那一刻才會發現證據從來沒有離開過本機。

### 兩件事要分開，不能互相替代

1. **耐久度**＝它躺在哪（有沒有進版控／有沒有離開這台機器）。
2. **可達性**＝有沒有人寫下路徑（翻案者知不知道去哪找）。

**保留檔案只買到耐久度的錯覺，買不到可達性。** 一份躺在資料夾裡、沒有任何文件
指向它的證據，跟不存在的差別只在於「有人碰巧翻到」。反過來，刪掉檔案而留下
「commit sha ＋路徑＋取回指令」，兩者都有。

### 三條閘門形狀

- **凡是閘門會讀的檔，必須進版控。** 建 repo 時就檢查一次：
  `git check-ignore -v <每個閘門的產物路徑>`，命中就是漏洞。
  用 gitignore **白名單**制的專案特別容易中，因為漏收是靜默的。
- **指標要有兩個入口，人一個、機器一個。** 人讀的寫進 ADR；
  機器讀的寫進閘門自己的帳本，且 **key 的形狀必須讓閘門不可能把它當成一筆證據**
  （例如底線開頭、外加顯式 `parity: "unverified"` 欄位）。
  這是 gates.md §A4 那條律在**指標**上的實例：指標不是證明，兩者同形就會被讀成證明。
- **刪除獨立成一個 commit**，指標引用它的父 sha。混在別的變更裡，
  將來 blame 要花十倍時間才能還原「刪之前長什麼樣」。

**代價要寫明**：刪檔＋指標把證據存續綁死在完整 git 歷史上。
所以採用這個做法的專案必須同時登記：主分支不得重寫歷史、遷移不得 shallow clone。
沒有這條配套，這個方案就不成立。

## §E 🔴 `not_run` 的**理由**是一句待查的主張，不是事實（2026-08-07）

「缺產物＝未跑」那條擋住的是**沒留下痕跡**。還有一種更安靜的失效：**產物在、狀態欄
寫著 `not_run`、旁邊附了一個理由，而那個理由是錯的。**

實測：某科的門 gates.md §A 報告寫

```json
{"status": "not_run", "reason": "本 repo 未留該科官方答案 PDF（找不到 <路徑> 下的答案檔）"}
```

那些答案 PDF 一直都在，只是不在理由裡寫的那個路徑下。門的程式本身讀得好好的——當場跑，
3945 題一致、15 題不一致（15 題全是官方送分而題庫存 null）。也就是說：**該科全部答案
在此之前都是回推的、從未對過官方鍵**，而報告看起來是一份「已知情、已記錄」的待辦。

#### 為什麼這比「沒跑」更難發現

`not_run` ＋ 一個具體的理由，讀起來像**已經有人查過而且查清楚了**。它把「還沒做」
包裝成「做不到」，於是每一個後來的人都會跳過它——理由愈具體，跳過得愈心安。
「找不到檔案」這種理由尤其危險，因為它**看起來可驗證所以沒有人去驗**。

#### 閘門形狀

1. **`not_run` 的理由裡若提到路徑、檔案、缺料，就必須附一條當場可跑的驗證指令**
   （`ls <路徑>`／`test -f`），讓下一個人一秒鐘就能證偽它。寫不出這條指令的理由不准寫。
2. **`not_run` 要帶 `checked_at` 日期。** 沒有日期的 `not_run` 一律當作未查證，
   下一輪碰到就重跑一次，不要讀理由。
3. **重跑的成本若低於讀懂理由的成本，就直接重跑。** 本例整科重跑約四分鐘，
   而爭論理由對不對要更久。

> 一般化：**擋路的告示牌也要定期驗。** 一條寫錯的理由和一個真的阻塞，對後來者的
> 觀測效果完全相同，但前者不會自己消失。

## §F 🔴 修復腳本的成功訊息，必須由**讀回檔案**產生，不能由計畫產生（2026-08-07）

實測：一支回源修復腳本印出「✅ 已修 4 題」並逐題列出改動，**而檔案一個位元組都沒變**。
成因是 `plan()` 內部自己 load 了一份題庫、`apply()` 又 load 了一份，改的是前者、
寫出去的是後者。訊息是從**計畫**推出來的，所以計畫對，訊息就對。

這與「用內容驗、不用狀態碼驗」是同一條，只是發生在自己家裡：**工具回報自己成功，
和工具真的成功，是兩件事。**

#### 閘門形狀

- 寫檔後**重新讀一次那個檔**，對每一筆改動斷言新值（選項、題幹、答案字母都要），
  斷言過了才印成功訊息。
- 順帶一提：**寫回時要保持原檔的排版**。單行 JSON 用 `indent=1` 寫回去，
  4 筆改動會變成 7 萬行 diff，等於把改動藏起來，review 時沒有人看得見。

同族：§P（回傳值被丟掉）、batching-and-measurement-lessons.md §31（產物只活在回傳值裡）。

## §F′ 🔴 一道閘讀錯欄位不會報錯，它只會一直說沒事（2026-08-09，同一天兩次）

同一個形狀在一天之內出現兩次，依教訓畢業律升級為硬規則。

| 閘 | 讀了哪個欄位 | 該讀哪個 | 後果 |
| --- | --- | --- | --- |
| 孤兒圖引用 | 只有 `stem` | `stem` ＋ `passage` | 靜默漏抓 137 題（題組的圖引用寫在共用 passage） |
| 教訓寫回 | commit 的 `%s`（標題） | `%B`（整則訊息） | 誤放一個真的沒寫回的 commit（標題寫做了什麼，學習痕跡永遠在內文） |

兩次都不是判準錯，是**判準套在錯的欄位上**。這種失效沒有任何外顯症狀：
閘照跑、報告照印、抓到的數字看起來很合理，漏掉的那些長得跟乾淨資料一模一樣。
**能報錯的錯誤便宜，不能報錯的錯誤才貴。**

### 硬規則：新閘門的 selftest 必須有一個「payload 放在錯欄位」的反例

known-bad 樣本不可以全部把訊號放在最順手的那個欄位。至少要有一則，
它的訊號**只**出現在次要欄位（passage 而非 stem、body 而非 subject、
巢狀結構而非頂層），而該樣本必須被抓到。

這條的價值在於它逼你回答「這個訊號還可能停在哪裡」——那個問題如果不在寫
selftest 的當下問，之後就不會有人問了，因為閘門會一直回報通過。

### 推論：一道可以被**無關動作**滿足的閘，等於沒有閘

教訓寫回閘 v2 的判準是「skill repo 的最新 commit 晚於所有帶標記的專案 commit」。
在 skill 改一個錯字就會特赦當天全部債務——判準看的是**時間先後**，
而時間先後不承載「這則教訓有沒有被寫下來」的任何資訊。

改成**逐筆對帳**：每一筆債要嘛被一則 skill commit 以 `lesson-of: <sha>` 明確認領，
要嘛被一則 `no-lesson-for: <sha> <理由>` 明確豁免。判準問的是「這一筆結清了嗎」，
不是「有沒有人在那之後做過事」。

> 設計閘門時要問的第三個問題（前兩個是「讀不到怎麼辦」「錯誤值會落在哪個方向」）：
> **有沒有一個與這件事無關的動作，可以讓它通過？**

### 推論二：工單要用**目標狀態**算，不要用**狀態轉換**算（2026-08-09，一天內兩科都中）

孤兒圖引用那道門的 `--apply` 只把 `orphan_figref` 這條理由標給**這一輪從 `ok` 降下來**
的題。下游裁圖站照這條理由取件，於是「早就因別的理由待審、但同樣缺圖」的題
**永遠不會進工單**——它們已經在目標狀態裡了，所以不再發生狀態轉換。

| 科目 | 照「這一輪降了幾題」派工 | 實際「現在還缺附件幾題」 | 漏掉 |
| --- | --- | --- | --- |
| 藥師 | 239 | 263 | 24 |
| 分科測驗 | 186 | 401 | 215 |

分科測驗漏掉的比派出去的還多。而漏掉的那些**在驗收報表上完全看不見**：
代理把 239 題做完、雙向檢查自報 0/0/0、涵蓋率 100%——因為它的雙向檢查
也只掃它自己的工單。**一道範圍等於自己工單的雙向閘，數學上只能回傳零。**

兩條硬規則：

1. **工單的定義句必須是狀態，不是動詞。** 寫「現在仍缺附件的強證據題」，
   不要寫「本輪降級的題」。前者可以重跑到收斂，後者只在第一次跑對。
2. **雙向檢查的掃描範圍必須是整個題庫，不是這一輪的工單。**
   驗收時主控要自己重跑一次，代理自報的 0 只證明它的工單做完了。
   實測就是這樣抓到藥師那 24 題的：代理報 `ref_no_fig: []`，主控重跑得到 24。

> 設計工單時要問的問題：**如果這件事昨天做過一半，今天這份工單會不會漏掉那一半？**

### 推論三：跨紀錄的**引用**，要夾帶一段冗餘的自證（2026-08-09）

教訓寫回閘允許事後豁免：在任一個後續 commit 的內文寫 `no-lesson-for: <sha> <理由>`。
判準只認那個 sha。

實測翻車：作者想豁免**正在建立的這一筆**，於是在 commit 訊息裡寫
`no-lesson-for: $(git log -1 --format=%h)`——而 `git log -1` 在 commit **之前**求值，
回的是**上一筆**。那一筆是真的教訓，就這樣被靜靜豁免掉，閘門回報全綠。

這個 sha **格式正確、長度正確、確實存在於歷史裡**，只是指向錯的東西。
與「配額讀數回 0.0」是同一族：**wrong-but-legal 的值比讀不出來的值危險得多**，
因為每一道健全性檢查都會放它過。

治法是讓引用**帶著它自己的證明**：豁免格式改成

```
no-lesson-for: <sha> ~<被豁免 commit 的主旨片段>~ <理由>
```

閘門拿 sha 去查主旨，對不上就拒認。一段冗餘資訊，把「寫錯」從**合法**變成**可偵測**。

> 一般化：**任何用識別碼指向另一筆紀錄的地方（sha、qid、檔名、外鍵），
> 都要問「寫錯一個仍然合法的識別碼，會發生什麼」。**
> 答案若是「安靜地做錯事」，就補一段冗餘欄位讓它自證。

#### 但先問一句：這裡真的需要識別碼嗎？（2026-08-09 第二次修正）

上面那條是對的，卻不是最省的。**這個事故的真形不是「sha 抄錯」，
是「想指涉一個還不存在的紀錄」**——作者要豁免的是**正在建立的那一筆 commit**，
而它在寫訊息的當下還沒有 sha。不存在的東西沒有名字，於是他用
`$(git log -1)` 去猜，猜到上一筆。

所以更好的形是把指涉整個拿掉：**讓豁免長在被豁免者身上，身分由包含關係決定。**

```
# 常態：豁免這一筆 → 寫進它自己的內文，不寫 sha
no-lesson: 純派工與環境安裝，無可推廣判準

# 罕見：豁免已推送的舊 commit → 才需要識別碼，且錨詞兩個字就夠
no-lesson-for: d0d3b24 ~多選~ 這條已由 lint 的 canary 覆蓋
```

**沒有名字，就沒有名字可以寫錯。** 冗餘自證退居第二軌，只服務真正需要跨紀錄指涉的少數情況，
而那時錨詞只要有鑑別度即可，不必複述整段主旨。

> 順序固定為三問：
> 1. **能不能不用識別碼**（把資訊放進被指涉者本身、用包含或鄰接關係定位）？
> 2. 不行的話，**寫錯一個合法識別碼會怎樣**？
> 3. 會安靜出錯的話，才補冗餘自證，而且**只補到夠鑑別為止**。
>
> 先做第 1 步的價值不只是省字：它讓那一整類錯誤**沒有語法可以表達**，
> 而第 3 步只是讓錯誤變得看得見。

#### 同一晚的第三次：`git add <被忽略的路徑>` 是靜默 no-op

`.gitignore` 寫成**白名單**（先 `*` 全擋、再逐一放行 `*.py`／`*.sh`⋯）是對的設計——
黑名單漏一種是靜默進庫，白名單漏一種只是少收一個檔、看得見。

但它有個副作用：**`git add path/to/ignored.json` 會成功返回、什麼也不做**，
不警告、不非零退出。於是 commit 訊息可以理直氣壯地宣稱「同時落盤了題庫」，
而那個檔從頭到尾不在版本控制裡。實測 2026-08-09 一晚犯三次。

這與 gates.md §A1 那個 `pdf.name.replace("試題","答案")` 是**同一個東西**：
**靜默 no-op 讓「我沒做這件事」偽裝成「這件事做了」。**

判準：**凡是「把東西加進某個集合」的操作，都要回頭確認它真的進去了。**

```bash
git add "$f" && git diff --cached --name-only | grep -qF -- "$f"   || { echo "add 是 no-op（多半被 .gitignore 擋了）：$f" >&2; exit 1; }
```

順帶一條紀律：**跑批中的 staging 題庫本來就不該進 git**（它每小時都在變、且是產物）。
它的保命方式是**盡快併進 `_dev/data/`**（那條路徑才在白名單裡），
不是 `git add -f` 硬塞。看到自己想 `-f`，通常表示該做的是併庫。

##### 更正：訊號本來就在，是我自己把它靜音的

追下去才發現 `git` **本來就會**印「The following paths are ignored by one of your
.gitignore files」，`git add` 與 `git add -A` 都會印。三次沒看到的真因是——
指令尾巴被加了 `2>/dev/null`，用意是消掉「路徑不存在」的雜訊，順手把安全警告一起蓋掉。

**所以這一類失敗有兩個來源，而第二個更常見**：不是工具沒警告，是執行者為了讓輸出乾淨
把警告關掉了。`2>/dev/null`、`|| true`、`-q`、`--quiet` 都是同一個動作。

> 判準：**消雜訊的重導向，只能加在你已經逐條看過那些雜訊之後。**
> 還沒看過就先加 `2>/dev/null`，等於預先同意所有你還不知道的錯誤。
> 真的很吵，就過濾**已知的那幾行**（`grep -v 'known noise'`），不要整條 stderr 丟掉。

這也改變了守衛該放在哪：**放進一個執行者蓋不掉的通道**。專案的作法是 PostToolUse hook
獨立重探（`git check-ignore` ＋ `git ls-files`），不解析指令輸出，所以 `2>/dev/null`
對它無效。

#### 什麼時候該用 hook，什麼時候不該（三條全真才裝）

hook 便宜但會累積，累積到一定量就開始干擾連續工作。判準（2026-08-09，fable 裁決）：

1. **訊號可被執行者在同一次呼叫內抑制**（重導向、旗標、改路徑就能消掉）。
2. **沒有更晚的單一必經入口**能攔到同類失敗（沒有 fail-closed 的 dispatch／publish／
   `--apply` 可以掛）。
3. **零 token 機械判定**（exit code、regex、檔案系統事實就夠，不需語意理解）。

附加規則：**自己擁有的程式碼出的錯，修程式，不包閘。**

拿這三條篩今晚七個實測失敗，只有 `git add` 那一項三條全真；其餘不是有更晚的必經入口
（派工閘、紅隊入口），就是本來就該修在自己的程式裡。**結論是零個新 hook。**

數量上界：**每個工具事件至多一支會擋的 hook，全專案會擋的 hook ≤ 3**；
新裝必須引用至少一次實測失敗，禁止「以防萬一」型；`/loop` 連續運行中誤擋超過每週一次
即降級為入口閘或移除。

> 「模型變聰明就不需要 hook」對一半：會隨智力歸零的是**判斷型** hook
> （官方明列的反模式就是「用 hook 複製模型的決策邏輯」）；不會歸零的是**觀測保證型**——
> **再聰明的模型也讀不到被 `2>/dev/null` 消掉的訊號。智力修不了觀測通道的洞。**

### 推論四：閘門把自己的補救說明吞掉，比擋不下來更難查（2026-08-09）

新寫的 fail-closed 閘門長這樣：

```zsh
echo "✗ 靜態頁落後於題庫，共 $total 個檔：" >&2
printf '%s\n' "$dirty" | head -5 >&2          # ← 這一行
echo "   先 commit 這些檔案再發佈——發佈取的是 HEAD:_dev" >&2
return 1
```

實測擋下來了，但使用者看到的是**一句沒有下文的錯誤**，腳本退出碼 **141**。

成因：`set -eo pipefail` 之下，`head` 讀滿五行就關掉管線 → `printf` 收到 `SIGPIPE`
→ 整條管線回 141 → `set -e` 當場中止函式。**第三行的補救指示根本沒有機會印出來**，
`return 1` 也沒有執行到。閘門擋對了，但它把「接下來該做什麼」連同自己的退出碼一起吞了。

這是靜默 no-op 家族的另一員（前面幾位：`pdf.name.replace()`、
`git add <ignored>`、把 `2>/dev/null` 接在會警告的指令後面）。共同形狀是
**執行者親手消掉了自己需要的訊號**，而消掉之後的畫面跟正常一模一樣。

修法：不要在 `set -eo pipefail` 的閘門裡用 `… | head -n`。用 here-string 迴圈，
順便滿足「不得靜默截斷」——列了幾筆、還有幾筆沒列，都要說出來：

```zsh
local line shown=0 total
total="$(wc -l <<< "$dirty" | tr -d ' ')"
while IFS= read -r line; do
  echo "   $line" >&2; shown=$((shown + 1))
  [ "$shown" -ge 5 ] && { [ "$total" -gt 5 ] && echo "   …另有 $((total - 5)) 個未列出" >&2; break; }
done <<< "$dirty"
```

**驗收要看退出碼，不要只看有沒有擋下來。** `./gate; echo $?` 應該是 1；
是 141／143 就代表中止點不在你以為的那一行。

### 推論五：閘門的樣式若比對得到自己的解釋註解，它就是恆真／恆假的（2026-08-09）

那道跨檔一致性斷言的第一版是：

```python
assert "Disallow: /data/" not in render_robots()
```

它**立刻紅了**——而 `render_robots()` 產出的檔案裡根本沒有那條指令。
命中的是我為了說明「這裡刻意沒有 Disallow」而寫的那段註解。

反過來想更危險：如果當時那段註解沒寫，這道斷言會一路綠燈，而它綠的理由
與它想驗的事情無關。**一道會被自己的說明文字觸發的樣式，也會被別的無關文字放過。**

修法是**先把格式解析乾淨，再比對語意**——robots.txt 的 `#` 之後對爬蟲無效：

```python
rb_rules = [ln.split("#")[0].strip() for ln in rb.splitlines()]
assert not any(r.lower().startswith("disallow") and "/data/" in r for r in rb_rules)
```

**硬規則（與 gates.md §A3.1 的兩側驗證同一條）**：新寫的判定式必須在 **known-good 與
known-bad 兩種輸入各跑一次**，兩次結果不同才算數。

```
known-bad（真的有指令）    → True
known-good（只在註解裡提到）→ False
```

兩次跑出同一個答案的判定式，不管答案是什麼，它驗到的都不是你要的東西。

## §G 門查不到東西時，三種原因長得一模一樣（2026-08-13 實測，藥師上線那輪）

一道門回報「這批我驗不到」，底下可能是三件完全不同的事，而**它們的輸出字串常常
是同一句**。分不開的代價不對稱：判成「資料真的缺」會把成本推給人（回源重抓、
甚至跑一趟公部門），判成「工具沒找到」則只要改幾行程式。

| 真實原因 | 該做什麼 | 那天實際發生的 |
| --- | --- | --- |
| 資料真的不在 | 回源重抓 | —— |
| 工具的定位假設壞了 | 改工具 | `qid.split("_")[1]` 取場次碼。6 科的 qid 是 `113_113030_…` 所以成立，藥師多一段考試名前綴 `pharmacist_101_101030_…`，split[1] 拿到年份 → **整科 13,050 題回報「無答案 PDF」**，而 174 份答案 PDF 就躺在 `_raw/` 裡 |
| 命名隨時間改過 | 補對照表 | 舊卷科目寫「藥劑學（包括生物藥劑學）」、現行寫「藥劑學與生物藥劑學」。**改寫過的名字沒有任何寬鬆比對救得回來**（加後綴的那些反而自己就中了），只能列表 |

三條可操作的規則：

1. **識別碼靠形狀定位，不靠位置。** 場次碼的識別特徵是「六位數」，不是「第二段」。
   位置假設會在下一個命名慣例出現時安靜地錯。
2. **每一種「驗不到」都要有自己的計數欄。** 把「查無試題 PDF」與「無答案 PDF」
   合成一個數字，就是把「改工具」與「回源重抓」合成一個結論。
3. 🔴 **`unverified` 這類欄位要逐一列進 `status` 的判定裡。** 少列一種，
   那種未驗就會被算成通過。

## §H 彙整器不可以把量過的結果降級成「沒跑」

同一輪實測：`verify_answer_key.py` 剛把門 A 驗成「13,050 題全一致」，
接著跑彙整腳本 `gate_report.py`，整筆被覆寫成 `status: "not_run"`——
理由是**彙整腳本自己跑不了門 A**。

一個彙整器用「我沒跑」蓋掉「別人跑過了」，比不寫還糟：它銷毀證據，
而且**銷毀後的樣子與從來沒人跑過完全相同**。

判準：**彙整器對每道門的權威性是有限的，越權的方向只能是保守。**
合併規則寫成「新的是 not_run 而舊的不是 → 保留舊的」，並在保留時留一個
`kept_by` 欄位讓人看得出發生過什麼。否證測試要驗**雙向**：
量測不可被降級、而 not_run 可以被後來的量測取代。

（這與 §缺產物＝未跑 是一體兩面：那條講「沒跑要留得下痕跡」，
這條講「跑過的痕跡不可以被別人擦掉」。）

## §I 衍生物的「新舊」要用內容指紋判，不要用檔案的 commit 判（2026-08-18 實測）

詳解、關聯、裁切圖這類**衍生物**都有同一個問題：它比它所依賴的來源舊了沒有？
最順手的判準是「來源檔的最後 commit 晚於衍生檔的最後 commit」。**那個判準是錯的，
而且它的錯法特別難看見**——它不是漏抓，是**在你做對事的那一刻把帳一起銷掉**。

### 形狀

一個檔的 commit 是**全檔共用的一個時間點**。`explanations.json` 裡有 981 則詳解，
其中 115 則今天重寫過、866 則沒有。只要 commit 這個檔一次，**全部 981 則的時鐘一起歸零**。
於是：

```
merge 115 則   → 閘門：44 則過期   ✅ 誠實
commit         → 閘門：0 則過期    ❌ 那 44 則一個字都沒動
```

第二行不是 bug 造成的，是**判準的定義**造成的。而它出現的時機恰好是「你剛完成一批
修復、心情最好、最不會去質疑綠燈」的那一刻。

### 判準

**每一則衍生物,在生成當下,蓋一枚它所依賴那筆來源的內容指紋**
（只取衍生物真正依賴的欄位，見 gates.md §A3 的欄位清單紀律）。驗證時只跟現況比：

```python
stale = [qid for qid, stamp in stamps.items() if stamp != fingerprint(current[qid])]
```

與任何 commit 無關 ⇒ commit、搬檔、改路徑、rebase 都洗不掉。

**未蓋章的要單獨計數並印出來，不得計入通過**——不知道 ≠ 沒問題（gates.md §A4 同一條）。
指紋會隨著每一批 merge 累積，未蓋章數只會往下走；把它印在報表上，
它就自己變成一條進度條。

### 🔴 蓋章工具的「來歷」參數不可以有預設值

同一輪內踩到的第二個坑，比第一個更值得記：蓋章工具需要知道「未蓋章那些是對著哪一版
來源寫的」。第一版把它預設成「來源檔的最後一個 commit」——**那個值在第一次
merge+commit 之後就變成現況**，於是第二次跑會拿現況幫所有舊則子蓋章，
把時鐘全部歸零。**用這道門的預設值，重建了這道門要擋的病。**

> **一般形式：從可變狀態算出來的預設值不是預設值，是藏起來的參數。**
> 它只在工具還沒被用過的那一刻是對的，而那正是最不需要它的時候。
> 改成必填，並在錯誤訊息裡寫明該怎麼查、以及「要取那批實際生成當時的 commit，
> 不是最新的那個」——錯誤訊息是這條規則唯一會被讀到的地方。

### 它第一次跑就抓到什麼

換成指紋之後第一次跑，數字比預期多一則。那一則被排除在重生成清單之外，理由是
「上一批有它的可用產出」；而上一批整批決定不 merge。**兩個各自正確的決定之間掉出一題**，
舊錨點永遠看不見它——因為它從來不是「某個檔比較舊」，它是「沒有任何一批負責它」。

## §J 判定用一組輸入、動手用另一組，等於那道閘不存在（2026-08-18 實測）

數學重建器裡最貴的一個 bug：`classify()` 用**過濾過**的取字窗判「這條線上方有一個
乾淨的分子」，`resolve()` 卻用另一個 16pt 的**原始窗**去**消耗**字元。

判定說「是分數」，消耗把 16pt 內的整行散文塞進去，於是合成出
`\dfrac{12-14題為題組}{a,b}`；而且那些字被吃掉之後，**下一行的散文從此殘缺**——
一個錯誤同時製造了兩處毀損，其中一處還在別的題目上。

實測規模：19 卷 531 帶裡，「拒收理由為空、會被寫入」的 229 帶有 **78 帶（34%）**
含機檢看得見的毀損，而毀損長相全是「讀起來幾乎像對的」。

> **一般形式：一道閘的防護力，等於它與實際動作之間的距離。**
> 判斷用 A、動手用 B 的時候，A 上的每一道過濾在 B 上都等於沒寫。
> 修法不是把 B 的窗也調成 A 的（那只是把兩份說明書調成一致，下次改一邊照樣分岔），
> 而是**讓判定回傳它所依據的那組東西，動作只能用那一組**。
>
> 這條與 §F′「一道閘讀錯欄位不會報錯」是同一個病的兩面：
> 前者是閘讀了不存在的東西，後者是閘讀對了、但動手的人讀的是別的東西。
> 兩者都不會報錯，都只會一直說沒事。

**自檢要走實際路徑**：若自檢自己組出 up／dn 再餵給 `classify()`，它就檢不到這一類
bug——那正是本案的自檢通過、資料卻毀損 34% 的原因。自檢必須呼叫與生產同一支
「取字 → 判定」的函式。

## §K 硬失敗要挑對例外型別，否則失敗半徑會擴散到整批（2026-08-18 實測）

「未登錄的 PUA 一律中止，不預設不略過」是對的規則，但它原本丟的是 `SystemExit`
——那繼承自 `BaseException`，**穿過呼叫端的 `except Exception`**，於是一顆字殺掉
整個跑批（實測 19 卷有 30 帶因此連跑都沒跑到）。

改成 `ValueError` 之後，仍然是硬失敗、仍然不預設不略過，只是**失敗的半徑從
「整批」縮回「這一題」**，而那一題會帶著具名理由進拒收清單、被人看到。

> 一般形式：「要不要吞掉錯誤」與「這個錯誤會炸掉多大範圍」是**兩個獨立的決定**。
> 前者的答案通常是「不吞」，但那不蘊含後者要選最大值。

## §L 守恆閘擋不住「字還在，但沒人看得懂」（2026-08-18 實測）

重建器的 dry-run 畫面上，`|x-a|≤b` 印成 `x-ab`。看起來像掉了三個字。

實際上一個字都沒掉：`≤`（U+F0A3）、`α`（U+F061）、`β`（U+F062）不在造字譯碼表裡，
於是**原封不動穿過去**——而終端機沒有那些字形，所以它們是**隱形的**。
字元多重集守恆閘當然全過，因為守恆得好好的。

補一道閘就抓出來了：**輸出不得殘留 U+E000–U+F8FF 的任何字元**。

> 一般形式：守恆類的閘門守的是「量」，不是「意義」。一個沒被翻譯的符號、
> 一個掛錯位置的字、一個被誤讀成別的字的造字——這些在多重集上全部合法。
> 每一道守量的閘，都要配一道**守值域**的閘：輸出裡不准出現「我們自己都
> 還沒定義它是什麼」的東西。

這一道也是把不可見變可見的標準手法：**失敗如果沒有外觀，就給它一個外觀。**
未登錄造字在畫面上是空白，在閘門上是一個具名的拒收理由與一串碼位——
後者才有人會去處理。

## §M 渲染器設成「不要拋錯」，就等於把它的錯誤回報關掉（2026-08-18 實測）

前端用 KaTeX 的 auto-render 渲染題幹裡的 `\( … \)`，設定是 `throwOnError: false`
——那是對的選擇：一條壞公式不該讓整頁作答介面爆掉。**但它的代價是：
壞公式會安靜地渲染成一行紅字留在題目裡，而「上線沒出事」與「公式是對的」
在觀測上完全一樣。**

補法是把渲染器**拿到 build 期再跑一次，這次設 `throwOnError: true`**：

```bash
node _build_features/katex_lint.js <exam…>   # 逐條編譯題幹／選項／passage／詳解
```

全站首跑就抓到 5 處正在線上壞掉的公式（`\overparen`、`array` 的 `@{}`／`\cline`／
`\multicolumn`——都是這一版 KaTeX 不支援的巨集）。它們存在多久沒人知道，因為
沒有任何東西會叫。

兩個實作紀律，兩個都踩過：

- **必須用上線的那一份渲染器**（`_dev/web/katex/katex.min.js`），不是另外裝一個。
  版本不同支援的巨集就不同——拿別的版本驗過，證明的是別的網站不會出事。
- UMD 打包的函式庫在 CommonJS 底下走 `module.exports`、**不會掛到 global**。
  只讀 global 的話拿到 `undefined`，而它的症狀是「每一條公式都失敗」——
  看起來像資料全壞，其實是載入方式錯了。兩條路都接住。

> 一般形式：**凡是為了健壯性而吞掉錯誤的地方，都要在別處補一個會出聲的版本。**
> 執行期吞錯是對的（使用者不該因為一條公式看不到題目），但**吞錯的那一刻，
> 你也失去了「這裡有錯」這個訊號**——它必須在別的時間點、用別的設定重新取得。

### 推論：`Array.isArray(x)` 這種型別判斷，false 的意思是「跳過」，不是「有問題」（2026-08-18 實測）

同一個形狀的另一半，而且更難發現，因為這裡連 `throwOnError` 這種可疑的設定都沒有。

前端畫「答題架構」的條件是 `if (Array.isArray(ref.frame) && ref.frame.length)`。
資料有兩種 schema：一科寫成陣列（292 列），四科寫成字串（329 列）。
`Array.isArray` 對字串回傳 false → **整個區塊不被建立**。不是空白、不是報錯，是不存在。
於是 329 列的答題架構在線上消失了好幾個月，而且：

- 沒有 console 錯誤（沒有東西出錯，只是沒有東西發生）。
- 沒有版面破洞（區塊本來就是選擇性的，缺了看起來像「這題沒有」）。
- 資料層全綠（欄位在、內容對、JSON 合法）。

**「沒有顯示」與「沒有資料」在畫面上同形**——這是本檔反覆出現的那個病，換了一件衣服。

判準：**凡是用型別／存在性判斷決定「畫不畫」的地方，都要有一份「渲染器認得哪些形狀」
的清單，並用一道閘檢查「資料的形狀 ⊆ 清單」。** 渲染器多認一種就回來改清單；
資料多出一種而清單沒有，閘門要擋。範例實作：`check_essay_ref.py`。

### 推論二：閘門要窄到「亮起來就代表真的有事」（同日，寫上面那道閘時當場踩到）

那道閘第一版把「渲染器不認得的欄位」一律報出來，結果 `confidence` 與
`needs_verification` 這兩個**刻意不顯示的稽核欄位**讓 621 列各噴兩筆，共 1,242 筆紅燈。

一道永遠紅的閘，兩天內就會被無視——**它的訊號值是零，但它的維護成本不是零**，
而且它會讓「真的出事」那一天長得跟前 30 天一模一樣。
**寬到會誤報的閘比沒有閘更糟。** 新閘上線前先在真實資料上跑一次：
不是為了看它抓到什麼，是為了看它**不該抓的有沒有安靜**。

## §N 不變式帶著它的適用範圍；範圍掉了，規則看起來還是規則（2026-08-18 實測）

專案文件寫著資料檔的不變式：「單行 JSON、無縮排、無尾換行」。我照做，把 `essays.json`
寫回去——**內容全對、格式全錯**：一個改 10 個字串的修正變成 **14,191 行刪除的 diff**。

那條不變式的原文點名的是 `bank.json` 與 `explanations.json`。`essays.json` 不在其中，
而且它**根本沒有統一格式**（實測：四科 `indent=1`、三科單行）。我讀到規則、記住規則、
執行規則，唯一漏掉的是它句子裡的主詞。

同形的前例就在同一個專案裡：「恰 4 選項」是**四選一考科**的不變式，不是全站的——
把它套到五選一的學測卷上，486 題正常題被降級、162 題的 `options[0]` 被併進題幹。

- **寫規則時**：主詞寫進句子裡，不要寫「資料檔一律…」這種省略主詞的句型。
  能列舉就列舉；不能列舉就寫判準（「凡 X 者」）。
- **讀規則時**：套用前先問「這條的主詞包含我手上這個檔嗎」，**去量，不要推定**。
- **機器閘**：真正該擋的不是「用了哪一種格式」，是「**順手把整份檔案重新排版**」。
  所以閘門跟 `git HEAD` 那一版比格式，不挑一種正確格式。反例要雙向都測
  （A→B 與 B→A），否則你只證明了閘門討厭其中一種。

> 一般形式：**一條規則的適用範圍，跟規則本身一樣是規則的一部分。**
> 範圍是最容易在轉述中掉的部分，因為它讀起來像背景，不像指令。

## §O 只報 `fail` 數的閘門，分不出「都對」與「都沒看到」（2026-08-18 實測）

§M 講的是渲染器把錯誤回報關掉；這一則是同一根因的**分母版**：閘門看得見的
樣本數自己會縮，而報表只印分子。

實測：法條錨定包的 `--verify` 三科都印「0 fail」——因為註冊表寫官方全名
「中華民國刑法」、詳解寫俗名「刑法」，**21% 的引用（1,741 筆）從來沒被檢查過**。
補上俗名解析與缺的法規後，看得見的引用 7,205 → 9,292，並立刻冒出 1 筆真 fail
（而且那是解析器的 bug，不是資料的）。

- **閘門的 summary 一定要同時印分母**（看了幾筆），不能只印 fail 數。
- 分母掉下去比 fail 冒出來**更難察覺**，因為它長得像「這批資料很乾淨」。
- 比對法則：把分母跟上一次的數字比，**數字變小要跟 fail 變大一樣醒目**。

完整判準（含冒名者守衛、需求量該往哪一層量、否證怎麼做）在
`reviewer-input-parity.md` §「字面比對的查核器」。

## §P 閘門的回傳值被丟掉，畫面是紅的、行程是綠的（2026-08-19 實測）

「缺產物＝未跑」講的是**產物不存在**；這一則是它的另一個形狀：**產物存在、
判斷正確、訊息也印出來了，只是沒有人接**。

實測（`anchor_pack.py --check`）：延後施行的條文在生效當天，修正日期一個字都不會動，
所以另有一道 `checkCommencement()` 專門看 `effective_date`。它寫好了、邏輯對、
會印 `🔴 延後施行已生效但包更舊，須重建`。接線是這一行：

```python
commencement = reportCommencement(pack, today)   # 回傳值再也沒被用到
...
print("all ... are up to date")
return 0                                          # ← 修正日期全對就回 0
```

**月維護是看 exit code 決定要不要重建的**，所以那道檢查對呼叫它的流程等於沒跑。
人在終端機前會看到紅字，CI／排程不會。

- **判準**：一道閘門的存在證明不是「它會不會印」，是「它的結論走到哪裡」。
  寫完就往上追一層：**誰讀這個回傳值？沒有人讀＝這道閘不存在。**
- 這種洞**不會被 `--selftest` 抓到**，除非測的是接線本身。所以自測要有一條
  斷言回傳值（`report(...) == 2`／`== 0`），而不是只斷言內部分類正確。
- 靜態檢查抓得到的形狀：**被指派卻從未被讀取的區域變數**。凡是變數名叫
  `result`／`status`／`errors` 而後續沒出現，都要當成閘門斷線的候選。

同族：§F、batching-and-measurement-lessons.md §31。

## §Q 一道閘門在某些資料形狀上會當掉，而「當掉」與「沒跑過」同形（2026-08-19 實測）

§P 講回傳值沒人接；這一則更早一步：**閘門根本沒有執行到底**。

實測：門 A3（圖題掛載雙向檢查）的掃描函式寫 `stem + "\n" + passage`。多數考科的
`passage` 是字串，這行一直沒事；學測與會考存成 **list**（多段材料），一跑就
`TypeError`。結果是四道必跑門的第三道，在那兩科（2,338 題）**從來沒有跑過**——
而且沒有任何紀錄會顯示這件事，因為**沒有人會因為一個從不執行的指令收到錯誤訊息**。

修好後第一次掃得動，那兩科立刻報出 19 題「引用圖卻無附件、且仍 `parse:ok`」。

- **判準**：閘門的涵蓋率要按**資料形狀**報，不只按考科報。同一個欄位在不同科可能是
  `str`／`list`／不存在，三種形狀都要有一條自測——不是為了型別安全，是為了讓
  「這科我跑不動」變成一個看得見的事件。
- **跨科的閘門要有一份「跑過哪些科」的產物**。只印本次結果的閘門，分不出
  「這科乾淨」與「這科我從來沒碰過」。
- 一般形式：**閘門的失敗模式有三種——報錯、報空、與從未執行。第三種最貴，
  因為它在任何報表上都不佔一行。**

## §R 掃「缺東西」之前，先掃反方向（2026-08-19 實測）

門 A3 是雙向的（引用了卻沒有檔／有檔卻沒人引用），但實務上大家只跑第一向。

- **順序決定成本**：先掃反方向，工作從「裁圖」降級成「接線」，差一個量級。
- **兩個方向要在同一份報表裡**。分開跑就會像本例一樣：一邊排著裁圖工單，

## §U 🔴 閘門的**層級選址**：閘要放在所有路線的交會點，不是放在其中一條的 runner 裡（2026-08-23 實測）

一道閘的位置，決定它擋得住誰。放錯層級的閘，對走另一條路的人**形同不存在**——
而它在文件上看起來一樣有效。

**實測**：跑批工具鏈有一道「skill 戳記漂移就拒絕開跑」的閘。它的設計寫在
`mkprompt.py` 的註解裡，措辭是「`run_stage.sh` 開跑前比對 hash，skill 比戳記新就拒絕開跑」；
操作卡第 1 行的戳記註解也這樣寫。兩處文件、寫得很具體。

`grep -c skill_ref run_stage.sh` 的結果是 **0**。

它從來沒有被實作過。而且就算實作了也只擋得住一條路：`run_stage.sh` 是 codex 線的 runner，
Claude 線（Workflow／子代理）根本不呼叫它。**兩條路線唯一的交會點是 prompt 產生器**
（兩條路都得先有 prompt），所以閘的正確位置是那裡。

發現它不存在的方式，是有人手動比對了一次 hash——**那正是這道閘本來要取代的動作**。

### 三條可直接照做的規則

1. **先問「有幾條路可以到達這件事」**，再決定閘放哪。答案 ≥2 就找交會點；
   找不到交會點，就每條路各放一道，並讓它們共用同一支判定函式（不是各抄一份）。
2. **繞過開關要綁在值上，不要綁在布林上。** 這道閘的承認機制是
   `SKILL_REF_ACK=<當前hash>`，不是 `SKILL_REF_ACK=1`。差別是：綁值的承認會隨下一次
   改動**自動失效**；布林開關會被第一個人關掉，之後所有人繼承那個關閉狀態，
   而**沒有任何事件會把它打開**。
3. **閘的涵蓋面要跟它守護的東西同尺度。** 上面那個戳記指的是**整份 reference 檔**，
   但只有其中一部分（審查者／撰寫者的站別規則）是操作卡該蒸餾的；同一份檔裡的主控層
   教訓（prefix 衛生、跑批次序、兩臂合併）一改，閘就會響一次假警報。實測第一次觸發
   就是這種：**136 行新增、0 行刪除，六個新節全屬主控層**。
   假警報累積會養出「習慣性繞過」，那比沒有閘更糟——因為帳面上還有一道閘。
   涵蓋面對不齊時的最低要求是：**拒絕訊息要教人怎麼分辨真假警報**
   （印出「去看這段期間多了什麼」的那行指令），不要只說「不符，拒絕」。

> 一般形式：**「這道閘擋得住誰」是可以量的，而且量法很便宜——`grep` 它的名字。**
> 沒 grep 過的閘，你知道的只是它的設計意圖。

## §V 🔴 欄名就是閘門：把「所有候選」和「被否決的」並排回傳，等於沒有閘（2026-08-23 實測）

一支跑批工具跑完生成、跑完紅隊，回傳這樣一個物件：

```js
{ generated: [...所有過 lint 的...],   // 讀起來就是「產品」
  fixes:     [...紅隊判 fix 的...] }   // 另外報一份，從來沒有被扣掉
```

呼叫端要自己做 `generated - fixes`。**沒有人會每次都記得做減法。**
實測：140 則被併進題庫，其中 **69 則是紅隊判 fix 的**。整條路上沒有任何錯誤訊息——
紅隊跑了、裁決產生了、數字都印出來了，只是沒有人把它接上。

**修的不是文件，是欄名與結構**：

```js
{ shipped:      [...],  // 只有這一欄可上線
  held_redteam: [...],  // 判 fix
  unreviewed:   [...],  // 🔴 沒有裁決——與「審過判 pass」在檔案裡長得一樣
  lint_failed:  [...] }
```

第三欄是關鍵。抽查模式下「沒被抽到」是常態，舊版在「這一塊沒有任何一則進紅隊」時
直接把整批當可上線——**而那正是抽查最常發生的情況**。

> 一般形式：**當一個欄位的名字讀起來像「成品」，它就會被當成成品用。**
> 閘門要嘛長在資料結構裡（可上線的只有一個名字叫得出來的欄位），
> 要嘛就不存在——寫在註解裡的減法不是閘門。

## §W 🔴 黑名單式判準會在資料多出一個合法值的那天靜默出錯（2026-08-23 實測）

併庫工具把題目從待校升級為可作答，判準寫的是：

```python
promote = [q for q in rows if bank[q].get("parse") != "ok"]   # 非 ok 就升
```

寫的當下只有兩種狀態（`ok` 與 `review`），所以它是對的。後來多了第三態
`noanswer`（官方從未公布答案、`answer` 欄是空字串、規定維持不可作答），
於是這一行**把 46 題永遠不該可作答的題升成可作答**，前端會拿空字串去比對答案。
沒有任何東西報錯，因為那一行從來沒有錯過——**是世界變了，不是它變了**。

改成白名單，並讓落在白名單外的狀態**印出來**而不是靜默維持原狀：

```python
promote = [q for q in rows if bank[q].get("parse") == "review"]
blocked = sorted({bank[q].get("parse") for q in rows} - {"ok", "review"})
if blocked:
    print(f"  ⚠ 不升級（非 review 的 parse 狀態）：{blocked}")
```

> 判準式：**「不是 X 就做 Y」在列舉型欄位上永遠是定時炸彈。**
> 列舉會長出新值（`gates.md §A4` 那條「不知道要有自己的值」正是在製造新值），
> 而黑名單對新值的預設回答是「做 Y」。白名單的預設回答是「不做」，
> 而不做的代價幾乎總是比較低。

## §X 🔴 報告裡的截斷必須留下痕跡（2026-08-23 實測）

一份閘門報告同時寫了摘要與清單：

```python
{"stale": len(stale), "stale_qids": stale[:20]}
```

於是摘要說「gsat 22 則」而清單只有 20 筆。**同一份 JSON 裡兩個互相矛盾的數字，
而截斷本身沒有留下任何欄位、任何旗標、任何訊息。** 下游程式讀清單，人讀摘要，
兩邊各自都覺得沒問題。

報告是給下游程式讀的，不是給人瀏覽的——要省版面該省的是別的東西。
真的必須截斷時，**截斷的事實本身要是一個欄位**（`"truncated": true, "shown": 20`），
不可以只靠讀者去比對兩個數字。


## §S 偵測器與修復器必須共用同一個模式定義（2026-08-23 實測，同一天兩例）

一道門（偵測器）通常配一支自動修復器。兩者若各自寫一份 pattern，**它們會漂**，
而漂開之後的殘留有一個很難察覺的形狀：**咬得到、卻修不掉。**

看起來像「有幾則比較難，修復器處理不了」——實際上是**一整類永遠修不掉**，
數量固定、每批都出現、每次都被當成長尾扣住。而且**沒有任何東西會報錯**：
門盡責地咬，修復器盡責地跑，兩邊各自的自檢都過。

### 例一：修復器比偵測器窄

偵測器 `WIDE_OP_IN_LATIN` 兩側都容許 `\s*`；產線跑的修復器自己寫了一條
`(?<=[0-9A-Za-z])([全形運算子])(?=[0-9A-Za-z])`，**要求緊貼**。
於是 `A ＜ 0`、`t ＋ b` 這種帶空格的寫法永遠卡在 held。

坑更深一層：那支修復器**寫回後的自檢**問的是「我這條窄 regex 還找不找得到」——
所以它每次都通過。**自檢用了與 bug 相同的假設，於是它驗證的是 bug 本身。**

> 兩條修法，選第一條：
> 1. **修復器委派給偵測器的正規化函式**（一個 pattern，一份定義）。
>    本例中 lint 內部本來就有一支與偵測器共用 regex 的 `normalize_mixed_punct()`，
>    產線卻叫了另一支——**同一個偵測器配了兩個修復器，叫錯了那個。**
> 2. 真的必須兩份實作時，**寫回自檢一律用偵測器的 pattern**，不用自己的。

⚠️ 換掉實作時，被換掉那支的 selftest 就是護欄：它釘住的是**刻意的窄**
（本例中 `：` 被排除，因為三段式的段落標記 `D：BUN` 兩側都是 ASCII，一轉就毀掉格式）。
委派若破壞任何一條，selftest 當場倒。**刻意的窄與疏忽的窄，只有 selftest 分得開。**

### 例二：字母表是開放集合，補特例會有第四次

組合題的「敘述標籤」原本只認天干（甲乙丙丁）。實測 6 則選項是
`['①②','③④','①③','②④']`，詳解逐敘述辨析——**正是這種題該有的寫法**——
卻因標籤不是天干而整批判 `mid-head-bad` ＋ `mid-letters:∅`。

這是同一條教訓的第三次：括號段首 → 天干段首 → 圈數字段首。
前兩次都是**加一個特例**。第三次改成**擴字母表**（天干 ∪ ①–⑩），
因為「組合題的標籤長什麼樣」本來就是開放集合——逐次補特例只會有第四次。

> 判準：同一道門連續被**同一類合法寫法**觸發，先問「我列舉的是不是一個開放集合」。
> 是的話，補特例是在延後問題；該做的是把列舉換成**性質**（這裡是「選項全由標籤構成」）。

### 驗收：擴的是門的視野，不是門的鬆緊

放寬與放行只差一線，而兩者在通過率上長得一樣（都是「fail 少了很多」）。
**每一次放寬都要留一條護欄，並確認它在改前改後都 fail：**

- 例一的護欄：`D：BUN` 段落標記不得被轉（改前改後都不轉）。
- 例二的護欄：詳解漏掉 ④ 仍須 fail（改前改後都 fail）。

🔴 例二的護欄在**舊字母表下是因為 `mid-head-bad` 而 fail**，不是因為 `combo-uncovered`
——**舊的門連「漏了一項敘述」與「認不得段首」都分不出來。**
護欄要看的不只是「有沒有 fail」，還有**fail 的理由對不對**。


## §T 一條沒有任何一處在驗的硬條款，就只是建議（2026-08-23 實測）

生成規格裡有一條「保真條款」，寫得很硬：**改寫前出現過的每一個英文原名，
改寫後都必須至少出現一次**。它是實測換來的（事實保留率 43.4% → 100%），
寫在必經的 prompt 產生器裡，每一塊都逐字送給模型。

一年後回頭查，**整條產線沒有任何一處在驗它**：

| 誰可能驗 | 為什麼沒驗 |
| --- | --- |
| 紅隊 | 審查者的 payload **依設計不含改寫前的版本**（欄位註冊表如此）。它手上沒有原件，無從判斷掉了什麼。 |
| 腳本 | 不存在。那個 43.4%→100% 是一次 A/B 實驗量出來的，**從未變成產線閘**。 |

兩邊各自都合理：紅隊不看原件是為了避免錨定；實驗量完就結案是常態。
**合理與合理之間掉出來的那個洞，沒有名字，也沒有人負責。**

實測代價：兩科 1,414 則改寫，**77 則掉了實質英文原名**（疾病名、量表、學者姓氏、
診斷準則縮寫），其中 **28 則已經上線**。保留率 93.5%，不是規格宣稱的 100%。

> ⚠️ 這個「28」第一版寫成 32。差別的來源值得記：第一版用「`explanations.json` 裡有沒有
> 這一題」判斷是否已上線——**而每一題本來就都有舊詳解，存在性證明不了線上是哪一版。**
> 改成比對內容（線上那份是否等於本次生成產出）才對。同一天內這種錯犯了兩次
> （另一次見 batching-and-measurement.md §21.7 的恆真斷言）：**用存在性回答同一性問題，而存在性檢查總是通過，
> 所以錯的方向永遠是「看起來沒事」。**

### 這個洞是怎麼被發現的：被另一道閘擋下來

不是有人想起來要查。是往紅隊 payload 加欄位時，`parity` 閘回了
`unregistered:old_t`——**一道守著別的東西的閘，順手暴露了這一個。**
> 推論：閘門的價值不只在它擋下的東西，還在它**逼你把隱性約定寫成明文**的那一刻。
> 欄位註冊表真正的產出不是欄位清單，是「這個欄位誰看得到、看不到的話誰是權威」這個**必答題**。

### 三條

1. **每一條硬條款都要指名它的驗證者**，寫在條款旁邊。指不出來，它就不是條款。
   驗證者可以是紅隊、可以是腳本、可以是別的權威——但不可以是空的。
2. **形式決定驗證者。** 「A 的每個 X 都要出現在 B 裡」是集合包含關係——
   確定性、可全跑、零 token。**這種東西送模型審既貴又不可靠，還會錨定。**
   反過來，「這段推論成不成立」機器判不了，那才該送紅隊。
   🔴 先分類條款的形式，再決定誰驗；別預設「重要的就送紅隊」。
3. **審查者拿不到原件時，權威要指名，不可以留空。**
   本例中註冊表最後寫的是：`old_t` 紅隊看不到，保真度由機器閘負責、併庫前扣件——
   與「圖片給不了純文字紅隊，故視覺哨兵是圖面正確性的唯一權威」同構。
   **宣告一個盲區，同時就要宣告誰補上它。**


## §Y 閘門只看一層，以及新閘第一次報紅先驗閘不驗資料（2026-08-23 實測，同一支閘兩天兩例）

`scripts/check_section_ids.py` 是 2026-08-22 因為 `## §24`／`## §25` 一天內撞號兩次才寫的，
regex 只吃 `## `。2026-08-23 稽核發現 batching-and-measurement.md 裡 `### 21.5`、`### 21.6`
各自重複兩次，這支閘回報零重複。**閘只看一層，等於留了一個洞，大小剛好等於它沒管的那一層。**
修法是加第二條 regex，用（母編號、子編號）配對比對。

延伸閘第一次真的跑，回報 explanations-redteam.md 有 `5.2 ×3`。打開一看，三則其實是
`5.2`／`5.2′`／`5.2″`——子正則 `(\d+\.\d+)\b` 把撇號尾碼吃掉了。順手一查，`##` 層原本就有
同一種盲區（`12′`／`12″` 兩者互相隱形，也是零成本閘從沒報過）。

**規則：新閘第一次報紅，是一則待查的主張——既可能是資料真的錯，也可能是閘本身錯；
先開檔驗閘本身，再信資料。** 現在這支閘有 15 條 selftest，含撇號尾碼的邊界案例。

一般化：編號空間的形狀（有幾層、有沒有尾碼記號）要從真實檔案枚舉
（`grep -oh '^#\{2,3\} §\?[0-9A-Z.′″]*' | sort -u`）再寫比對式，不能用假設——
和 §W 是同一種病（黑名單式判準）。

同族：§W、batching-and-measurement.md §21.7（恆真斷言）。

## §Z 表側詞界擋了、圖側沒擋就是規則不對稱，兩種指示詞要一起補（2026-08-19 實測，工單 59→58）

規則：中文指示詞（圖／表）的詞界判準若只套用在其中一種身上，另一種完全沒有防護，
就是規則不對稱——之後同一類假陽性只會在沒防護的那側再中一次。

實測全庫只有 **1 題**：「小康一邊拼圖一邊低聲說」的「圖一」其實來自「拼圖」一詞，
表側早已擋了同型假陽性，圖側卻沒有；補上後工單 59 → 58。量少不代表不用補，
缺了它，下一份題庫必定再中一次。selftest 補一正一反。

一般化：修好一種指示詞的假陽性防護後，要順手檢查同伴指示詞
（表／圖、上表／下表、見圖／如圖…）是不是共用同一套規則、卻只套用在一邊。

同族：gates.md §A3；跟 §AA 同一種病（中文沒有詞界，指示詞被鄰字吃掉），
§AA 有完整的 20 題實測與雙側判準細節，這裡不重複。

## §AA 中文沒有詞界，指示詞的正則要在前後兩側都設防（2026-08-19 實測，工單 89→59）

規則：中文字串沒有空白斷詞，「圖N」「表N」這類指示詞會被前後鄰接的字整個吃掉、
變成別的詞；判準要在指示詞的**前側與後側**都放黑名單，只防一側等於沒防。

實測全庫 **20 題**因此進工單，每題都 `parse:ok`、都答得出來：
「代表一個國家→表一」「發表一段談話→表一」「詢問下表示→下表」
「顯微鏡下表現的特徵→下表」「分別代表甲、乙兩班→表甲」等。
前側被「代／發／報／圖／儀／量／外／年／課…」吃，後側被「情／示／現／達／面／白／明／徵…」吃。
修法：前後各一組「合法鄰接詞」黑名單，兩側都擋；判準沒有變，仍是「有沒有指示詞」，
不是「有沒有出現圖／表這個字」。

selftest 補 6 條真實假陽性（護理／社工／醫師卷各取）＋ 3 條反向 canary
（表一／如下表／見表二仍須命中）；strong 10/10、放行 13/13 全綠。
逐題稽核確認沒有任何真指示詞被誤擋——其中 gsat 111_數學B_10 原本已排進裁圖清單，
差一點去裁一張不存在的圖。

同族：gates.md §A3；跟 §Z 是同一種病的另一種形態（§Z 補的是圖／表兩種指示詞
之間的對稱，這裡補的是同一個指示詞內部前後兩側的對稱）。

## §AB 附件判定要認得「內嵌在題幹裡」的表格，不能只看結構化欄位（2026-08-19 實測，工單 104→89）

規則：`has_attachment()` 只認 `figure`／`table_md` 這幾個欄位，看不見內嵌在題幹裡的
表格（HTML `<table>` 或 markdown 表）；資料其實完整、學生答得出來的題，
會因為欄位盲區被誤判成缺附件、排進裁圖工單。

實測 **16 題**（teacher 14、nursing 2）是「下表為…雙向細目表」後面直接接著內嵌
`<table>`；補上內嵌表格判定後工單 104 → 89（其中 **49 題仍 parse:ok**，
代表本來就答得出來，只是誤標）。

判準有分野，不是一律放行：內嵌表格只滿足「表」的指示詞，滿足不了「圖」——
一題說「下圖」卻附了張表，仍然是殘缺的。selftest 補三條：HTML 表、markdown 表、
以及「內嵌的是表但指示詞是圖」的反例。

同族：gates.md §A3，是 §A3.1（掃描範圍只看 stem、漏了 passage）同一種病的
另一種形態——這次漏的不是欄位，是附件的**存在形式**（結構化 vs 內嵌）。

## §AC 跨考試類型複用定位腳本前，要先驗證錨點格式在新類型上成立（2026-08-19 實測，nursing 10→0）

規則：錨點 regex 沒命中時若靜默回報「沒找到」，看起來會像那些題根本不在卷裡；
跨考試類型（國考／升學）複用同一支定位腳本前，要先確認題號／選項標記的格式一致。

實測：國考卷的題號是獨立一行、沒有句點；升學卷是 `44.` 帶句點。照升學的錨點
regex 去掃三份國考卷，一題都對不到，而且腳本靜默回報零命中——不是報錯，
是報「沒有這幾題」。改對錨點後，nursing **4 題**（2 圖＋1 表）補齊附件，
門 A3 nursing **10 → 0**。

補上的附件都經人工開檔核對：產兒科那張圖 x 方向貼邊，是 image anchor（bbox
取自嵌入影像自己的 rect）造成的正常現象，依 skill 規定貼邊是常態不是裁壞；
精神社區那張表用橫向加總自驗（40+880=920、118+762=880）確認抓對格子。

同族：gates.md §A3，跟 §A3.1（題組圖掛在共用 passage、掃描欄位要跨科目驗證）
是同一種病的姊妹例——那次是「掃描欄位要跨科目驗證」，這次是「錨點格式要跨考試類型驗證」。

## §AD 「同題組有附件」不等於「附件是這題共用的材料」，附件可能是別題的選項圖（2026-08-19 實測）

規則：附件存在且格式合規時，缺圖偵測完全看不見錯掛；改之前要先把「為什麼這樣改」
寫成可檢查的斷言（這題的選項是否為空字串代表圖選項題、那題選項是否為文字），
前提不成立就 REFUSE。

實測：會考_114_社會_43 是圖片選項題（四個空字串選項），四張展品圖本來就是它的
選項，掛著沒錯；_44 是文字選項題，題幹問「圖（十九）…」，卻掛著 43 的選項圖之一——
有圖、格式合規、缺圖偵測不會叫，但學生看到的是別題的答案；_45 同組共用材料原本
空著。裁圖（十九）改掛給 44、45，43 維持原圖不動。

這是「同題組有附件≠那是共用材料」的第二種形態：第一種是把選項圖誤傳播出去
（已寫進 exam-pdf-asset-extractor skill），這次是選項圖**早就**被傳播出去了，
存在性檢查一樣看不出差別。

同族：gates.md §A3——圖→題方向與圖檔去重兩個檢查在這裡都通不過，因為圖檔
存在且格式合規，這是「附件存在性」判準本身的盲區。

## §AE 🔴 資料層的門只問「資料對不對」，沒有一道問「前端讀得到嗎」（2026-08-24 實測；已升級 check_field_readers.py）

藥師 17 題把表格存在 `table_md`，前端 `run.js` 只讀 `q.table`。題幹寫「如下表」、
畫面上沒有表，學生物理上無法作答——**上線數月**，躲過所有既有閘門，因為
`table_md` 是**合法欄位、合法 JSON、內容也正確，只是沒有讀者**。缺陷藏在
「資料正確」與「畫面可見」之間的縫隙，而那條縫沒有任何斷言跨過去。

**規則**：既有的資料層閘門全部只問「這個欄位裡的值對不對」，沒有一道反過來問
「這個欄位有沒有被消費端讀取」。要補的不是更多資料驗證，是一支**欄位讀者清點器**：
逐一比對題庫寫出的欄位集合與前端實際讀取的欄位集合，落差就是候選死欄位。

→ 已升級：`check_field_readers.py`（commit f78ba2b）。豁免清單只准列**具體欄位名**、
每筆附理由，**不准萬用字元或前綴比對**——否則下一個新欄位自動落入豁免範圍，
閘門退化成永遠會過（同族：§W 黑名單式判準）。

首跑順帶挖出一組休眠矛盾：gsat 47／cap 21 筆的 `render` 值與 figure/table 實況對不上，
前端不讀 `render` 所以畫面沒壞，**但只要有人接上去，那 68 題的圖就會被藏起來**——
同一種缺陷，還沒發作。

## §AF 關鍵詞驅動的閘，抓不到隱性依賴（2026-08-24 實測）

`detect_orphan_figref.py` 靠「下圖／如圖／圖中」這類觸發詞判斷題目是否指涉圖表。
實測藥師 11 筆「圖缺失」漏網，**9 筆題幹一個觸發詞都沒有**：

- 「由藥品血漿中濃度—時間關係圖…」——有「圖」字，但在複合詞裡，詞表只列單詞；
- 「下列化合物①-④具有何種作用？」——指涉的是畫出來的編號化合物，沒有「圖」字；
- 「在化合物 ␣ 的 1H NMR 圖譜中，劃底線之氫訊號…」——化合物本身不見了，
  「劃底線」的標記在純文字裡根本不存在；
- 「本藥物的代謝不包括：」搭配選項 `['①','②','③','④']`——**選項全是純圈號**。

**規則**：關鍵詞表是「已經想到的說法」的清單，而缺陷的說法是開放集合，
詞表永遠追不完。要補的是**結構訊號**（選項全為符號、指涉編號但本文無該編號、
懸空指涉無前文），不是更長的詞表。

→ 本輪主線的第一個實例（詳見 §AK）：`detect_orphan_figref` 用**詞表**定義
「這題有沒有指涉圖」，而真實缺陷的判準是**結構**——兩者定義在不同的地方，
詞表擴到多長都追不上結構訊號。

**收尾（2026-08-24 round 3 續）**：上面 4 個例子逐一核對後分兩類，不是一次性
「詞表補長就好」。①-④ 圈號範圍、全圈號選項——**維持結構訊號**，留在
`detect_broken_structure_q.check_implicit_figure`，沒有搬回這裡；NMR 那題的
「化合物 ␣」是**內容本身消失**，跟這支要抓的「文字指涉了圖但沒附件」不是同一
件事，也沒有動。真正屬於「詞表遺漏」的只有「關係圖」這一個裸複合詞，和後來
另外發現的一種——PDF 斷行把「如下圖」拆成「如下 圖」，指示詞被空白腰斬——
這兩個補回 `detect_orphan_figref.py`，但**壓成 weak 分級**（列管、不自動降級），
因為複合詞與空白拼接都有肉眼判斷才分得出的假陽性風險，跟 STRONG 那種「文字明講
了指示詞」的確定性不對等。空白拆散那支正規化邏輯本身**用 import**，不是抄一份
（`collapse_narrow_split` 從 `detect_broken_structure_q.py` 去底線公開），這樣
兩支往後只有一份判準會漂移。dry-run 全站掃過，pharmacist 命中數與本輪稽核時
記下的「11 筆」吻合，逐筆讀了原文，9 筆全是真的濃度—時間關係圖題。

## §AG `parse:'ok'` 對結構式選項題有系統性偽陰性（2026-08-24 實測）

四選一考科的不變式是「恰 4 個選項」。壓平的化學結構式**確實是 4 個選項**，
所以 `parse` 判 `ok`：

```
opts: ['HO O OH', 'O OEt O C O C H H N N N N C CH3 C CH3 EtO O EtO O O', 'OH', ...]
```

**閘在驗結構（選項數對不對），壞的是內容（選項本身能不能讀）。** 而
`mkchunks` 只挑 `parse:'ok'` 送生成，這些題會拿到一則「解釋一道無法作答的題」的
詳解——讀起來還很流暢，因為模型會繞過它看不懂的部分繼續寫。

**規則**：`parse:'ok'` 這個不變式本身沒有錯，錯在把它當成「這題可以生成」的
充分條件用。結構有效（選項數對）與內容有效（選項可讀）是兩件事，閘只驗了前者。

## §AH 同一條教訓修在下游，沒有往上游推（2026-08-24 實測）

`mkfix.py:86` 的 `prev` 觸發條件是 `CARRY_OVER.search(stem) or len(stem) < 40`，
docstring 寫明理由：「原 `CARRY_OVER` 只認字面『承上題』，但 `106080_醫五_44`
『下列何者是最合適的處理方法？』整句沒有那三個字，臨床敘述在前一題——紅隊為此
開了 3 則 `input_gap`。」

**同一條教訓，`mkchunks.py` 沒有**——而 `mkfix` 正是 `from mkchunks import CARRY_OVER`，
修的人碰過那個檔，卻只在自己這一站加了 fallback，沒把它推回定義處。於是修復站
看得到上下文，**生成站看不到**，而生成站才是第一手寫詳解的地方。

**實測**（本輪 14 筆 payload gap）：

```
現行 CARRY_OVER               → 0/14
mkfix 現成的 len(stem)<40 判準 → 11/14
len(stem)<50                  → 12/14
```

漏掉的 2 筆：「王先生使用的藥品…」（82 字，訊號是**出現人名卻無前文介紹**）、
以及一筆 `prev` 也幫不上忙的（表格欄位錯位，見 reviewer-input-parity.md §12）。

**代價**：門檻 40 會讓全庫 7,681/13,050（59%）附上前 3 題題幹，約多 200–400
token/題；一批 698 題約多 20 萬 token。相對於「模型對著缺口硬寫」的代價，
這是便宜的保險。

**規則**：在下游補的 fallback，是上游缺陷的**證據**，不是它的**解法**。補在
下游只保護了下游那一站，缺陷本身還在上游，上游的其他消費者仍然裸奔。加下游
fallback 時要多問一句「這個判準該不該回到定義處」——若答案是該，就不要只加在
自己這裡。

→ 本輪主線的第二個實例（詳見 §AK）：判準（`CARRY_OVER`／`len(stem)<40`）
定義在 `mkfix.py`，消費它的 `mkchunks.py` 卻沒有引用，各走各的。

## §AI 產線兩端各自維護契約，而沒有任何東西比對它們（2026-08-24 實測）

送分題（`answer=='#'`）的詳解，生成端與閘門端的要求互斥：

| | `mkprompt.GEN0FREE_TASK`（生成） | `build_free.lint_free`（閘門） |
|---|---|---|
| 開頭 | `正解：本題經考選部公告一律給分，作答任一選項皆得分。` | 必須 `startswith('本題經考選部公告一律給分。')` |
| 結構 | 三段式、四選項各一段、末段考點 | — |
| 長度 | 未限 | 110–300 字 |

照 prompt 寫，`startswith` 永遠失敗；六段式也不可能壓進 300 字。實測：本輪照
`gen0free` 生成 63 則藥師送分題，`expl_lint` **0/63 通過**。線上現況佐證閘門端
才是多數（合閘率 58–85%），但平均字數 134–401 普遍超過 300 上限。

🔴 LOOP_PLAN L16 掛著的「237 則送分題用選擇題契約寫」很可能不是 237 次個別
失誤，而是這一個矛盾的 237 個實例。把系統性矛盾記成一堆個案，會讓人一則一則
去修，而每修完一則、下一次生成又會製造新的。

**規則**：同一份契約寫在兩個地方，就會分岔，而且分岔沒有任何東西會報錯——
生成端照自己那份產出、閘門端照自己那份擋，兩邊都「正常運作」。契約只能有一個
正本，另一端**引用**它而不是複述它（`build_free_gate.py` 已經是這個形狀——它
刻意只做接線、判定邏輯全在 `build_free`；但 `mkprompt` 的 prompt 文字沒有走這條
路，是手抄的）。

→ 本輪主線的第三個實例（詳見 §AK）。

## §AJ 涵蓋式斷言對被涵蓋的方向是瞎的（2026-08-24 實測）

`merge_stage.py` 的驗收斷言是 `assert parse in ("ok", "noanswer")`。`noanswer`
被誤升成 `"ok"` 之後，`"ok" in ("ok", "noanswer")` **仍為真**——斷言涵蓋了它
本該擋下的那個結果。

**規則**：斷言寫成「值屬於某集合」時，集合裡的**任何一個成員**都能讓它通過，
包括「錯誤地變成了另一個合法值」。要抓「不該變的變了」，斷言必須是**逐項比對
前後**（先存 before，再比對「該變的變了、不該變的一字未動」），不是「變完之後
看起來合不合法」。

**配套實測**：同一個 bug 在 2026-08-23 的 commit `8008951` 修過一次——訊息寫著
「已回滾、讀回驗證、50 題全回 `noanswer`」，聽起來很紮實，但它**只改了判準與
斷言，沒動寫入迴圈**。判準與執行分兩處，於是修了判準以為修完了。

→ 本輪主線的第四個實例（詳見 §AK），同時也是「只量已送範圍」姊妹命題的一個
實例（詳見 §AL）——一個涵蓋式斷言只驗了「結果落在合法集合裡」，驗不到「結果
落在合法集合裡的哪個成員」，而缺陷剛好躲在後者。

## §AK 🔴【總論】判準與執行寫在兩個地方，就會分岔；而分岔不會報錯（2026-08-24，8 個確認實例，全數結清）

本輪 26 條教訓裡有 8 條確認屬於同一個結構性問題：

> **判準與執行寫在兩個地方，就會分岔；而分岔不會報錯。**

因為兩邊各自「正常運作」——各自對著自己那份定義跑，各自的自檢都會過，
唯一看得出分岔的地方是把兩份定義並排讀。這與 §W（黑名單式判準）是近親但不同
病：§W 是判準本身的形狀有洞，這裡是**同一個判準被抄了兩份**，洞出在抄本之間。

確認實例（本輪，8/8 已結清）：

- **detect_orphan_figref 的詞表 vs 真實缺圖的結構訊號**——見 §AF；最後關閉，改用
  import 收成一份，不是把兩份判準合併。
- **mkfix.py 的 CARRY_OVER fallback vs mkchunks.py 沒有**——見 §AH。
- **mkprompt.GEN0FREE_TASK（生成契約） vs build_free.lint_free（閘門契約）**——見 §AI。
- **merge_stage.py 的判準（parse 是否合法） vs 它的寫入迴圈（parse 有沒有真的被擋）**——見 §AJ。
- **操作卡的黑名單詞 vs 模型實際的用詞分佈**——見 explanations-redteam-lessons.md §24。
- **我手寫的修復站規格 vs `mkprompt.py` 內嵌的操作卡正本**——見 explanations-redteam-lessons.md §30。
- **`expl_lint` 的免責詞黑名單 vs 實際洩漏**——71 則只抓到 4 則，補寬後又被插詞規避。
- **`fix_punct_width` 的「兩側都中文」判準 vs 混合語境**——中文↔拉丁交界漏 42 則。

**配套**：發現任何「規則 / 契約 / 判準」以兩份獨立文字或程式碼存在時，先問
「這兩份會不會走到不同的更新節奏」；答案是會，就把其中一份改成**引用**另一份
（`build_free_gate.py` 只接線、判定邏輯全在 `build_free` 是這個形狀的範例），
不要讓兩份各自維護。

**唯一的例外要留路標，不要默默合併**：detect_orphan_figref 這格沒有把兩份判準
整個合併，因為安全等級不對稱——一份可以 `--apply` 自動改資料，另一份連
`confirmed` 級都自稱「不建議直接用於排除」。合併會把後者較弱的把握度誤當成
前者的確定性。分岔不一定要消滅，但沒消滅的那一半要有註解說「這裡刻意不做」，
否則下一個人會把它當成沒做完，動手合併，反而把風險等級搞混。

## §AL 【總論】只量「已送範圍內」的指標，對「範圍選錯了」是瞎的（2026-08-24）

姊妹命題，與 §AK 同輪浮現、同一個病灶的另一面：

> **一個只量「已送範圍內」的指標，對「範圍選錯了」是瞎的。**

已確認的實例：

- **`merge_stage.py` 的涵蓋式斷言**——只驗結果落在合法集合裡，驗不到集合裡的
  哪一個成員；見 §AJ。
- **段落級修復的兩個招牌數字**——「附帶損害 0/454」只量有沒有動到不該動的段落，
  「命中 225/271」只量送去的段落有沒有改，兩者都量不到「該修的段落有沒有被
  送進待修範圍」；見 explanations-redteam-lessons.md §13.1（含三個實例的下游損害）。

**配套**：報一個「範圍內達成率」數字時，要同時回答「範圍本身是怎麼選出來的、
選錯的代價多大」，否則這個數字只證明了「已經知道要看的地方沒問題」，對「根本
沒被列入待看清單」的缺陷永遠是 100% 通過。

## §AM 【總論】防禦只覆蓋防禦者已經想到的範圍，覆蓋不到被防禦對象的真實範圍（2026-08-24）

四個節點，各自獨立實測，同一個家族：§W（黑名單式判準對新合法值靜默出錯）、
§T（沒有驗證者的硬條款只是建議）、explanations-redteam-lessons.md §24
（字串黑名單只買得到換一個套語）、explanations-redteam-lessons.md §27
（靠提醒維持的格式規則會週期性失效）。**不合併**——四者的作用域不同，合併
會抹掉它們各自的細節；這裡只串共同機制，個別實例仍以各自的節為準。

**共同機制**：每一個防禦手段（黑名單、驗證者、禁詞表、口頭提醒）的覆蓋範圍，
都是**防禦者事先想到、事先寫下的範圍**，而不是**被防禦對象的真實範圍**。
兩個範圍不相等時，落差不會在防禦機制內部被看見——因為防禦機制永遠只對著自己
已知的清單檢查，清單外的東西對它而言不存在，不是「檢查了但沒抓到」，是
「根本沒被拿去檢查」。

**四個節點是這個機制的四種失效形態，差異在「落差是怎麼長出來的」**：

| 節 | 防禦對象 | 落差怎麼長出來 | 失效的時間性質 |
|---|---|---|---|
| §W | 資料的列舉值 | 世界後來多了一個新的合法狀態 | **時間漂移**——寫規則的當下是對的，後來變錯 |
| explanations-redteam-lessons.md §24 | 模型的用詞選擇 | 模型換一種沒被禁的說法 | **即時繞過**——不必等時間過去，規則一存在就有活的對手在躲它 |
| explanations-redteam-lessons.md §27 | 格式契約有沒有落實 | 防禦手段本身是「人記得要在派工時提醒」，換一個代理、換一次派工就重置 | **防禦手段自己會過期**——不是清單漏了誰，是選錯了防禦要放在哪一層（口頭提醒 vs 寫進工具的自檢） |
| §T | 條款有沒有被驗證 | 沒有人寫下「這條由誰驗」 | **覆蓋率的極限情況（＝0%）**——不是清單覆蓋不全，是清單根本不存在 |

**配套**：發現一個防禦手段是「列舉清單」「黑名單」「口頭提醒」這三種形狀之一
時，先問一句——**這個清單的範圍是誰定義的？是被防禦對象自己的真實範圍，還是
防禦者已經想到的範圍？** 如果答案是後者，這個防禦遲早會被範圍外的東西繞過去，
而繞過去的那一刻不會有任何警報，因為警報本來就只長在清單裡面。三個可行方向
（依防禦對象性質選一個，不是三選一都要做）：

1. **列舉型資料 → 白名單取代黑名單**（§W 的修法），讓「不在清單裡」變成
   預設攔下，而不是預設放行。
2. **開放型輸出（用詞、寫法）→ 分佈約束取代字串黑名單**
   （explanations-redteam-lessons.md §24 的修法），規則寫成「任何單一形態的
   佔比 < 門檻」，而不是列舉已經犯過的形態。
3. **格式契約 → 寫檔前自檢取代派工時提醒**
   （explanations-redteam-lessons.md §27 的配套方向，尚未實作），把驗證從
   「每次派工要記得講」搬進「產物落地前的工具層檢查」。
4. **任何條款，先確認它有沒有落在上面三種之一，還是根本沒有驗證者**（§T）——
   沒有驗證者的條款，連「防禦範圍不對」這個問題都輪不到問，先補一個驗證者。

## §AN 做完卻沒有合併的工作，是完全隱形的——沒有任何一道閘看得見它（2026-08-24 實測）

**症狀**：例行清查時發現一個沒合併的 worktree `claude/bold-yonath-2e2dae`，
commit 日期 8/18，領先 `main` 1 個 commit、落後 201 個。它修的是一個**已經在線上
的真缺陷**：藥師 17 題把表格存在 `table_md`，而前端只讀 `q.table`，於是那 17 題的
表格在網站上完全不顯示。修法在 8/18 就寫好了，然後躺了六天沒有人知道。

**為什麼沒有任何東西報錯**：所有既有的閘都是**對著 `main` 的內容**檢查的——
資料驗證、lint、發佈前掃描，每一道問的都是「現在 `main` 裡的東西對不對」。
一個修法只要沒有進 `main`，對這些閘來說**它從來不存在**，不是「檢查了但沒過」，
是根本沒有被拿去檢查。同時「線上有缺陷」這件事也不會叫——缺陷閘看的是資料，
資料裡 `table_md` 欄位好端端地存在、值也正確，只是沒有讀者。（欄位無讀者這條
獨立成 §AE，兩者疊在一起才讓它活了六天。）

**這是 §AM 的一個極端形態**：那裡講「防禦只覆蓋防禦者想到的範圍」，這裡的範圍
落差不在清單內容，而在**檢查的定位點**——所有閘都站在 `main` 上往內看，沒有一道
站在 `main` 外面往回看。落差是一整個維度，不是清單裡漏了幾項。

**閘門（已實作於本專案 runbook 的 CP2）**：每輪開工的狀態檢查，除了 `git status`
與 `git log`，必須加上**兩條往外看的指令**：

```bash
git worktree list          # 有沒有還活著的工作樹
git branch --no-merged     # 有沒有做完卻沒合併的分支
```

零成本、零 token。判準是**任何一條有輸出就要當場處置**（合併、或明確作廢並刪除
分支），不得留著「之後再看」——「之後」正是這 201 個 commit 的落差長出來的地方。

**一般形式**：問「我的檢查站在哪裡」和問「我的檢查看什麼」一樣重要。
所有檢查都站在同一個點上時，那個點以外的整個空間是零覆蓋，而零覆蓋不會發警報。

## §AR 官方送分符號可能蓋住真正的多答規則——閘 A 只讀了半份文件

`pharmacist_105_105100_P3..._3_04` 的官方答案表格印的是「＃」（一律送分），
而**同一份 PDF 表格外的備註行**卻寫「第4題答Ａ、Ｂ給分」——這是**多答皆給分**
（只有 A、B 算對，答 C、D 仍算錯），跟「一律送分」（怎麼答都對）判分規則相反。
`verify_answer_key.answers_of()` 只呼叫 `find_tables()` 抽表格，從不解析表格外的
自由文字，於是這題從入庫那天起就被表格的表面符號吞成了 `free`，而備註裡真正的
規則沒有任何程式讀過。

這是 §A4（「我不知道」與任何合法值同形）的變體，但更隱蔽一層：不是「讀不出來」
偽裝成合法值，是**只讀了證據的一部分就下結論**，而那一部分的字面（＃）恰好也是
一個合法值，兩種病在下游看起來一模一樣。

判準：`is_footnote_multi(q, official)`——`official=="#"` 且 bank 已標
`answer_status:"multi"`＋查證過的 `accept`，算獨立一類（「表列送分＋備註多答」），
不強算一致（會蓋掉表格字面確實是＃這件事）、不強算不一致（會把查證過的資料錯判
成壞資料）。`answer` 欄要真的寫實際查證出的字母（不能留著 `#`，`answer_status.classify()`
的分支順序讓 `answer=="#"` 永遠先落 `free`，多標的 `multi` 下次被 `answer_status.py`
recompute 就會被吃回去）；`accept` 陣列比照既有的 `multi` 慣例（social-worker／teacher
共 39 則前例），只放實際可選的字母，不要為了湊表格字面把 `#` 也塞進去——那個陣列
之後會被前端拿來判學生答案對不對，混進非選項符號會做出真的判分錯誤。

🔴 **只查過這 1 則，量體完全未知。** pharmacist 還有 154 則 `free`，其他科也有
類似「表格＋備註」兩截式版面的官方答案 PDF。這不是本輪能收斂的範圍，已留一則
具名的系統性稽核工單（`LOOP_PLAN.md` §0 N7）——把「還有多少」的量測跟「這一則怎麼修」
的方法分開兩件事來記，量測沒做完不代表方法沒有結案。

## §AS 教訓寫回閘自己被 git 的動態縮寫長度整了——「已認領」會隨 repo 長大集體過期

推公開站前重跑 `lesson_gate.sh` 確認乾淨（前一刻才印過「✅ 已逐筆結清」），中間只多
commit 了一批機械重生的靜態頁（`chore:`，不改任何判斷邏輯），**同一道閘門立刻回報
一大批「未結清」**——名單裡包含幾分鐘前才剛被正確認領的 commit，也包含好幾輪之前、
早就 `lesson-of:` 認領完畢的舊 commit，一次性全部「過期」。

**根因**：`git log --format=%h` 給的是**當下**最短唯一碼，長度會隨 repo 裡的物件數
變動——多 commit 幾筆，之前 7 碼就唯一的 prefix，可能就要 8 碼才夠唯一。而
`lesson-of: <sha>` 這類 trailer 把縮寫**寫死**在歷史裡的那一刻，用的是**當時**的
最短長度。閘門原本的比對是「現查的 `%h` 去對歷史裡寫死的短碼，抓字首」，這個方向
的前提是「現查的一定比較短或一樣短」——**多 commit 一輪就可能反過來**，於是比對
從一個方向徹底停止成立，而且是**集體、無預警地**同時失效，不是漸進劣化。

這與 §AR 是同一個更高一層的形狀：**判準依賴一個會隨時間改變意義的量**（那裡是
「官方表格的字面」，這裡是「git 縮寫的長度」），而依賴它的程式碼在寫下的當下完全
正確、測試也全過——直到外部條件變了。

判準：**任何要跨時間比對的 git hash，一律正規化成 40 碼全長**（`git rev-parse
--verify -q <短碼>`）再比，不要在缩寫層次做字首比對。`git rev-parse` 對任何長度的
合法唯一縮寫都能解回全長，這步驟本身不受 repo 大小影響——一次正規化，永遠不會
再因為 repo 長大而重新壞掉。

selftest 加的否證案例**不是**靠讓測試 repo 長到觸發真正的長度變化（那樣脆弱又慢），
而是**直接寫一個比目前 `%h` 還短的縮寫**去模擬「這筆是 repo 還小時認領的」，
證明修法後任何長度的合法縮寫都解得回來——這樣測的是不變式本身，不依賴巧合的
repo 大小時機。

🔴 **這道閘擋住的正是它自己守護的那件事：發佈前的品質關卡。** 若沒有在推送前
重跑一次（而是信任幾分鐘前的結果），這個 bug 會在下一次真正需要它擋東西時安靜地
把所有債務判成「已清」——一個原本該擋的閘，因為自己的內部比對邏輯過期，變成
永遠開門。這正是「警告的機制本身要先被信任，而信任的前提是它測過會不會突然失靈」。

## §AT §AR 的規模驗證：footnote 不只「單一字母」一種形狀，還有全／半冪集合的
組合式送分（2026-08-25，N7 系統性複查，229 列跨 5 科）

§AR 只查過 1 則（`pharmacist_105_105100_P3..._3_04`），當時明講「量體完全未知」
並留了系統性稽核工單。這次全面複查 5 科官方答案 PDF 的「＃見備註」列，把 §AR
的判準套到量體上，發現備註欄實際上有 **3 種形狀**，而不是 §AR 原案例的 1 種：

1. 備註只點名**單一字母**（27 列）→ 直接算成官方答案，`answer` 改寫成那個字母。
2. 備註列出**平鋪的字母清單**（如「答Ａ、Ｂ給分」「答Ａ或Ｂ者均給分」，99 列）→
   `answer_status:"multi"`，`accept` 放入列出的每個字母。
3. 備註窮舉**冪集合組合**（如「答Ａ或Ｂ或Ｄ或ＡＢ或ＡＤ或ＢＤ或ＡＢＤ者均給分」，
   103 列，是三種形狀裡數量最大的一種）→ 同樣 `multi`，但 `accept` 要把單字母與
   組合 token（`"AB"`／`"AD"`…）**逐一都收進去**，不能只收單字母、丟掉組合 token，
   也不能反過來只收組合、漏掉單字母（備註原文兩種都平等列出，判分語意也平等）。

第 3 種形狀在套用前**沒有直接假設安全**：先讀前端 `grading.js` 的
`sortLetters`／`isCorrectPick`／`acceptListOf` 確認 `accept` 是整串比對、與順序
無關，再對照社工科既有 35 列同形寫法的既有前例（`fix_sw_official_notes.py`
先例），兩邊判準一致才動筆——**新形狀套用一個既有機制前，要先讀那個機制的原始
實作，不能只憑「看起來像」就類推**。

判準延伸：**`is_footnote_multi()` 的備註解析不能只認「單一字母」這一種正規表達式
形狀，備註原文本身可能是任意長度的字母組合枚舉**——解析器要能吃「一個或多個字母
token，中間用頓號／或字分隔，token 本身可能是單字母也可能是多字母組合」，而不是
寫死成「抓一個字母」。§AR 留下的「量體未知」到這裡才真正封閉：229/229，橫跨
pharmacist／clinical／counseling／nursing／cpa 五科，含 1 筆官方字母本身已過期
需訂正的例外。

## §AV Gate A 只驗答案字母，驗不到「字母沒錯、字母底下的選項文字被調換」
（2026-08-25，N13：`會考_113_數學_9`）

Gate A（答案配對全驗）逐題核對 `answer` 欄的字母是否等於官方答案鍵，`會考_113_
數學_9` 的 `answer:"C"` 跟官方答案鍵完全吻合，Gate A 判過。但官方 PDF 逐字核對
後發現，**站上 `options[2]`／`options[3]` 這兩則選項文字本身被對調**：官方 C 選項
是「甲正確，乙錯誤」、D 選項是「甲錯誤，乙正確」，站上兩則文字剛好互換位置——
`answer:"C"` 字母沒有錯，錯的是「C 這個字母底下掛的那段文字」，學生選 C 看到的
會是官方 D 選項的敘述。這個缺陷 Gate A **結構性地看不到**：它比對的對象是字母，
不是字母底下的文字，字母比對兩邊都是 C、逐題全過，沒有任何訊號會被觸發。

連鎖效應比缺陷本身更貴：既有詳解（clean-room 生成）是根據站上（錯置的）選項文字
寫的，於是詳解本身邏輯自洽、內部找不到矛盾，卻整段建立在錯的選項文字上——**修
資料一定要連帶檢查詳解**（既有紀律，見「修題必檢詳解」），這裡是它的一個具體
反例：詳解看起來完全正常，正常到光讀詳解本身找不到任何可疑之處，只有回頭比對
選項文字跟原始 PDF 才抓得到。

判準：**Gate A 的涵蓋範圍要明講止於「字母」**，不能誤以為「答案配對全驗」等於
「這題的作答資料都驗過了」。要抓這一類缺陷，需要獨立於答案字母之外的**選項文字
本身**對官方 PDF 逐字核對——這是量體全然未知的一類新稽核（本次只抓到 1 例，
起因是人工複查一批「兩個敘述句判斷」題型時順手發現，不是任何既有閘觸發的）。
已對 cap／gsat／ast 三庫用 4 種互補偵測法（含一支 `difflib`-based 鏡像欄位偵測器
專門抓「同一組選項文字互換位置」這個形狀）掃過「兩敘述句判斷」題型（26 題候選），
本次未擴大到全部題型；量體與是否要擴大稽核範圍留給下一輪／使用者裁決。

## §AW 本機 `grep` 已被 ugrep 取代；巢狀 shell 裡它會靜默截斷長 UTF-8 匹配，

（同樣帶中文、格式完全相同）正常過關，一開始完全看不出規律。

**根因分兩層，缺一不可才會觸發**：

1. **本機 `/usr/bin/grep` 不是系統原生的 BSD grep，是被換成 ugrep 7.8.4 的
   實體檔案**（`grep --version` 印的是 `ugrep`，不是 alias、`which`／`type`
   查不出來——它就是那個路徑上的真實二進位檔）。`exam-pdf-asset-extractor`
   skill 早就記過這件事，但原本以為它只影響「預設跳過隱藏檔／遵守
   `.gitignore`」，這次踩到的是完全不同、更隱蔽的另一個壞法。
2. **ugrep 在「巢狀執行情境」（`while read < <(cmd)`、或深一層的函式呼叫）裡，
   對 `grep -oE 'PREFIX:[[:space:]]*[0-9a-f]{7,40}[^\n]*'` 這種「短 ASCII
   前綴＋長 UTF-8 尾端」的匹配，串流裡第一筆命中會在固定字元位置被硬斷**——
   實測 `b0642dc2 ~audit_materialized_inputs 推廣~ 重複命名腳本的覆蓋率`
   在英文單字中間（`materialized_i` 之後）整段消失，斷點不落在任何標點或
   多位元組字元邊界上，肉眼完全看不出是哪裡出的錯。**同一條指令在真正的
   頂層（不巢狀）跑、或改用 `perl`／讀已存檔的靜態檔案，三者都不會重現**——
   已縮小到「ugrep＋巢狀＋這個正規表達式形狀」的組合，不是 `read`、不是
   zsh、也不是本檔的迴圈邏輯。

**為什麼這個坑特別貴**：受害的那一筆 `no-lesson-for` 格式、內容、錨詞全部
正確，人工核對只會看見「明明寫對了，閘門卻說沒寫」，直覺反應是懷疑自己的
格式或懷疑閘門的比對邏輯（§AS 剛好才修過一個閘門自己的 bug，很容易先往
那個方向查）——但這次真正壞掉的是**閘門呼叫的外部工具**，不是閘門的判斷
邏輯本身。判準要往前推一步：**若一段字串「肉眼比對逐字正確」卻仍被判失敗，
下一步不是重看比對邏輯，是重看擷取這段字串的那一行指令有沒有可能被腰斬**
——尤其當受害的行有「長 UTF-8 內容」而其他行沒有，或受害的行剛好是輸出
串流裡最先出現的那一筆。

**修法**：`grep -oE` 換成 `perl -nle 'print $1 if /PATTERN/'` 做同樣的
「找到＋擷取」，一次到位不再依賴 grep 的匹配-输出管線。只換掉會壞的那一處
（長 UTF-8 尾端的擷取）；同檔案裡另一段 `grep -oE` 只擷取純 ASCII 的 40 碼
十六進位雜湊，同樣的巢狀測試沒有重現，維持原樣、不擴大變動面——**修法要
對齊根因的範圍，不是看到一個工具壞了就把它在全檔的每一處都換掉**。

通則：**任何 shell 腳本若假設 `grep` 是熟悉的 BSD／GNU 行為，這個假設在
本機不成立**——`grep` 這個名字現在指向 ugrep，它的匹配輸出在某些條件組合
下與傳統 grep 不同形；凡是「肉眼比對完全正確卻仍判失敗」的詭異案例，都該
把「擷取這段內容的工具本身」列入嫌疑，不要預設工具永遠忠實。

## §AX 零 token 掃描的「沒中標」只證明「沒有這個特定症狀」，證明不了「沒事」
（2026-08-28，N7 紅隊全查，cpa 那 1 題實測反例）

N7（229 題答案已從無條件送分訂正為具體字母集）的詳解幾乎全帶「本題經考選部
公告一律給分」舊樣板句。跑一支零 token 腳本掃全部 229 題現存詳解，228 題
命中、只有 cpa 那 1 題「沒中標」——當下的直覺解讀是「這題大概沒事」。

紅隊全查（fable 2026-08-28 裁決全查非抽查）到 cpa 這題時，結果剛好相反：
它不含「一律給分」樣板句，但問題**更嚴重**——詳解開頭直接寫「官方答案為
A」，現行 `bank.json` 官方答案已是 C，等於教學生官方定案的答案是錯的。這題
之所以「沒中標」，只是因為它的缺陷不屬於樣板句過期這個症狀類別，不是因為
它沒有缺陷。

**判準往前推一步**：零 token 掃描（關鍵字／正則／欄位比對）能證明的只有
「這段文字有沒有某個已知特定訊號」，**永遠證明不了「這段文字沒有任何問題」**
——沒中標的分母裡混著「真的乾淨」與「有另一種缺陷、只是掃描沒設計去抓」兩種
情況，掃描本身無法區分。這是 fable 當時裁決「全查不抽查」的理由之一（抽查會
依賴這類掃描去縮小範圍），這裡是拿到了具體實測反例：**任何用零 token 掃描
「沒命中」當作縮小全查範圍依據的判斷，都要先確認掃描的偵測範圍等於缺陷的
全部範圍，而不是只等於已知的那一種**。

## §AY 待套用的「patch 檔」動手前先確認它的 `status`：投資調查報告與可套用清單不同形
（2026-08-28，L5 造字修正，實測 108 次「造字」只有 27 次真的能直接套用）

`l5_pua_glyphmap_proposed.json` 被交辦時的描述是「108/108 造字已 staged 待
套用」，但檔案自己的 `status` 欄位寫的是「PROPOSED ONLY」——打開細看才發現：
108 次造字出現裡，**27 次（5 個碼位）是安全直接代換，81 次（2 個碼位，向量
箭頭重音）需要先寫一段「刪箭頭、在底字後插入 U+20D7」的重排邏輯，這段邏輯
在專案裡完全不存在、從未被測試過**——後者不是「套用既有 patch」，是要現場
生一段全新、沒有自我驗證的數學排版邏輯去湊數字，跟「patch 已就緒、只等解鎖」
的描述完全是两回事。

**判準**：任何被稱為「patch」「待套用清單」的檔案，動手套用前先讀它自己的
`status`／`meta` 欄位（如果有），並且用當下的資料重新核對一次它宣告的計數——
「調查報告列出 N 個候選」與「N 筆已驗證、可以無腦套用的修正」是兩種不同的
產物，前者常被後續轉述壓縮成後者（本例中「108」在轉述過程中從「造字出現
次數」變成「已 staged 待套用的修正筆數」），而這個壓縮本身就會製造出「還沒
存在的工具」被當成「已就緒」的假象。真正安全的做法：**只套用你能重新驗證
（re-derive）的部分，其餘明確標成「需要新工具，未開工」，不要為了讓完成度
好看而在沒有 selftest 的情況下現場發明邏輯。**
