## §5.4 修正腳本的 `\s` 會吃換行——一行 regex 壓掉 21 則的三段結構（2026-08-09）

全形算符要轉半形（`9,786＝8×1,200＋186` → `=`／`+`），順手在同一支腳本加了
`re.sub(r'\s{2,}', ' ', t)` 想清掉多餘空白。`\s` 匹配 `\n`，於是段落之間的 `\n\n`
被壓成一個空格，**21 則詳解全部從三段變成一段**。

抓到它的是 `expl_lint`：下一秒回報 `paras<3` 21 則、`mid-letters` 21 則，pass_rate 0.0。
**這是結構型硬門唯一一次真的付清了它的成本**——這種破壞在 diff 上看起來只是
「少了幾個換行」，人工複核極易放過，而它會讓全站 21 題的詳解版面塌掉。

兩條規則：

- **文字修正腳本只准動它宣稱要動的那一類字元。** 要換算符就只換算符，
  不要在同一支裡「順手」清空白、統一引號、trim 行尾。順手的那一項沒有測試護著。
- **改完一定重跑 lint 再併庫**，而且要看 `pass_rate` 不是看「有沒有報錯」——
  腳本跑完 exit 0，破壞是靜默的。

### 5.4.1 續：把它寫成腳本之後，第一版仍然砍到段落標記

上一節的結論是「不要在同一支腳本裡順手做第二件事」，於是全形算符轉半形被抽成一支
專用腳本 `fix_wide_ops.py`，判準寫成**「全形算符的左右都是 ASCII 英數就轉」**，
還附了 selftest。跑下去 26 則被改，逐條看才發現真正被改的幾乎全是**段落標記**：

```
D：BUN 顯著上升   →   D:BUN 顯著上升
A：4 家平面媒體   →   A:4 家平面媒體
```

`：` 在轉換表裡，而 `D：B` 的左右確實都是 ASCII。三段式規定誘答段以
**字母＋全形冒號**起頭，這一轉就把 lint 唯一在驗的結構弄壞了。真正需要轉的只有 7 則。

**selftest 為什麼沒擋住**：它有「該轉的」正例（`C＝56`、`I／B`）也有「不該轉的」反例
（`劑量：每日一次`、`比例是三：一`），但那些反例全是**中文語境**——因為我腦中想的
就是「中文語境不要動」。**段落標記這個情境從頭到尾沒被想到，於是也沒被寫進 selftest。**

> **只測你想到的那些情況的 selftest，擋不住你沒想到的那些。**
> 寫這種修正腳本時，反例要從**下游那道門在驗什麼**倒推，不要從「我打算改什麼」正推。
> 這裡的下游門是 expl_lint 的三段結構，所以 `A：`／`D：` 必須是第一個反例。

修法是把 `：` 整個移出轉換表（比值 `I／B` 由 `／` 那條處理，`：` 從來沒有真的需要轉），
並把段落標記寫成 selftest 的必測反例。

## 9. 長跑運維坑（跨模型大批量紅隊的實戰教訓）

巨科（上千則詳解＝數百批）紅隊是多日背景工程，跨越額度重置與多次重啟。以下坑真實踩過，寫進來讓任何人／任何 AI 接手時不重蹈：

### 9.1 「假完成」：批次跑完 ≠ 真的全做完

外部模型（如 Codex/OpenAI）額度**瞬斷**時，紅隊批會「成功啟動但沒產出 verdict」，逐批迴圈把它們記 ERROR 後，仍走到結尾**寫下「ALL DONE」並退出**——但其實缺了幾十批。若下一階段（Opus 修補）信這個 ALL DONE，就會修到不完整的層。

兩道防線，缺一不可：
1. **完整度閘**：判定某層完成**只認 `verdict_b*.json 數 == in_b*.json 數`**，永遠不信 log 裡的「ALL DONE」字樣（它可能是額度斷時寫的假標記）。
2. **有界重試**：跑批的函式跑完一輪後，若仍有缺批就**再跑一輪，最多 N 輪（如 4），且某輪無進展即停**（批本身壞或額度持續斷，別空轉）；唯有真正補滿才寫 ALL DONE。`done` 集合要**排除 ERROR 行**（成功批才算完成，ERROR 批下輪重試）。

### 9.2 resume 要冪等、checkpoint 要逐批

逐批寫 checkpoint（每批一行 `b007 n=25 fix=2`），重跑時讀 checkpoint 跳過已完成批。如此「電腦睡眠／session 變動／額度斷／手動重啟」中斷都無妨，重跑自動接續、不重做、不漏做。**背景進程用 detached（`nohup`）＋ 防閒置睡眠**，否則 session 一變動就被收掉。

### 9.3 額度保險：偵測 → 停 → 等重置 → 自動接

外部模型 5 小時滾動額度燒完時：①**停掉 pool**（別讓它空轉狂記 ERROR）②**清掉卡死的 in-flight 進程**（額度斷時這些呼叫會 hang 成數小時殭屍，務必殺掉，否則佔資源又不產出）③記下重置時間、到點先**測一個極小呼叫**確認通了再重啟。並行隊數（concurrency）越高燒越快——撞額度就降隊數。

### 9.4 shell 斷詞坑（zsh）

手動補跑缺批時，`zsh` **不對未加引號的變數做斷詞**（與 bash 不同）。`NNS="108 109 110"; cmd $NNS` 會把整串當**單一參數**傳入，導致「找不到 in_b108 109 110.json」這種錯。補跑批號要用 `cmd ${=NNS}`（zsh 強制斷詞）、或逐一列出、或用陣列。這個坑會讓「補跑」看似執行其實零產出。

### 9.5 主控三職能：發包、中途校正、驗收

把管線的「主控」角色明確定義為三件事，不親寫詳解（金樣／規則卡除外）：

- **發包**：準備批次輸入（隨機種子固定、排除尚未併庫批次的題號，避免重複發題）、顯式指定模型分級（生成與修復可用不同層級；**別信 CLI 的 config 預設模型**，每次呼叫都顯式帶模型參數）、把啟動腳本**寫成檔案**（絕對路徑），不要只存在於對話上下文——中斷後才補得回來。
- **中途校正**：宿主應用升級或關閉會砍掉背景執行的外部 CLI 波次——重啟後先盤點行程與輸出檔數，**只補缺塊、不重跑已完成的**。腳本一律冪等（已有非空輸出檔就跳過）。輸出**逐塊落地**（例如 15 塊×10 題，而非單檔 150 題），任何中斷損失至多一塊。
- **驗收**：零 token 硬門（結構 lint／引用守恆／答案錨）→ 裁決修復 → 跨家族哨兵抽審 → 併庫（先備份、格式不變式、總數不變 assert）→ 進度更新。**驗收不可下放給執行方**——寫的人不能自己驗收自己。

### 9.6 fix 率異常先歸因，再決定處置

紅隊 fix 率突然飆高（例如從 15–23% 跳到 90%+）不必然是品質崩壞。先統計 finding 的 type×severity 分佈再行動：**新檢查條款掃「舊規則生成」的批次**會系統性高 fix（絕大多數是同一型的 low severity 缺漏），這種交修復站統一補齊即可，不必整批重生；只有 med/high 實質錯誤佔比高才升級處置（如全抽跨家族審查）。因此**規則條款的生效批次邊界要寫明**（「第 N 批起生效，之前的批由修復站補驗」），否則後人讀紅隊統計會誤判。

### 9.7 跨模型分工與兩套執行策略

把管線環節交給不同家族模型時，判準是**產出是否面向使用者**：非面向使用者的判斷型環節（紅隊審查、歸因分類、抽查、工具腳本）最適合委外部模型——跨家族異質審查不與主家模型犯同款錯，反而是加分。面向使用者的正文（詳解本文）要下放前，先過**金樣批盲測**：同批題雙軌各 30–50 則，維護者盲讀可接受才放量。風格由「規則卡＋金樣 few-shot＋結構 lint＋引用守恆＋紅隊」五道門保證，不靠單一模型——這也是開源共編的前提（風格由規格保證、不靠單一作者）。委外生成的 prompt 必附金樣為風格 few-shot，並明令**先精讀金樣學風格再動筆**。

兩套策略依配額狀況擇一，**品質門檻完全相同、不隨模型降**：
- **全主家**：生成到裁決都在同一家族內做，成本高、風格最穩。
- **重委外**：生成／紅隊／修復都交外部模型，主家保留金樣、規則卡措辭、驗收與併庫。此策略必配兩個校準器，**不可省**：①**跨家族哨兵**——主家對成品抽審 10–20%（偏重 c=low 與敏感題），哨兵抓到外部紅隊漏掉的真錯即該批升級全抽；②**投毒召回**——定期在送審批裡混入已知錯誤，量測外部紅隊召回率。理由：**fresh context 只防錨定，防不了同族盲點**——同家族模型寫與審會犯同款錯、漏同款錯，「紅隊 0 fix」可能只是同族看不見，不是品質證明。

## 11. 併庫驗收的三個陷阱（2026-07-30，各踩過一次）

零 token 硬門都過了、數字看起來乾淨，錯還是會從**驗收方式本身**溜進來。

### 11.1 lint 函式的回傳值：取 `[0]` 不是 `[1]`

lint 一則詳解通常回 `(fails, warns)`＝**硬門失敗**與**軟門警告**兩個 list。
把 `r[1]` 當成失敗，會把 93 則警告報成「硬門失敗」，於是去修 93 則其實沒壞的東西
——真正的硬門失敗只有 5 則。

> **軟門警告的數量不是品質指標。** 一個精度爛的 warn 通道會**訓練人忽略它**：
> 實測某條 warn 規則在 699 則跑出 85 則、逐則看過**精度 0%**，靠白名單擋要再加
> 28 個字、下一批還會冒新的。處置不是加白名單，是**重寫規則去瞄真實反例的指紋**
> （該例：改成「同一子句內 ≥2 個『內容（字母）』且字母遞增」＝在照選項順序列清單），
> 誤報 85 → 0。改完把實測誤報句寫成 selftest 的否證 canary。

### 11.2 覆蓋率的分母：必須含**所有**題型 store

混合式考科把選擇題放 `bank.json`、申論題放 `essays.json`（見 parsing.md）。
只拿選擇題當分母，會算出**覆蓋率 102.8%** 這種不可能的數字，然後把那 292 則
申論題詳解誤判成「孤兒鍵」——**照那個判斷去清，會刪掉 292 則正當詳解**。

驗收覆蓋率的正確寫法：`分母 = ⋃(每一個題型 store 的 qid)`，逐科列出該科有哪些 store
再算。**超過 100% 永遠是自己的分母錯了，不是資料多了。**

### 11.3 視覺封條要在修復**之後**蓋

封條含 `sha(詳解文字)`＋`sha(圖 bytes)`，用途是「這則詳解的圖衍生內容曾被能看圖的人
核對過，且從那時起文字與圖都沒變」。**先蓋再修＝當場過期**（`expl_sha` 對不上）。
順序固定為：紅隊 → 裁決 → 修復 → **蓋封條** → 併庫。

併庫腳本也要記得把封條**帶進去**：若它只保 `{t, c}`，封條會在併庫這一步被靜默丟掉，
覆蓋率每次併庫歸零、儀表顯示「未覆蓋」，看起來像哨兵沒跑過。用白名單帶
（`vision_seal` 帶、`ans`／`findings` 這類流程中間態不帶）。


## 12. 提早驗格式：先看 fail 的**分佈**，再決定要修 opcard 還是修一塊（2026-08-01）

大批量生成不要等跑完才 lint。跑到一半就拿已落地的塊做一次 lint（讀法見
`batching-and-measurement-lessons.md` §9），成本是零 token，換到的是「系統性格式問題」在
幾百則時就被發現，而不是幾千則之後。

### 判準：fail 集中在一塊 ＝ 單次呼叫漂移，不是規則問題

nursing 跑到 760 則時 lint 合規 97.5%、19 則 `mid-letters`。**看起來像 opcard 沒把
「一段一字母」講清楚**——但把 fail 攤到各塊上，19 則全在 `nu1_out_p28`（該塊 20 題），
其餘 740 則 100%。

```python
loc = collections.Counter()
for p in sorted(pathlib.Path(".").glob(f"{prefix}_out_p*.json")):
    for r in json.loads(p.read_text("utf-8")):
        if r["qid"] in failed_qids: loc[p.name] += 1
print(loc)          # 集中一塊 → 單次漂移；散在各塊 → 才是 opcard 的問題
```

**沒做這步就會去改 opcard**——改一個本來沒壞的東西，還把已經正確的 740 則暴露在
新規則的風險下。

### 結構壞而內容對 → 零 token 修，不要重跑

那 19 則的內容全對，壞的只有 A／B／D 三段被壓成一段：

```
A：漿性惡露…不符。B：粉紅惡露…不是。D：白惡露…故非答案。
```

重跑一塊＝一次 codex 呼叫；依這個比率 449 塊會出約 12 塊。拆段是純字串操作。
`fix_merged_letter_paras.py` 做這件事，兩條紀律：

1. **切點的字母頭用 `expl_lint.HEAD`，不另寫一份**（兩端各寫各的判準已害過兩次）。
   本檔獨有的只有「前面必須是句末標點」這個位置條件——閘門看段首、修法找段中。
2. **拆完每一段都必須是合法字母頭，否則整段退回不動**。寧可留給修復站，不要半修。

### 🔴 驗收要在 known-good 上也跑一次

「修完 760/760 過」證明不了什麼——一個把每個 `[A-J]：` 都無條件切開的爛版本同樣會通過。
真正的證據是**在另一科的 3,120 則 clinical 上動了 0 則**。判定式恆真的失敗模式，
只有 known-good 對照跑得出來（同 `batching-and-measurement-lessons.md` §8 的併發自檢）。


## §14 R 線重構的保真條款：不寫的話事實保留率只有 43%（2026-08-02 實測）

R 線（重排既有詳解成三段式）存在的正當性是**舊詳解是人寫、已驗證的資產**——實測
支持這點：R 線產出的紅隊 fix 率 7.8%，低於 A′ 從零生成的 9.2%；高嚴重度 finding
更是 0.45% vs 1.9%，差四倍。**守不住保真，走 R 線就沒有意義。**

但原本的 `GEN_TASK` 守不住。40 題真散文實測（`old_t` 平均 125 字，重構後擴寫 2.5 倍）：

| 配置 | lint 合規 | 事實保留率 | 零遺失題數 |
|---|---|---|---|
| terra low（原 prompt） | 100% | **43.4%** | 27/40 |
| terra low ＋保真條款 | 100% | **100.0%** | **40/40** |
| luna low（原 prompt） | 100% | 58.5% | 28/40 |
| luna low ＋保真條款 | **57%** | 100.0% | 40/40 |

### 掉的是什麼：全部是英文原名，數字一個都沒掉

診斷清單：`labeling`、`fully functioning person`、`NEO-PI`、`Costa`、`McCrae`、
`OCEAN`、`CPI`、`MCMI`、`burnout`、`propinquity effect`、`Minuchin`、`Satir`。
中文譯名都在，掉的是括號裡供學生查證與對照教科書的原文。

**根因是規格漏洞不是模型缺陷**：opcard 只在末段要求「本題考點：…（附英文原名）」，
中段沒有要求，模型就照做把中段括號裡的原文省了。它沒有違規，是規格沒說。

### 條款本文（已併入 `mkprompt.py` 的 `GEN_TASK`，只在 gen 站生效）

> old_t 裡出現過的每一個英文原名都必須在新詳解中至少出現一次，位置不拘，寫法沿用
> 「中文譯名（English original）」括號式。數字、劑量、年份、法條號同理。某個原文若
> 明顯誤植，仍保留並以中文一句話點出疑義，**不要靜默刪除**——靜默刪除會讓下游無從
> 察覺資產流失。

代價只有 token +6%。**不要掛在 `gen0`（從零寫、沒有 old_t）或紅隊站**上。

### 🔴 便宜模型加了這條會壞掉結構，別直接套

luna low 加上條款後保真度同樣衝到 100%，但 lint 從 100% 掉到 57%——17/40 題**把正解
字母也寫成中段一段**（`mid-letters:ABCD≠ABD`），違反「中段只放非正解選項」。
它為了塞進英文原名而犧牲了結構約束。加約束前後都要重驗合規率，別只看新指標。

## §15 🔴 產線缺陷：生成站的內部欄位會漏進學生正文（2026-08-06）

紅隊盲裁的副產品：84 則被判「質疑成立」的裁決反覆指向同一種東西——
詳解正文寫著「故本題把握度較低」「查證不足，故為 low」「把握度中等。」。

`c`（把握度）是**生成站自報的內部欄位**，本來只給紅隊看（「c=low 加倍嚴審」）。
它漏進正文有兩層傷害：學生看到一個沒頭沒尾的檔位值只會困惑並削弱對正解的信任；
同時它是 `c` 這個欄位的第三條洩漏路徑（另兩條是洩漏給紅隊，屬量測問題）。

**全庫實測 259 題、8/10 科。** 關鍵在**十科全掃**：發現途徑是臨床科，
但 doctor 有 131 > clinical 85——**只掃發現途徑那一科會漏掉三分之二**。
生成站 prompt 是共用的，所以缺陷必然跨科。

### 偵測器不能拿高頻普通詞當錨點

第一版規則靠「信心」兩字定位，**被真實資料打臉兩次**，兩次都不是 selftest 抓到的，
是抽真實命中人眼看才發現：

| 誤報 | 領域 |
| --- | --- |
| 信心水準、信心區間 | 統計學（confidence level／interval） |
| 自信心、信心不足、重建信心 | 心理學與護理 |

**每補一個排除就冒出另一類**——那是錨點選錯了，不是補得不夠勤。
改成白名單式：必須**同時**有「宣告對象（信心／把握度）」與「檔位值或宣告動詞」，
**且落在句末**（真實的洩漏都是收尾宣告；不要求句末的話，
「個案信心較高，故較願意嘗試」這種正常句就會中招）。

### 偵測器可以寬鬆，切除端必須嚴格

機械切除時另設四道閘門（切內容比改標點危險）：
切完必須完全過 lint／被切片段須整段只有信心宣告（白名單 ＋ ≤40 字）／
只准變短／切點不得留下連續標點。

**結果：用「還有誤報的偵測器」跑的 164 刀，一刀都沒切錯**——
切除端的白名單擋住了「自信心高且追求完美」這類夾帶內容的片段。
⇒ 一般化：**兩層不同性質的判準疊加**，偵測寧可多報、動手必須嚴格。
若兩端共用一條規則，偵測器的誤報就會直接變成切錯。

### 閘門的嚴格程度要對應「這個動作的反面是什麼」

同一批修復，**新增入庫**與**覆寫既有**要用不同標準：

| 動作 | 閘門 | 為什麼 |
| --- | --- | --- |
| 新增（要進庫） | 必須**完全過門** | 反面是「不進庫」＝沒損失；允許半修的話，殘留的 fail 會被「已處理」掩蓋掉，從清單消失但問題還在文字裡 |
| 覆寫（已在庫） | 只要**不新增 fail** 且確有改善 | 反面是「留著有洩漏的版本繼續給學生看」＝有損失 |

第一版兩者共用「必須完全過門」，47 則被誤退——那些題的舊文字**本來就不乾淨**
（正是因為有洩漏才被抓出來），把「洩漏＋其他問題」換成「其他問題」是嚴格改善。
分流後多收 42 則，**同一批修復前後差近一倍**。

⇒ **反面有代價時，過嚴的閘門本身就是一種代價。**

### 修復站比重生成適合這類「只有一句話有問題」的缺陷

把 lint fail 轉成 finding 送修復站，而不是整篇重新生成——
重生成會丟掉原本已經正確的部分；修復站走「對每個 finding 先驗證再修、最小幅度」，
其餘保真（實測三個配置的「破壞保真」皆為 0）。**選對站比選對模型重要。**


## §16 一個 prefix 一波，永遠不要在舊 prefix 上重跑切塊

紅隊的切塊工具（本專案是 `mkrt.py`）預設會**重新切、重新編號**。拿舊 prefix 再跑一次，
產出的區塊與上一波**不是同一批題**：實測 2026-08-13，只有第 1 塊保住原本的 qid 集合，
第 2 塊就已經與舊的重疊 10/30。

後果不是報錯，是**每一則判決都配到錯的題**——而檔案數、qid 數、verdict 分布
全都看起來正常。這是「wrong-but-legal」的典型：所有計數都對，只有配對錯了。

規則：
- **一個 prefix 一波**，新的一波開新 prefix，並用 `--skip` 明確排除前幾波涵蓋過的題。
- 切塊工具要能**把「這一波涵蓋不到的題」落成一份檔案**（本專案是 `*_orphan.json`）。
  沒有生成輸入的題永遠進不了任何區塊，於是它們**既不會被判 pass 也不會被判 fix**——
  如果只看 verdict 分布，它們是隱形的。落成檔案，合併時才排得掉。
- 🔴 **合併時要主動排除 orphan**。它們有詳解、沒被審過，而「有詳解」這件事
  在檔案系統上與「審過的詳解」完全同形。

同一條規則的機器閘與 2026-08-17 重犯紀錄在 batching-and-measurement-lessons.md §24。


## §17 重生成會丟掉修復；每一批重生成都要自己再走一次紅隊與修復站（2026-08-18 實測）

同一輪裡，一題可能經過：gen0 → 紅隊判 fix → 修復站修好 → **然後因為上游輸入被修好而重生成**。
重生成用的是**不同的輸入**，所以它丟掉先前那次修復是對的（那次修復是對著殘缺輸入做的）。
但很多人在這裡直覺會反過來——「修復站是後面的站，應該贏」——於是把修復的輸出疊在
重生成之上，等於把新資訊丟掉。

**疊層的先後由「輸入的完整度」決定，不由「站的順序」決定。**
拿更完整的輸入重生成的結果，排在拿殘缺輸入修出來的結果**後面**。

而重生成之後那一則是**沒有被審過的新文字**：實測 `111_分科化學_10` 在第 2 層被修過、
被第 5 層覆蓋，紅隊在第 5 層的產出上又抓到兩則真錯。所以：

> **每一批重生成，都要自己再走一次紅隊與修復站。** 不能沿用上一批的判決——
> 那份判決是對另一份文字下的。

疊層要用一支腳本、每層斷言「不得引入外來 qid」「不得有題被疊掉」：
疊錯不會報錯，只會靜默少 ship 或 ship 到舊版，而兩者在最終檔裡長得一模一樣。


## §18 補救腳本回報「0 則」時，先分辨是「沒事」還是「沒認出來」（2026-08-18 實測）

零 token 的 lint 補救腳本（刪信心自述、寬度正規化、段首修正）都是**樣式比對**，
而樣式是照著**當時看到的那個表面形式**寫的。換一科、換一個模型，同一件事會用另一種
寫法出現，樣式就整批漏掉——**而它的失敗長相是「0 則」，看起來跟「沒事可做」一模一樣。**

實測：`conf-leak` 的樣式寫死成「…把握度較低。」，ast 這批寫成
「…仍有不確定性，故本則把握度低；採此配置可得…」——沒有「較」、收在分號、
後面還有半句。腳本回報「合計 0 則」，而 lint 同時紅著三則。

**判準**：補救腳本跑完，**拿 lint 重驗、比對「它宣稱修好的則數」與「lint 少掉的 fail 數」**。
兩個數字對不上就是樣式漏了，不是沒事。這與 `gates-lessons.md` §H「彙整器不可以把量過的結果
降級成沒跑」是同一條——**「0」是一個需要解釋的數字，不是一個可以直接相信的數字**。

順帶兩條，都是同一輪踩的：

- **收尾標點要原樣還回去**。刪掉一段子句時，它前面的標點是逗號還是分號決定了句子有沒有
  結束；一律換成句號會把後半句切成沒有主詞的殘句。
- **壞的查找會回一個合理的值，而不是報錯**。`load_bank_file()` 回的是
  `{ans, n_opt, opts, …}` 不是原始題目，寫成 `q.get("options") or []` 靜默回 0 個選項，
  於是字母覆蓋判準把每一則都判成「字母逸出」。**對契約寫 `assert`，不要寫註解。**


## §19 操作卡的兩個靜默缺陷（2026-08-23，同一張卡上同時中兩個）

修復一張被紅隊判死的操作卡時，這兩件事都不會有任何東西報錯。

### §19.1 產物形狀要對著**併庫的目標**寫，不要對著自己順手的寫

實測：`OPCARD_cpa215.md` 要求產出 `{qid, outline, c, sources_used, uncertain}`，
而目的地 `essays.json` 的 `ref` 欄實際是
`{summary, frame, keywords, pitfalls, confidence, needs_verification}`。
兩者沒有一個欄名相同。215 篇草稿照卡寫完、格式合法、卡的自檢全過——
**併進去會讓同一個檔出現兩種 ref 形狀**（既有 120 篇一種、新的 215 篇另一種），
而 JSON 不會抱怨，前端也只會在讀到缺欄時安靜地少顯示一塊。

規則：**卡的「產物」段要從目的地的既有紀錄複製 schema，並在卡裡放一則真實的既有紀錄當金樣。**
金樣取自同一個檔，schema 就永遠不會分岔。自己寫一份「看起來合理的」欄位表，
等於在下游埋一個沒有錯誤訊息的分岔。

### §19.2 一張卡的字句被診斷為病因時，要 grep 所有姊妹卡

實測：`OPCARD_essay30.md` 的 §3 在 2026-08-13 被紅隊判出 `架構不可操作 ×15`，
根因診斷為它自己的字句——「每點**一句說明這一層要證成什麼**」。那張卡當場修好了。

十天後才發現，`OPCARD_cpa215.md` 的 §3 有**一字不差的同一句**，而它產出的 215 篇
從沒被紅隊看過。修好的是那張卡，不是那個句子。

規則：**根因是一段字句時，修復範圍是「這段字句出現的所有地方」，不是「發現它的那個檔」。**
一行 `rg -F '<那句話>' _build_features/OPCARD_*.md` 就夠。
配套的一般形式已經在本檔記過一次：**一條規則若寫成它想防止的那個句式，模型會照著寫、
而且完全合規**——所以這種病因會沉默地散佈到每一張抄過它的卡。


## §20 禁令與示範相衝突時，示範贏（2026-08-23 實測）

**規則**：prompt 明文禁令與金樣示範衝突時，模型照著示範走，不是照著禁令走。
金樣母體本身有偏差、又不可能重新取樣（母體就那幾則）時，不能只讓模型模仿示範的
結構與語氣——要在金樣區塊明說偏差方向，並明令**只模仿結構語氣、不模仿成因型別**。

**實測**：六科 194 則送分題重寫，紅隊判 fix 95 則（49%），其中 53 則因
`manufactured_tie`——模型找不到真正的送分理由就編一個爭議。prompt 裡有大寫的
`NEVER MANUFACTURE A TIE`、明列五種合法成因，寫得很清楚；但可得的 5 則金樣裡
4 則是「兩解並存」型。修法：`cause_of()` 零 token 粗判成因型別，金樣區塊開頭印出
分佈並明說「這是可取得的樣本，不是成因的真實分佈……請模仿金樣的結構、語氣與
長度，不要模仿它們的成因型別」。本波落地 99 則、全數通過紅隊。

**同族病，第二次**：§19.2 已記過「一條規則若寫成它想防止的那個句式，模型會照著
寫、而且完全合規」；這次是同一族病的另一種表現形式——不是規則字句本身示範了
禁止的東西，是**示範素材**示範了禁止的東西。兩次結論一致：**光改條文不夠，凡是
prompt 裡放了具體示範，示範的實際內容永遠壓過條文的抽象禁令。**


## §21 lint fail 先判版面代理指標還是真內容契約，別直接放寬契約（2026-08-23 實測）

**規則**：lint fail 出現時先判是「測到版面代理指標」還是「真內容契約」。前者是
檢查本身綁錯了東西（該用內容判準卻綁了版面特徵），要改檢查本身（例如逐行展開
後再判）；後者是資料真的沒達到契約，屬資料缺陷，要用零 token 機械補值修。
**兩者都不可以直接放寬契約**——那等於把不變式花掉。

**實測**：護理 461＋臨心 114 則三段式詳解，紅隊兩臂（opus medium／fable medium）
620 則全覆蓋、零缺塊。lint 兩項改動對應兩種判斷：
- `mid-letters`（版面代理指標）：176/470 被誤判，逐則內容全對，只是 A/B/D 三行
  寫在同一段而非分行——契約要的是「逐項辨析恰好覆蓋非答案選項」（內容），檢查卻
  綁在 `\n{2,}` 切段（版面）。新增 `explode_option_lines()`，且只在整段每行都是
  選項段首時才展開，失敗方向是扣住不是放行。
- `paras<3`（真內容契約）：`\n\n` 是前端真正用來分段的字元，放寬它等於花掉不變式。
  改成補資料：`normalize_expl_paras.py` 零 token 補空行，56 則，不變式是「去掉
  空白字元後改前改後逐字相同」。

selftest 先驗過失敗：改前版本「同段多行不誤判」fail，「漏掉 B 仍 fail」與
「含續寫行不展開」兩條護欄改前改後都 fail（放寬沒有變成放行）。
`mid-letters` 判準定義見 §12／§14 附近的「中段只放非正解選項」。


## §22 刪文字片段的右界要停在最近的既有終止符，不跨句不跨行（2026-08-19 實測）

**規則**：切除文字片段（如信心值自述）時，右界要停在**最近的**既有終止符：
命中本身已在句末就不再往後找下一個句號；命中後接分號就切在分號**之前**、把
分號留給接續句用；右界落在換行就不跨行。為求乾淨句尾而多吞一句、多吞一個換
行，就是過度刪除——被下游結構門正確擋下，不是「不可切」。

**實測**：LOOP_PLAN 記「8 則 conf-leak 由 `strip_conf_leak.py` 處理」，實跑一則
都切不掉，9 則全被判「需重生成」。查下去不是內容不可切，是右界找錯，三種切法
都是切太多，被 G2（切段必須整段只有信心宣告）正確擋下。三條右界修法：
① 命中已句末標點收尾（`把握度低。`）→ 右界就是命中結尾；原版再往後找一個
`。`，把下一整句吞進去（實測多吞 58 字）。② 命中後接 `；`→ 切到分號之前，留著
當接續標點，否則前後黏成一句無標點的話。③ 右界落在換行 → 不切；原版連 `\n`
一起吃，正解段與 `A：` 段黏成一行，`mid-letters` 立刻紅——「切完反而多一個
fail」。驗收：8 則逐則列出切掉字串，每刀只有信心宣告本身，只動 `t` 欄；
conf-leak 8→0，總 fail 28→20。

**同一支腳本，另一族失效**：§18 記過 `strip_conf_leak.py` 的樣式漏認（回報
「0 則」其實是沒認出來，不是沒事）；這次是同一支腳本的另一族失效——**認得出來，
但切多了**。同一支修正腳本要同時防「認不出」與「切過頭」兩種方向相反的錯。


## §23 全形規則被整體撤銷後，用相鄰字元類開精準窄縫（2026-08-19 實測）

**規則**：一條全形／半形轉換規則因誤傷特定樣式而被整體撤銷之後，若回頭發現
「該轉」與「不該轉」兩邊可以用**相鄰字元類**（如字母 vs 數字）分開，就開一道
精準窄縫只放行那個字元類組合，不要停在「整體排除」或「整體開放」兩個極端。

**實測**：`：` 在 §5.4.1 因為誤傷段落標記（`D：BUN` 被轉成 `D:BUN`，毀掉三段式
lint 唯一在驗的結構，實測毀過 26 則護理詳解）而被整體移出轉換表。這次藥師
wave 3 草稿轉完全形算符後仍有 13 題卡在 `wide-op-in-latin`，形狀全是
`0：1`／`1：1`／`4：2`／`100：1`——都是比值。三段式段落標記左邊永遠是字母
（A–E），比值左邊永遠是數字，兩者在字元類上分得開，於是只開
`(?<=[0-9])：(?=[0-9])` 這一道縫。加上後 13 題歸零，剩 12 題是 `mid-letters` 9／
`half-punct-in-cjk` 2／`data-complaint` 1，那些要人判斷、不機器修。selftest 補
兩正兩反：比值要轉、`D：2 倍以上` 與 `第一：3 個條件` 不得被波及。

直接延續 §5.4.1 那次「`：` 整體排除」的決定——不是推翻它，是在它的排除範圍裡
再切一刀精準的例外。


## §13.1 段落級修復：0 附帶損害不是免費的，代價是覆蓋率（2026-08-24 實測）

段落級修復站（定案於 explanations-redteam.md §13）的招牌數字是「**附帶損害
0/454（位元組層級）**」，
對照全文修復的 3.4%。本輪複審 A 臂量出了它的另一面：

> 段落級修復把「附帶損害」壓成 0，代價是把「修復覆蓋率」也壓低了。44 則 fix
> 裡約 15 則是「正解／中段修好、**考點段仍留著同一個舊錯誤或舊判準**」，另約
> 14 則是「出問題的那一段**根本沒被列入待修範圍**」。

**實測（三個後果比修之前更糟的實例）**：

```
01_22  正解段已改成 ammonia trapping；考點段仍寫「代謝性酸血症會提高 NH3/NH4+ 比例」
       → 同一則詳解現在有兩套互相矛盾的機轉
3_45   正解段仍寫 fu=0.9，而同段算出的 0.0099 是用 fu=0.1 算的；交修的卻是 A 段

```

🔴 兩個招牌數字要一起讀，單獨看都會誤導：「附帶損害 0/454」量的是**有沒有動到
不該動的**，量不到**該動的有沒有動**；「命中 225/271（83%）」量的是**送去的
段落**有沒有改，不是**該修的段落**有沒有被送去。兩個都是「已送範圍內」的指標，
而缺陷正好在**範圍之外**——與同輪 gates-lessons.md §AJ 那條「涵蓋式斷言對被
涵蓋的方向是瞎的」是同一個病（總論見 gates-lessons.md §AL）。

**修法（A 臂提的，可機械化、幾乎零成本）**：finding 只要提到某個錯誤陳述，就
該把該則裡**所有含相同陳述的段落（尤其考點段）**一併交修。實作方向：
`ab8_segfix.py` 的 `target_keys()` 現在只認 finding **明文點名**的段落鍵；應改成
先抽出 finding 指涉的錯誤陳述（或其關鍵名詞片語），在**全文**搜同一陳述，所有
命中的段落一併列入待修。多送一兩段的成本，換掉「修出一則自打嘴巴的詳解」。

**量化的代價**：本輪 142 則修過的，複審聯集只有 80 則（56%）可上線，45 則仍
`fix`（多數是選段缺陷不是內容不可修）、17 則 `needs_input`。

## §24 字串黑名單只買得到「換一個套語」（2026-08-24 實測）

操作卡黑名單了「題眼在」（doctor 曾實測佔 61.1%）。本輪實測：模型改用
**「本題問的是」，佔 71.7%**——禁一個詞，長出另一個詞。

**規則**：套語是**分佈現象**，規則要寫成分佈約束（任何單一引導詞 < 25%），不是
字串黑名單——黑名單只能列出已經犯過的那些，永遠追在模型後面。

**實測**：校正後，最大單一引導詞降到 3–9%，82% 改為「不用引導詞、直接切進
內容」。而且直接切入更短、資訊更密——它不是妥協，是更好的寫法。

→ 本輪主線的第五個實例（詳見 gates-lessons.md §AK）：黑名單詞表定義在操作卡裡，
模型實際的用詞分佈是另一個獨立變動的東西，禁令追不上分佈漂移。

## §25 把「同時在場、沒有對照組」的旁證寫成因果——manufactured_tie 的再核對（2026-08-24 訂正）

本節原稿把 0/63 記成「具名反例」這個新手法的功勞。**逐項比對 §20 之後，
那個歸因是錯的**，訂正如下。

**§20 vs 本節，逐項比對**：

| | §20（2026-08-23） | 本節（2026-08-24） |
|---|---|---|
| 母體 | 六科 194 則送分題重寫 | 藥師 63 則新生成 |
| 49% | 紅隊判 fix 95 則、其中 53 則是 `manufactured_tie` | 引自同一個來源數字（LOOP_PLAN L14 記的「49% of fix verdicts」）——**不是獨立量到的第二個 49%** |
| 修法 | 金樣區塊印出成因分佈、明令「不模仿成因型別」 | 派工規格裡加具名反例＋明講替代動作 |
| 結果 | 本波 99 則全數通過紅隊 | 0/63 命中 `manufactured_tie` 指紋 |

**關鍵**：§20 的金樣修法在本輪**同樣生效**——`gen0free` 走的就是同一份金樣，
而 §20 落地時已經是 99 則全過。也就是說本輪跑的時候，**兩個修法同時在場**：
`gen0free` 自帶 §20 的金樣分佈修正，派工規格又加了本節的具名反例。0/63 這個
結果**無法歸因**於本節新增的具名反例——它同樣可能只是 §20 那次修法持續有效
的旁證，本節原稿把「同時在場、沒有對照組」的觀察寫成了「新手法生效」的因果，
是誤判。

🔴 **這件事本身就是本輪的一條教訓，而且是同一輪內犯了兩次**：我在 LOOP_PLAN
L14 已經寫過「那是觀察不是歸因」的警告，寫在別處；然後在寫這一節時，同一個
數字又被我自己寫成了因果。**警告寫在別處，不會保護到這裡**——每一節下因果
結論的地方，都要重新自問一次「有沒有對照組」，不能靠「我在別的地方提醒過
自己」。

**規則**：`manufactured_tie` 是否需要具名反例這個額外手法，目前仍是**未驗證
的假說**，不是已驗證的結論。與 §24 合起來，唯一站得住的一般形式縮小為：
「單純禁令容易被繞過，給模型一個可執行的替代動作是更好的方向」——這個方向本
身有 §20 的獨立實測支持（金樣分佈修正也是一種「給替代動作」）；但「具名反例」
這個**具體手法**是否有加成效果，本節的資料回答不了。

**要驗證需要什麼**：同一批題、關掉具名反例（只留 §20 的金樣分佈修正）、其餘
規格不變，跑第二次；若 fix 率顯著回升，才能把加成效果歸給具名反例。

同族：本節與 §20 是同一個 `manufactured_tie` 問題的兩次記錄，互相參照，
**不合併**——§20 是已驗證的修法，本節是未驗證的假說＋一次歸因錯誤的訂正記錄，
兩者性質不同，合併會把「已驗證」與「待驗證」的界線抹掉。

## §26 違規紀錄要帶逐字的原始術語，不能帶轉述（2026-08-24 實測）

保真閘報 `114_114030_內外科護理學_30` 遺失 `erythroplakia`（口腔紅斑症，癌前
病變）。計畫文件把它轉述成「`erythema` 遺失」。照那個轉述去修，會補進
**`erythema`**（紅斑／發紅，意思不同的另一個字）——閘門那筆**仍然報紅**，而
內容更錯了。實測線上文字正是這個狀態：「口腔紅斑症（oral erythema）」。

**規則**：修復要對著**原始術語**驗，不能對著計畫文件裡的**轉述**驗。任何違規
紀錄（fixlist、finding、報告）引用原文時要逐字帶術語本身，不能用自己的話重述——
轉述是有損壓縮，壓縮後的東西拿去比對，比對的已經不是原本的缺陷。

## §27 靠提醒維持的格式規則會週期性失效（2026-08-24 實測）

`gen0fig` 站的輸出「首段必須以『正解：』起頭」這條，在本輪**兩次**整塊失守
（p2 的 13 則、p13–p16 的 13 則），中間還在派工文字裡明確加過提醒。

**規則**：提醒有效但不持久——換一個代理就重來一次。這條該在**寫檔前自檢**
（工具層），不是靠每次派工記得講。

**實測**：機械補回是安全的（首段其餘內容完整、中段與末段都在），但那是事後
補救，而事後補救每次都要有人先發現才會啟動——與提醒同一個失效節奏。

## §28 跨題一致性缺陷，逐題審查在定義上看不見（2026-08-24 實測）

複審 B 臂抓到一則單題審查**結構上不可能**發現的東西：

> `pharmacist_111_111100_P3_..._3_14` 與 `pharmacist_102_102100_P4_..._3_09`
> 對礦物油／揮發油濕膠法的比例互相對調（3:2:1 vs 2:2:1）——同庫內兩則不可能同時對。

兩則各自**內部完全自洽**，逐題看都無懈可擊，缺陷只存在於**兩則之間**。現行
產線每一站（生成、紅隊、修復、複審、lint）都是逐題的，**沒有任何一站在看
跨題一致性**。它被抓到純屬僥倖——同一個複審代理剛好在同一批裡看到兩則，而且
記得住；換一個切塊方式（兩則落在不同塊、不同臂）就永遠不會被發現。

**規則**：逐題審查對跨題一致性缺陷是結構性盲區，不是漏抓，是類別上就抓不到。

**配套（可行的機器化方向，零 token）**：對同一科同一概念的**數值宣稱**建索引
（比例、劑量、期限、天數），同概念不同值即報。難點在「同概念」的認定，但先從
**完全相同的名詞片語＋不同數字**這個窄樣式開始就有價值——本例的「濕膠法」
「初級乳劑」就是同一個名詞。

## §29 一個大量誤報的閘，它的代價要有名字（2026-08-24 實測）

`官方答案為` 那條 lint 規則降為 `warn`（實測精確度 15–20%，當硬門會製造 218
個假警報）。複審隨後點名 5 則「只是換句話說」，新 lint 命中 3/5——**漏掉的
2 則正是被降級的那條該管的**。

**規則**：這就是那個取捨的具體長相——換到不製造假警報洪水，代價是這類真發現
要靠紅隊抓。取捨本身可能是對的（紅隊抓得到，而假警報會讓閘門失效被人忽略），
但**代價要有名字、有數字**，不能含糊帶過。下次有人想把它升回硬門時，該看到
的是這兩個數字並排：`精確度 15–20%` 對 `漏掉 2/5`。

## §30 我手寫規格派工，等於繞過操作卡（2026-08-24 實測）

修復站沒有走 `mkprompt`，而是自己寫了一份 `L20ph_fix_spec.md` 派給子代理。結果：
**操作卡的規則沒有進到代理眼前**，其中包括這一條：

```
pharmacist_opcard.md:79   ## 🔴 clean-room：不要上網查
                          本站的輸入**只有**題幹、選項與官方答案鍵。**不要使用網路搜尋**
```

於是 p4–p6 的代理為了不杜撰法規數字，**用 WebSearch 查了全國法規資料庫**（7 項
法定期限與機關名稱）。動機是對的，路徑是被禁的，而它讀的是我的規格、不是操作
卡——責任在我（clean-room 的完整分析見 data-sources.md §10）。

**規則**：`mkprompt.py` 的整個設計理由就是「把操作卡逐字內嵌進 prompt，取代讓
模型自己去讀檔」，而且它還帶漂移閘（skill 比戳記新就拒絕開跑）。**任何繞過
`mkprompt` 的派工，同時繞過了操作卡與漂移閘**，而這兩件事都不會報錯。

**配套**：

1. 手寫站別規格時，**必須把該站操作卡的硬規則段落逐字帶進去**（至少 clean-room、
   `ans` 不得竄改、標點、禁鷹架詞這幾條），或者乾脆讓代理自己跑一次
   `mkprompt.py <stage>` 取規則正本。
2. 更好：替段落級修復站補一個 `mkprompt` stage（現有 stage 是
   `gen／gen0／gen0fig／gen0free／redteam／fix`，而 `ab8_segfix` 走的是另一套），
   讓它也吃得到操作卡與戳記。

→ 本輪主線的第六個實例（詳見 gates-lessons.md §AK）——這次分岔的兩端是「操作
卡」與「我手寫的規格」，跟 gates-lessons.md §AI 的生成契約 vs 閘門契約是同一個病。

## §31 一條「所有站都適用」的規則，實際只寫在 12 分之 2 張卡上（2026-08-24 實測）

§30 收在「配套 2：替段落級修復站補一個 mkprompt stage」。真的去補的時候，先量了
一件更基本的事：**clean-room 條款到底寫在哪幾張操作卡上。**

```
12 張 *_opcard.md，含「## 🔴 clean-room」段落者：2 張
     ast_opcard.md（fb3806c4）   pharmacist_opcard.md（7f673ffe）
```

兩張的 hash **不同**——差在「藥學知識」與「學科知識」一詞，以及斷行位置。缺的 10 張
裡包含 **lawyer**：最會想上網查法條的那一科，它的操作卡上一個字都沒有。

> **一條寫給 N 個消費者的規則，如果靠手抄分發，它實際存在的份數不是 N，是「有人記得
> 抄的次數」。** 而抄過的那幾份，會各自開始漂。

這比 §30 更前置：§30 說的是「繞過 mkprompt 就繞過操作卡」，隱含前提是**操作卡上有那
條規則**。實測前提不成立——就算那兩個代理老實走了 mkprompt，只要跑的是律師或社工，
拿到的卡上照樣沒有 clean-room。

**修法**：條款收成 `goldens/mkprompt.py` 的 `_CLEANROOM` 單一常數，`build()` 對每一站
（含稽核站）注入；12 張卡上的手抄版刪除。`ab8_segfix.py` 改 `from mkprompt import
_CLEANROOM`——這行 import 同時把段落級站接回漂移閘（mkprompt 在 import 時跑
`drift_gate`），因為 §30 記的洞是「操作卡與漂移閘一起被繞過」，補一半不算補。

**閘門（三條，皆已否證）**：

1. 每一站 `build()` 的產物必含**剛好一份**條款且含 `tw_statute_at_date`。
2. 任何 `*_opcard.md` 不得再出現 `clean-room` 字樣——**這條擋的是退回原形態**，
   而不只是擋當下的錯。否證方式：在 `lawyer_opcard.md` 補一份手抄，斷言即失敗。
3. `ab8_segfix.py` 模組層 `assert`（該站沒有 `demo()`，所以檢查寫在模組層，每次跑都驗）。

**一般形式**：查「這條規則被違反了嗎」之前，先查「這條規則存在幾份」。散文規則的份數
是可以直接數的，一行 `for f in *_opcard.md; do ...; done` 而已——而它常常不是你以為的
那個數字。同一件事的量法見 `gates-lessons.md §AL`（只量已送範圍內的指標，對範圍選錯是
瞎的）：這裡「已送範圍」＝那 2 張卡。

## §32 禁一個套語只會長出隔壁那個——要的是分佈約束（2026-08-24 補上）

這條在 LOOP_PLAN 掛了一整輪「規則未改成分佈約束」，本輪才補。觸發它的是一個提問：
剛寫進 clean-room 的「母法寫『由中央主管機關定之』時，那本身就是可寫的答案」，
**會不會太頻繁出現？**

會。而且機轉跟舊事故一模一樣：操作卡禁掉「題眼在」之後，同一個位置長出「本題問的
是」，占比 71.7%。**禁一個詞只是把機率質量推到隔壁的詞**——套語空間比任何黑名單大。

### 量出來的基線與門檻

「由中央主管機關定之」在 59,331 則已上線詳解裡只有 **7 則（0.01%）**。稀有。而新規則
的曝險面是法規類科目約 2,960 題——足以讓它從 0.01% 長成兩位數而沒有任何東西報錯。

各科開場／收尾 shingle 的最高占比（扣掉法定契約句）：

```
ast 0.1  cap 0.3  gsat 0.4  pharmacist 0.6  teacher 0.6  nursing 0.7
social-worker 0.8  cpa 1.1  clinical 1.3  counseling 1.5     ← 健康群
🔴 lawyer 7.9%（268 則「正解：本題為負向題，選錯…」）        ← 異常值
```

門檻取 **3%**：健康群最高值的 2× 餘裕，異常值的 1/2.6。**不是挑一個好聽的數字，是量完
之後找那條把兩群分開的線。**

### 閘的形狀：沒有黑名單

`phrase_share.py` 不問「用了哪個詞」，只問「同一個開頭／結尾佔了這批的多少」。取每則
首段與末段的前 12 字當 shingle 數占比。**哪個套語長出來都會被抓到，包括還沒被命名的
那個**——這是它跟黑名單的全部差別。

一個必要的例外：**法定契約句要排除**（送分題的 `OPEN_LINE`、官方未公布答案的開頭）。
它們必須每則都一樣，占比高是正確的。不排除的話，這道閘會去罵一條我們自己規定的規則。

🔴 **第一次跑就抓到一個已上線的**：lawyer 那 268 則活在線上好幾週。逐則審查看不到它
——每一則單獨看都合格，問題只存在於分佈裡。這是 §28（跨題一致性缺陷，逐題審查在定義
上看不見）的同一個形狀，只是這次的維度是文體不是內容。

**一般形式**：一條規則如果會**建議**某種寫法，就要同時問「它被採用到什麼比例算過頭」，
而且那個比例要有東西在量。沒有分佈約束的建議，等於在鼓勵套語。

## §33 一個契約，五個消費者——修到四處仍然是分岔的契約

2026-08-24 一天之內，送分題契約（開頭句 `OPEN_LINE`、四選項各一段、上限 600 字）
在**五個**消費者身上各漏一次。上一輪把前兩個對齊之後，看起來就結案了。

| # | 消費者 | 症狀 | 為什麼難認 |
| --- | --- | --- | --- |
| ① | `build_free.lint_free` | 正本 | — |
| ② | 生成端 prompt | 63 則裡 9 則超長 | 上一輪補了開頭句，**上限沒人 import** |
| ③ | 審查端 prompt | 63 則裡 **30 則**被要求改成契約禁止的寫法 | 另一臂 0 則同型誤報，**長得像模型差異** |
| ④ | 修復站的**判分器** | `lint 0/8` | **長得像修復整批壞掉** |
| ⑤ | 修復站的 prompt | 無症狀 | **是斷言寫完當場抓到的** |

🔴 **判準**：與其一個一個補，把「哪些站看得到這類題」寫成**可斷言的事**
（`FREE_AWARE` 集合 ＋ demo 逐站斷言「帶到開頭句、帶到上限」）。第五個就是它抓到的，
而它守的是第六個。

**一般形式**：一個概念有 N 個消費者時，把契約補到 N−1 處**在觀測上與補齊沒有差別**
——差別只在還沒被想到的那個位置何時被觸發。所以要有的不是「補齊」這個動作，
而是「N 是多少、每個都帶到了嗎」這個可執行的問句。

### §33.1 量錯了尺，會偽裝成品質崩盤

④ 的 `lint 0/8` 與「修復真的把 8 則全毀了」在觀測上完全同形——而它其實是拿
一般題的 lint 去判送分題（送分題**明文禁止**用「正解：」開頭）。換對尺之後 0/8 → 5/8，
**而剩下 3 則裡有一則是修復把它寫到 656 字（上限 600）——真缺陷在錯的尺底下根本看不見。**
假警報不只是噪音，它會壓在真警報上面。

判準：**判分器要跟著題型分流**，而分流條件要寫在資料上（`ans == "#"`）不是寫在檔名或前綴上。

### §33.2 寫入屏障保證零附帶損害，同時讓整份文件層級的約束變成不可滿足

段落級修復的安全來自「模型只能寫指定段落、其餘逐位元組保留」。**字數是整份文件的性質**
——要壓到上限可能得動它不准動的段落。實測告知上限後再修一輪：
**656→649、764→768、622→638（兩則更長）**。

所以「把上限寫進 prompt」對**生成站**有效（整份都是它寫的，實測 86% → 100%），
對**修復站**無效。字數超標的題要**回生成站重寫**，不要對修復站喊字數。
**這是架構的取捨，不是 prompt 的缺陷。**

🔴 **補一條當時漏掉的第三條路（2026-08-24 round 3 實測）**：「回生成站重寫」預設
的是內容本身有問題、值得重新生成。但如果**內容已經對、只是長**（clinical／counseling
各一則超長 114～126 字，四段結構完整、`manufactured_tie` 沒有發生），回生成站重寫是
拿一次新的模型呼叫去賭它剛好又寫出同樣正確的內容還壓得進上限——多一次不確定性，
換不到更高的正確率。此時**直接精簡既有文字**（保留全部論點與四段結構，只砍冗詞、
合併重複的鋪陳句）比回生成站更省也更穩，前提是精簡本身不引入新論點、不改變任何
判斷——這仍然是「只修確認的錯」（節制門），只是這裡確認的錯是字數而不是內容。
判準：**先問內容是否已經正確**——正確就精簡，不正確才重寫；兩者用同一把尺
（`build_free.lint_free`）驗收，寫回前後都要跑一次確認仍是 0 fail。

### §33.3 選段規則：紅隊指的是一個「陳述」，而詞彙層只認「詞」

`target_keys` 原本只認選項字母、「正解」、「考點」這些**詞彙**。實測 5,761 則歷史修復輸入：

- 全形括號寫法「（D）段」詞彙層**整個看不見** → **513 則（8.9%）**，其中 54 則因此
  定位不到、被推去走已淘汰的全文修復。**漏掉的不是罕見寫法，是紅隊最常用的那一種。**
- finding **引號裡引述**的錯誤陳述被複述在別段（正解 650、考點 127）→ **1,011 則（17.5%）**
  至少漏一段沒送修。修完命中率、lint、附帶損害三個數字全都好看，**同一句錯話還留在頁面上**。

修法：只吃引號內 ≥6 字的引述（一般 n-gram 會把「臨床上常用於」這種到處都有的套話
變成全文修復），在全文出現幾段就送幾段。定位不到率 16.4% → 12.2%。

🔴 **配套**：選段放寬之後「命中率」會**機械下降**（每題平均送 1.43 → 2.30 段，
分母裡多了「含同一句話但其實沒錯」的段落）。實測 24/76＝32%，對照舊基準 81%。
**把它讀成「修復變差了」是錯的**——那個指標量的是送出去的段落有沒有被改，
它會隨選段規則移動。選段放寬時唯一仍然可信的是**附帶損害**（理論值 0，實測 0）。

### §33.4 操作卡叫模型回報的欄位，要有人讀

修復站的操作卡寫著「若你認為某個未被指涉的段落也該改，寫進 `建議另修` 欄回報，
由主控裁決」。2026-08-24 查證：**沒有任何程式讀它。** 模型每一輪都在回報
「這一段也有同樣的錯」，而那些回報一路落在地上。

判準：**prompt 裡出現「回報給主控」這種話時，去 grep 那個欄位名。**
grep 不到消費者，那句話就只是安慰。接上之後本輪它產出 28＋5＋5＋1 則第二輪工單。

## §34 條號指錯是一個會重複發生的缺陷類，不是單一事故

2026-08-24（round 3）把藥師 P6 法規詳解引用的 55 則／81 筆法條主張全部查完
（`tw_statute_search_text`，clean-room 唯一開放的窄門）：**71 match／7 out_of_corpus／
3 mismatch**。三筆全部同一種形狀——**答案與實質推理都對，唯獨條號錯**：

| 誤引 | 正確 | 兩者的關係 |
| --- | --- | --- |
| 藥事法第 28 條（西藥販賣業者駐店管理） | 第 32 條（醫療器材聘用技術人員） | 同法、鄰近條號、都在講「聘用什麼人管什麼」 |
| 藥師法第 11 條（執業以一處為限） | 第 10 條（歇業／停業 30 日內報備） | 同法、相鄰條號、都在講執業狀態變動 |
| 藥事法第 92 條（新藥許可證未依限回覆罰鍰） | 第 90 條（販賣供應劣藥罰鍰） | 同法、相近條號、都是罰則章節 |

**一般形式**：模型引用法條時最常見的錯不是「引錯法」或「編出不存在的條文」，
是**在正確的法、正確的章節附近，指到鄰居的條號**——因為條號鄰近的條文常常主題也相近，
語意上「合理」，讀起來不會有違和感，逐字審查看不出來，只有把條號真的去查一次才會現形。

**這與「wrong ruler」（§33.1）是同一個家族**：兩者都是「錯誤的東西讀起來完全合法」。
差別是 wrong ruler 錯在判分端、條號指錯錯在生成端，但**破案方法一樣**——找到一把
獨立於模型記憶的尺（這裡是 `tw_statute_search_text`，clean-room 明訂唯一可查證窄門），
把每一個看似成立的斷言真的量一次。

**判準（尚未升級為機器閘，先留在此當散文規則）**：任何詳解引用「法規名＋條號」且
該條號承載了**具體規範內容**（不是泛泛帶過），值得走一次本輪同款的稽核——抽出
`(law, article, claim)` 三元組、逐筆 `tw_statute_search_text` 查現行條文、比對 claim
的具體內容是否真的落在該條號。**這次只查了藥師科 P6 法規**；護理／社工／諮商／
教檢等科凡引用具體法條的詳解，同一種缺陷形狀大機率也存在、只是還沒有人查過。
分佈 3/81（3.7%）不算低，值得推廣，但推廣前腳本還沒寫成可重用的形式
（`pharm_statute_claims.json`／`pharm_statute_verdicts.json` 目前是這一科的一次性產物）。

🔴 **`CronCreate` 的一次性排程跨 session／compaction 邊界會消失、不執行也不留痕跡。**
round 2 結尾排定 16:17 執行的一次性 cron（訂了完成後自我刪除）——round 3 接手時

## §35 `type` 是模型自由造詞、不是 enum：關鍵字比對「缺陷類 finding」會漏接，但寬鬆補漏比不補更危險（2026-08-25）

`mkfix.py` 的 `is_defect()` 靠英文子字串關鍵字表（`data_defect`／`input_gap`）比對紅隊
finding 的 `type` 欄位，決定該列進修復站還是轉 `_fix_worklist.json` 資料層工單。稽核
`_build_features/goldens/` ＋ `_build_redteam/` 下 110 個形狀吻合的歷史
`_rt_*.json`／`*_union.json`，`type` 欄位**共 1805 種相異值**——它從來不是 enum，是每個
紅隊臂、每一輪自由造出來的自然語言標籤。同一語意（「詳解文字本身無誤，缺陷在來源
資料」）至少有 21 種中英文變體，其中 `來源資料殘缺`（21 例）、`source_defect`
（22 例）、`input_defect`（7 例）三種單一標籤合計超過 50 例，全部被現行關鍵字表漏接
——**不是「中文沒配到」，是任何固定關鍵字表都會過期**，因為 `type` 的生成端從未被
prompt 約束成固定詞彙。

漏接的後果：這些 finding 沒被排除，反而被當「可用文字修的真發現」送進修復站——
`mkfix.build()` 不會報錯，也沒有任何門攔下來（explanations-redteam.md §13 修復站的
三道門只看格式與段落結構，看不出「這則 finding 根本無事可改」）。下游只有
`ab8_segfix.py` 的段落定位器會偶然
踩到（找不到可對應的段落鍵而卡住），但那是巧合、不是保證。

**補漏的直覺解法——多加幾個中文關鍵字子字串（如「缺陷」「資料」「殘缺」）——是錯的，
而且錯得比不補更隱蔽**：同一批稽核資料裡，「缺陷回報寫入正文」這個語意群
（`缺陷回報寫入正文`／`資料缺陷寫進正文`／`正文寫入資料缺陷`／`data_defect_in_body`…
十餘種變體、超過 60 例）表面上也很像資料層缺陷（`detail` 裡經常同時提到「資料殘缺」），
但它的 `suggest` 每一則都是具體的**文字重寫指示**（刪掉洩漏到正文的內部判定敘述、
保留可講的部分、必要時才另外標記 `data_defect`）——這是**詳解文字違規**，不是「無事
可改」。用寬鬆關鍵字子字串會把這整族也掃進 `DEFECT`；`is_defect()` 一旦判真，該
finding 就不進 `real`，若那是某列唯一的 finding，`real` 濾空、整列從 `items` **靜默
消失**——真正該進修復站被改寫的列，反而被錯誤地移去資料層工單晾著。方向和原本的
bug 相反，但一樣是靜默 misroute，而且更難發現（因為它偽裝成「正確地排除了缺陷」）。

**正確做法**：逐一讀 `detail`／`suggest` 判斷語意（唯有「詳解本身無誤／不需更動」才算），
只把驗證過的標籤**整串放進一個 exact-match 集合**，不當子字串關鍵字；新標籤出現時
再稽核、再加，不要憑標籤長得像不像就寬鬆比對。**判準可通用化**：分類器要在「自由
文字標籤」上做「這類要特殊處理」的判斷時，關鍵字子字串比對的假陽性率會隨標籤自由度
上升，而越寬鬆的比對抓到的假陽性越可能是「看起來像但語意相反」的近鄰類別（此處近鄰
是「資料層缺陷」vs「詳解文字違規、只是提到了資料層缺陷」）。子字串比對只安全用在
已逐一驗證「所有出現處語意都一致」的複合詞根——如 `data_defect_unreported`／
`source_data_defect` 都以 `data_defect` 為詞根、且全部同語意，這種情況子字串才安全；
一旦詞根本身可能出現在語意相反的合成詞裡（`來源資料` 是 `來源資料缺陷處理錯誤`／
`來源資料殘缺寫進正文` 的子字串，但那兩者都屬於「寫入正文」語意群，不該收），
就必須整串比對。

修復見 `mkfix.py` 的 `DEFECT_LABELS`（14 個精確標籤，逐筆稽核依據見程式內註解）；
`demo()` 同時斷言正例（新標籤該判真）與反例（「…寫入正文」一族不該判真）——只留
正例會讓下一次「順手加關鍵字」的修改無聲重犯本節的陷阱。回歸驗證法：對比新舊
`is_defect()` 在全部歷史檔上跑出的 `items`／`worklist` 差異，斷言（一）`items` 的 qid
集合只能變小不能變大（`is_defect` 只會變寬，不會變嚴）、（二）每個從 `items` 移除的
qid 都能用新收標籤解釋、（三）留在 `items` 裡的列除了 `findings` 只減不變之外，其餘
欄位逐位元組相同——三條同時成立才算修對，任何一條破了就是新迴歸，不是預期變動。

## §36 紅隊卡若把自己在抓的壞味道原句寫進指示裡，生成端照抄就會被誤判過關（2026-08-25）

`OPCARD_essay30_rt.md`（essay30 自己的紅隊卡）用來判「架構不可操作」的判準句
「每一點有沒有講清楚『這一層要證成什麼』」，跟生成卡（`OPCARD_essay30.md` §3）
與另一張紅隊卡（`OPCARD_rt_cpa_refs.md` 第1類）指名診斷過、判定為「元凶字句」的
壞味道**逐字相同**——那兩張卡在 2026-08-23 前後都已修正措辭，唯獨這張紅隊卡自己
還留著舊字句，直到今天才被抓到。連鎖後果：生成出來的 15 篇 lawyer 申論若寫法
剛好落在「檢驗」「衡量」這種層級（正是舊字句在教它避免的寫法），紅隊卡拿它自己
在抓的壞味道原句當判準，抓到的產出**恰好符合判準字面**時反而會被判定過關——
一張卡如果拿「我在抓的壞味道長什麼樣子」的敘述本身當通過條件，抓到的東西剛好
符合那個敘述時，判準會把它讀成「這裡有講到重點」而不是「這裡犯了我在防的錯」。

通則：**同一族卡（生成卡／紅隊卡／複用卡）修正措辭時，要跨卡一次查全部引用同一
句判準的地方**，不能只改被實際回報出錯的那一張——同一句壞味道的文字可能被抄進
好幾張卡當「反面範例」或「判準敘述」，改一張不會連動另一張，而紅隊卡是最容易被
漏掉的一張（它不直接產出內容，出錯不會立刻在成品上顯形，只會讓壞成品看起來合格）。
查法：`grep` 同族卡之間重複出現的長句（>15 字的完整片語，不是關鍵字），逐句核對
「這句話在每一張卡裡扮演的角色是不是一致」——同一句話在生成卡裡是「不要這樣寫」，
在紅隊卡裡卻被讀成「有講到這個就算過」，角色互換而沒人發現，就是本節的病灶。

## §13.2 `ab8_segfix.py` 拼回 naive join：中段鍵清空後留下 4 個連續換行（2026-08-28 實測；已升級：`splice_segments()` + 模組層 selftest）

段落級修復（§13）拼回步驟 `rebuilt = "\n\n".join(...)` 是逐鍵 join：中段鍵被
清空成 `""`（既定技巧——把已併入正解段開頭的獨立段落折疊消失，見本檔 §13.1）
且該鍵不是 `segs` 最後一個時，join 會在該處留下**4 個連續換行**，不是乾淨的 2 個。

`expl_lint.lint_one` 與本站自己的 `segments()` 都用 `re.split(r"\n{2,}", ...)`
切段，2 個或 4 個連續換行對它們是同一種分隔符——**lint 100% pass 的檔案裡完全
可能藏著這種瑕疵**，機檢看不到、人眼看了會皺眼。核對方式：已上線的
`_sf_n7fixhigh1_clin_merged.json`（101_101030_特論二_32，C 段折疊消失、C 不是
最後一個鍵）拼接處目前是乾淨的，但用**現在**這支 `merge()` 重算同一份輸入會
產生 4 個換行——這道正規化在某個時間點消失了，而且沒有回歸測試守著它，
n7fixhigh1／n7fixhigh2 兩批大概率也踩過同一問題，只是沒人往回追。

**修法**：把拼回邏輯抽成 `splice_segments(segs, new)`，join 之後補一行
`re.sub(r"\n{3,}", "\n\n", rebuilt).rstrip()`。不影響 `hit`／`collat`／`ok`
計分——那些數字都是拿 `segments()` 重新切過 `rebuilt` 算的，`re.split(r"\n{2,}", ...)`
本來就把 2+ 個換行當同一種分隔符，這純粹是清理寫進 `_{pref}_merged.json`
的輸出品質。回歸測試已收進模組層 selftest（重演「中段鍵清空、且非最後一鍵」
這個形狀）。範圍只動 `ab8_segfix.py` 一支檔案，不回頭改動任何既有
`bank.json`／`explanations.json`／goldens 資料——已上線的詳解若真的踩過
這個洞，屬於另一輪的資料層清理，不在本次範圍。
